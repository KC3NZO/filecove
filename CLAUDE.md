# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It holds only what every session needs. Area-specific detail lives in `.claude/rules/` (see [Where the details are](#where-the-details-are)) and loads automatically when matching files are read.

## Project

A client-side file manager React component built with React 19, TypeScript, Vite 8 and Material UI (`@mui/material` 9.x). It will later be extracted and published as a package, so write components with that in mind: self-contained, with no app-specific assumptions baked in. `src/` is the component and nothing else, laid out as it will be published. The Vite app in `playground/` is its development host and is never published.

A published component shouldn't force a global `CssBaseline` or its own `ThemeProvider` on consumers, so those stay in the playground and the component itself stays theme-agnostic.

**Pigment CSS is not used, and will not be.** The repo name mentions it, but styling runs on MUI's default Emotion runtime (`@emotion/react`, `@emotion/styled`). Do not add `@mui/material-pigment-css` or its Vite plugin, and do not write Pigment-style (`css`, `styled` from Pigment) code.

## Commands

The package manager is **Bun** (`bun.lock`). Use `bun` / `bunx` for everything, including installs and registry lookups such as `bun info <pkg>`. **Never use `npm` or `npx`**; they are broken on the maintainer's machine.

- `bun run dev` starts the Vite dev server.
- `bun run build` runs `tsc -b && vite build`. This is the only type-check; Vite itself does not type-check.
- `bun run lint` runs `oxlint` (not ESLint).
- `bun run preview` serves the production build.

There is no test runner configured.

## Layout

**Playground.** `index.html` loads `playground/main.tsx`, which mounts `<App />` (`playground/app.tsx`) inside `StrictMode` and the `Theme` wrapper (`playground/theme.tsx`, `ThemeProvider` plus `CssBaseline`). The theme in `playground/styles/theme.ts` (CSS variables, light and dark following the OS, GNOME-like colors, ripples off) styles the dev host only. `App` renders `<FileManager>` full-viewport, imported from `src/index.ts` as a consumer would, with switches read from the URL in `playground/options.ts` (`?single`, `?rtl`, `?locale=`, `?uncontrolled`, `?downloadUrls`) and data from `playground/mocks/`: an in-memory adapter with simulated latency keyed by full paths, plus fake sections and demo actions. A folder named `restricted` deliberately fails to load, to show the error state. The playground controls the file manager as an app would, through its own hooks in `playground/hooks/`: the location in the URL's hash, the view settings in local storage, and the selection shown in a footer whose buttons call `apiRef` (see `props.md`). `?media` mounts `playground/media-app.tsx` instead, the media manager over its own mock libraries (`mocks/mock-media.ts`; see `media-manager.md`).

**Source.** `src/` is organised by kind of code, and `src/components/` holds only components. File names are lowercase.

- `index.ts` is the public entry. It exports `FileManager`, `MediaManager`, `MediaPicker`, `MediaFields`, `MediaTile`, `MediaRow`, `PropertyDisplay`, `IconProvider`, `enUS` (the English text of both) and the public types, and nothing else is public.
- `components/file-manager/` is the frame and its parts (`sidebar/`, `header-bar/`, `content/`, `context-menu/`, `dialogs/`, and `properties-pane.tsx`, which places the properties panel).
- `components/uploads/`, `components/downloads/`, `components/transfers/` and `components/properties/` have the upload, download, copy and move, and properties panels, kept free of file manager imports so the planned media manager can reuse them (see `uploads.md`, `download.md`, `transfers.md` and `properties.md`).
- `components/media-manager/` is `MediaManager`, a sibling of the file manager for looking through and choosing media, built from the shared parts and importing nothing from `components/file-manager/`, and `MediaPicker`, one library to find or upload an asset in for a field pointing at it, with nothing for managing it (see `media-manager.md`).
- `components/buttons/` has `TooltipIconButton`, the icon-only button with a tooltip, and `ToolbarActions`, the app's actions as a header's buttons and "More actions" menu, shared by the file manager and the panels.
- `components/icons/` has `Icon`, `IconProvider`, `IconSlot` (a name or the consumer's element in an icon's box), and `FileTypeIcon` / `FolderTypeIcon`, the only way to render `@react-symbols/icons`.
- `types/` holds shared and exported types, one file per domain, re-exported from `types/index.ts`. Files marked internal stay out of `src/index.ts`.
- `locales/` has the component's text, in English only (`enUS`).
- `hooks/`, `contexts/`, `store/` (the folder listing cache, the thumbnail and properties caches, and the upload, download and transfer queues), `utils/` (plain functions), `styles/` (container-query constants, style helpers) and `icon-sets/`.

Imports are relative, with no path alias. The only barrels are `src/index.ts` and `src/types/index.ts`; everything else is imported by file, e.g. `components/icons/icon`.

## The three props

`FileManager` (`src/components/file-manager/file-manager.tsx`) is a file manager for the web, so it has no built-in locations (no Home, Trash or Network). The consumer supplies everything:

- **`adapter`** (`types/adapter.ts`) is the backend contract. It is lazy: `list(folderId, { signal, cursor })` returns `{ entries, nextCursor }` for one folder, called when a folder is opened or expanded, and again for each further page while it hands back a `nextCursor`. Listings are saved, so a folder opened again shows at once while it's listed again in the background (`relistAfter`; see `file-manager.md`). `FileEntry.id` is opaque (a full path or a database id) and is only ever handed back to the adapter; the component never parses or joins paths. Grow the contract by adding optional members, never by changing `list`, so existing adapters keep working. Optional members switch features on: `createFolder`, `rename`, `copy`, `move`, `delete`, `trash` and `restore` (the backend's trash, which a section shows; see `trash.md`), `upload`, `content` (a file's URL or bytes, for the preview and for downloading a file), `download` (folders or several entries as one file to save, such as a zip), `downloadAcross` (entries of several folders, a search's results, as one such file), `thumbnail` (a small picture of a file for the list and the grid, asked for per view), `search` (the entries below a section's root matching what's typed, each with its trail, for a search everywhere), `properties` (one entry's fuller fields and properties of the backend's own, for the properties panel, described groups or plain `values` the app's definitions show), `updateProperties` (saving the fields `properties` marks editable, such as a picture's alt text, caption or tags, changed in the panel), `measure` (what's in folders, counted all the way down), `processing` and `watchProcessing` (how assets the media manager shows as being processed, `FileEntry.processing`, stand now, polled or pushed), and `process` (the media manager asking the backend to make something more or again of an asset already uploaded, with what its library's `processForm` holds) so far, and `checkName` holds names to the backend's own rules: New folder's and Rename's as they're typed, and uploads' before anything is sent. Entries and a folder's listing may carry `permissions` (`write`, `rename`, `move`, `delete`), so what the backend refuses isn't offered (see "Permissions" in `file-manager.md`).
- **`sections`** is `SectionGroup[]`. Each `Section` (id, label, icon, `rootId`, optional own `adapter`, optional `showFolders`, optional `importFrom`, optional `acceptUploads`, optional `readOnly`, optional `trash`, marking it as its adapter's trash) is an independent root, with no connection to other sections even when they share an adapter. A single `section` can be passed instead, and its folders then fill the sidebar (see `file-manager.md`).
- **`actions`** is `ActionGroup[]` for the context menu.

The properties panel shows the content's selection, or the open folder, docked beside the content or over it, from Alt+Enter, the view menu or `ActionContext.properties()`, with the app's optional `propertiesActions` in its header (see `properties.md`).

Opening a file goes to the optional `onOpenFile(entry, context)`, or to the built-in preview when there's none or it returns `false` (see `preview.md`). The preview shows images (zoomed, panned, turned, full screen), videos, audio, PDFs, text and fonts itself, the app's optional `previewers` show other kinds (or take over these), and `previewActions` puts the app's actions in its header. There's no built-in editor, by choice, and no previewer beyond the browser's formats, so the package carries no heavy library. Downloading saves a single file from `content`, and folders or several entries from `download`, prepared in the background and shown in a panel while it takes a moment, and the browser's own downloads show the progress (see `download.md`). Copies and moves, by the picker, a paste or a drop, run in the background too, a few at once, shown in a panel of their own while they take a moment, with Try again for one that fails, for what of it didn't go when the adapter reports each entry as it goes (`TransferOptions.onEntryDone`); between sections of different adapters, the file manager copies them across itself, reading through one's `list` and `content` and writing through the other's `upload` and `createFolder`, and a drop there copies unless Shift or ⌘ is held (see `transfers.md`). Entries go to the adapter's trash at once with `ActionContext.trash()`, or by a drop on it, and are restored from it, asking about names their folders have now as a paste does, and shown where they went back to, deleted for good, or all of it emptied (see `trash.md`). Renames, new folders, copies, moves, moves to the trash and restores can be undone and redone, several steps back, with Ctrl+Z, the main menu or the notice each change shows over the content, checked against the listings first; copies and moves only when `copy` and `move` resolve with what they made (`TransferResult`) or report it entry by entry, what went of one that failed partway too, the trash's when `trash` and `restore` do (`TrashResult`), and a delete or an upload ends the history (see `undo.md`).

The optional `localeText` and `locale` set the component's own text, and the language numbers, sizes, dates and the order of names follow (see `locale.md`).

The rest are optional, and MUI-like (see `props.md`): the location, the view, the order, hidden files, the hidden sidebar and its width, the docked properties and their width, the tree's expanded folders, the content's selection, the search and each view's zoom can each be controlled (`location` / `defaultLocation` / `onLocationChange`, and so on), `apiRef` takes a `FileManagerApi` (navigate, back, forward, refresh, reveal, focus, download, actionContext, search, closeSearch, editPath, goToPath, showShortcuts, undo, redo), `mainMenu` fills the sidebar's ☰ menu above its own "Keyboard shortcuts" (see `file-manager.md`), `limits` sets how much runs at once and is kept (uploads, downloads, transfers, thumbnails, kept listings and thumbnails, undo steps, the search delay), and the root takes `sx`, `ref` and the `div`'s own attributes. Props may change after mounting, `sections` and `adapter` included.

## Conventions

- Code in `src/` and `playground/` uses 4-space indentation, double quotes, and semicolons. The template-generated config files use 2 spaces and single quotes. Match the file you're editing.
- `tsconfig.app.json` is strict about a few things that commonly trip up edits:
  - `verbatimModuleSyntax`: type-only imports must use `import type`.
  - `erasableSyntaxOnly`: no `enum`, `namespace`, or constructor parameter properties.
  - `noUnusedLocals` and `noUnusedParameters` are errors in `bun run build`.
- Oxlint runs the `react`, `typescript` and `oxc` plugins with `react/rules-of-hooks` as an error. Type-aware linting is off.
- Styles use logical properties (`insetInline`, `paddingInlineStart`, `textAlign: "end"`), never left or right, so the component follows a right-to-left page that sets only `dir`, with no RTL plugin or theme `direction` asked of the consumer. A MUI component used here gets its physical left and right overridden (see `rtl.md`).
- No text is written in a component. Everything shown or read to screen readers is a key of `FileManagerLocaleText`, read with `useLocale()`, and new keys go in `enUS` too (see `locale.md`).
