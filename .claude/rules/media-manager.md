# Media manager

`MediaManager` (`src/components/media-manager/media-manager.tsx`, public) is libraries of media to look through and choose from, as a CMS's media library is, and a **media picker**: **each library holding one kind of asset**: pictures, videos, audio or documents, each shown in its own way, searched by name, each asset opened in the library's place, shown by the app's previewers with the properties its adapter hands over, and, while the app takes a choice, what's selected listed in a column beside them, put in order there, each pick with the app's own fields for this use of it, and Choose handing it over. It's a sibling of `FileManager`, not a mode of it. Its look and feel, browsing and choosing are built (the first design 2026-10-27, its contract reworked 2026-10-31); uploading and processing come next (see "Not yet").

**Not a file manager.** The user's direction (2026-10-27): it's dynamic, what's chosen carries what the app needs for each use of it, so it isn't laid out as the file manager is. What's selected is a list to work with on the end side, not a strip of thumbnails; an asset's details open in the library's place, not in a properties sidebar.

## Keeping apart from the file manager

Nothing under `components/media-manager/` imports from `components/file-manager/`. It's built from the shared parts: the adapter (`FileAdapter`, the same one, growing only by optional members), the folder store (`store/folder-store.ts`, through `useFolder` and `DataContext`), the thumbnail cache (`useThumbnail`), the properties panel and its cache (`components/properties/`), the icons, `TooltipIconButton`, the locale, the direction, and the style helpers (`styles/mixins.ts`, `styles/header-field.ts`). Something of the file manager's that the media manager needs, such as the preview dialog or a dialog's clash step, moves out of `file-manager/` first, in a change of its own that changes nothing else.

## Decided, for the contract

These were settled with the user before any code, and the code follows them:

- **The consumer defines what's shown, filled in and previewed** (the user's direction, 2026-10-31). The media manager hardcodes no fields, no properties and no player: what an asset shows is the app's definitions (`properties`, `PropertyDefinition`, as a data grid's columns: types, kinds, `options`, `multiple`, `valueGetter`, `valueFormatter`, `render`, `renderEdit`; see "Defined properties" in `properties.md`) of the values the adapter's `properties` hands over, and **how a property is drawn is the consumer's too** ("very important"): the built-in types are only the default, a formatter changes a little, and `render` draws it entirely (the playground's renditions as jobs with a percent); what's filled in for a pick is the app's `fields`, definitions of the same kind, which the media manager draws; how an asset plays or renders is the app's `previewers`. There's no built-in HLS, nor anything else beyond the asset's thumbnail. The backend hands over data only, and each library defines what it shows of it, all of it, in code (the user, 2026-10-31: a backend describing properties at runtime wasn't wanted).
- **Backend-neutral** (the user, 2026-10-28). How a backend stores assets, their renditions, tracks and processing is never the media manager's business, nor mirrored in its contract. A Laravel backend was worked through on paper as an example (a 1080p MKV with three audio tracks, three subtitles and an HLS ladder) only to see what the media manager must cope with: parts of the backend's naming, each with its own state, work that isn't one-to-one with parts, an asset usable while it's being redone, delivery data the backend hands over.
- **Assets, not files.** What's chosen is one logical item. Its generated files (renditions, responsive sizes, other formats) are the backend's, kept out of the listing, and never selectable on their own. An asset is a listed `FileEntry`; what the backend delivers it by (an HLS manifest, a poster, a `srcset`) goes in `FileEntry.meta`, which the media manager carries without reading and hands back with the pick, so there's no reference type of the media manager's.
- **Flat libraries.** A library is a section's root, its files listed flat; folders it lists are left out. Organising is by tags (the properties' `updateProperties`) and the search, not folders. A library per client or project is a section of its own.
- **Sectionable, across backends.** `sections` (groups) or a single `section`, as `FileManager` takes them, each an independent library with its own `adapter` (or the media manager's), `readOnly` and, later, `acceptUploads`. **What depends on the backend belongs to the library; what depends on the use belongs to the component**: a library's own `previewers` come first, then the media manager's, and its own `properties` in place of the media manager's, as each backend delivers and shapes its data in its own way; `fields` are the component's, handed the asset and its library, as what's asked of a pick depends on what the app picks it for.
- **One asset, one pick** (2026-10-31). An asset is the same wherever it's listed when it's from the same adapter with the same id, ids being unique only within an adapter: it shows selected in every library listing it, and is picked once. Two adapters never share an asset. So an app keeps a pick's `section.id` with its `asset.id` to find it again.
- **The selection spans libraries** (the user's case, 2026-10-27: a product's carousel taking pictures and videos). Libraries stay one kind each, for showing them; what's selected is what the app asked for, which may be of several kinds. The app passes only the libraries of the kinds it takes (`[images, videos]` for the carousel, `[images]` for a logo), so no prop says which kinds can be chosen. With `multiple`, what's selected stays as another library is shown, listed in the selected column, and handed over in the order set there; one at a time, selecting in another library replaces it. Rules such as "one video at most" are the app's.
- **One kind of asset a library** (the user's idea, 2026-10-27, replacing a mixed library with a kind filter): a `MediaSection` declares its `kind`, which picks its tiles' shape, and which the app's `fields` and previewers can go by. The media manager trusts the listing and never sorts files into kinds itself.
- **What crosses kinds belongs to the asset**: a video's posters, renditions, subtitles and audio tracks, a piece of audio's transcript or cover, are the asset's, never assets of other libraries. For now they're shown as properties the app defines (the playground's "Delivery", drawn by its own `render`s, the poster picked in place); the draft `mediaSlots` was dropped (2026-10-31) until the media manager has to act on them (choosing a poster, uploading a subtitle).
- **Processing results are the consumer's.** Nothing is hardcoded about what processing makes. Images are quick requests, video transcoding long jobs.
- **Job updates by polling and by push**, both, for when processing comes: an optional adapter member asking for jobs' states (polling, and what's still running after a reload) and an optional `watch` subscribing to them (push, the consumer's WebSocket or server-sent events inside the adapter). The component opens no socket itself. A job may cover several parts or none, and an asset with work running on it may still be usable.

- `open-button.tsx`, a tile's or a row's button opening its asset (`mediaOpenAsset`, "Open name", the `info` icon), on the panel's surface, shown as the pointer is over it or the focus is on it, always on a touch screen and in forced colors, out of the Tab order and `aria-hidden` as the file manager's ⋮ is, since Alt+Enter does the same; its click neither selects nor chooses.

- `choices-pane.tsx`, the selected column, `choice-list.tsx`, its list, and `choice-fields.tsx`, a pick's fields (see "The selected column").

## What it shows

- **The library**: the section root's listing, files only, hidden ones left out (`isHidden`), newest first, then by name (`compareNames`), all taken to be of the section's kind. An app wanting only pictures passes only its image libraries.
- **The search** filters by name as the file manager's folder search does (`searchTerms`, `holdsTerms`, `foldLetters`): every word typed, anywhere, case and accents aside. Escape in the field clears it, and so does ✕. Opening another library clears it.
- Assets the search leaves out stay selected, and stay in the selected column.

## Selecting and choosing

- **What's kept** (`Picks` in `media-frame.tsx`): the assets selected in every library, each by the id of the library it was picked in, with its entry as it was listed when picked (`asset`) and what the app's fields hold for it (`values`), in the order set, and the anchor of a Shift-click, by library and id. What's shown (`choices`, `MediaChoice[]`) is made from it each render: a pick whose library has gone goes; one picked in the open library, once it's listed, is its entry as listed now, gone when it isn't listed any more; one picked in another is as the open library lists it when it does, through the same adapter, or else as it was picked. The open library's share is what its grid shows selected (`selectedIds`): every pick through its adapter (`inOpen`, `adapterOf`), whichever library it was picked in, so an asset two libraries list is selected in both and picked once (`samePick`, by adapter and id). Every change keeps a pick's values: moving it, selecting around it, Select in the asset view.
- **`defaultValue`**: what's selected as it mounts, with each one's values, in its order, such as a product's carousel being edited, each matched to its library by `section.id` (`picksFrom`). A controlled `value` isn't there yet (see "Not yet").
- **One at a time** (the default): a click, or Space, selects the asset alone, in place of what was selected in any library.
- **`multiple`**: a click, or Space, adds the asset or takes it away, as a media picker does, and Shift adds those from the last one clicked to this one (`nextSelection` with `toggle` always on, on the open library's share); Shift and an arrow key add as they move; Ctrl+A selects all those shown. What's selected in other libraries stays in its place, and what's added goes at the end, in the order shown (`picksWith`).
- **Keys**: one Tab stop, the arrow keys moving by a tile or a line (`gridColumns`), Left and Right swapped right to left, Home and End. Alt+Enter opens the asset view.
- **Choosing** (`onChoose(choices)`): Choose hands over everything selected, in every library, each a `MediaChoice` (`asset`, `meta` and all, `section`, whose `kind` says what it is, and `values`), in the order set in the column; a double click or Enter on one chooses it, alone, or after the rest selected when `multiple`. Without `onChoose` there's no selected column and no choose bar, and a double click or Enter selects the asset alone and opens it.

## The selected column

While there's an `onChoose`, what's selected, every library's, is listed in a column on the media manager's end side (`choices-pane.tsx`, a `section` named "Selected", `mediaChosen`), with one asset or several (`multiple`), as WordPress's and Shopify's pickers keep a selection to work with. From `mediaWide` (1040px) it's docked from the top, `CHOICES_WIDTH` (320px) wide, an inset `background.paper` card as the library is; below it, it's an overlay at the end side, `min(360px, 90%)`, over a backdrop, opened by the choose bar's button and taking the focus, closed by its ✕ (`mediaCloseChosen`, only shown there), Escape or the backdrop, the focus going back to the button. Which it is is read from its computed `position` by a `ResizeObserver` on the frame, which closes the overlay as it docks.

- **Its header**: "Selected" (`h2`) with how many in a badge (`aria-hidden`; a hidden `status` says `mediaSelected`), and Clear selection while there's any. **Its foot**: Choose, contained, disabled with none. With none: `mediaNothingChosen` and the select-all icon. With none left, it takes the focus (`tabIndex` -1), when the last one taken out or Clear selection had it.
- **Each one** (`choice-list.tsx`, a `ul`, `mediaChosen`) is a row: its thumbnail (the "list" view, `CHOICE_THUMBNAIL`, 3rem square, through its own library's adapter) or its type's icon (audio's the music icon), its name and its library under it, or in its place, while `errors` have some for its fields, how many (`mediaChoiceProblems`, "2 fields to fix", in `error.main`, read after its name, as the row's description; see "The backend's errors"), so the rows stay as tall as each other, then its details button (`mediaChoiceDetails`, "Details for name", the `edit` icon) while the app has `fields`, and ✕ (`mediaRemoveChoice`). Both buttons are out of the Tab order, Enter and Delete doing the same. A click on the row opens its details. Taking one out deselects it in its library too. One just added is brought into view at the end.
- **Reordering** (the user asked for it, 2026-10-27): the order in the column is the order `onChoose` hands over, so a carousel's order is set there. The frame moves the picks (`moveChoice`), the list tells it which (`onMove(from, to)`).
  - **Dragging**: the row's main part drags it, not its buttons: the mouse once it has moved 4px; a finger once it has been held still 350 ms (`LONG_PRESS`), so a swipe still scrolls the list, and moving first is a swipe. The pointer is captured by the list, not the row, as React moving a row's element would lose it. The one dragged follows the pointer, lifted (a shadow), and those between where it was and where it's going slide a place to make room (`translateY` in `style`, 150 ms, not with reduced motion), all a slot apart (`slot`, read from the first two rows' `offsetTop`), so where it goes is its offset in slots. Near the list's top and bottom it scrolls. Dropped, the order changes, with no slide, and the click that follows isn't taken as one on the row; a `pointercancel` puts it back. While a finger drags, the list's `touchmove` is prevented, so it doesn't scroll too, and a long press brings up no menu or callout.
  - **The keyboard**: the list is one Tab stop (each row's main part a `button`, "name, 2 of 5", described by `mediaChoicesHint` and, with details, `mediaChoicesDetailsHint`), Up and Down going from one to the next, Home and End. Space picks one up (outlined in `primary`), Up, Down, Home and End move it, Space or Enter puts it down, and Escape puts it back where it was; leaving it puts it down where it is. Enter opens its details (or picks it up, without details). Delete or Backspace takes one out, the focus going to the next, or the one before at the end. Each step is said from the list's own `status` (`mediaChoicePickedUp`, `mediaChoiceMoved`, `mediaChoiceDropped`, `mediaChoiceCancelled`), as dnd-kit's sortable lists say them. A move keeps the focus on the one moved, given back in a layout effect, as React moving its element blurs it; the blur waits a microtask before putting it down, so that doesn't count as leaving.
- **One at a time** (without `multiple`, the user's call, 2026-10-27), there's no list, as there's nothing to put in order: the column shows the one selected straight away as a pick's details are shown (what it is, "Show in library", the app's fields), under "Selected" with Clear selection beside it, and with none the column isn't there at all, docked or overlay, nor the bottom bar's button for it (`data-empty`), only its Choose, disabled; selecting another puts it, and its own details, in its place.
- **A pick's details** (the user's idea, 2026-10-27): the column shows them in the list's place, a back arrow (`mediaChoicesBack`, taking the focus as they open) and "Details for name" over what it is (its picture, its name, its library, and "Show in library", `mediaShowInLibrary`, which opens its library at the asset view, closing the overlay), then the app's fields, `fields(asset, section)`, drawn by `choice-fields.tsx`. Back, or Escape, goes back to the list, the focus on that pick's row when it was in the details. A pick taken out, or gone, closes them.
- **The fields are entirely the app's** (the user's correction, 2026-10-27, and direction, 2026-10-31: the consumer defines them, the media manager draws them): as many as it wants, in groups, a field per language when it has several, each with its `lang` and `dir`; the media manager hardcodes no fields, no languages and no localized values. Each is a `PropertyDefinition`, as an asset's properties are, editable unless it says `editable: false`, which only shows what it holds (by `render` or as its type has it), left out while empty. `ChoiceFields` draws the groups in a box of their own, so the first is its first child and drops its rule, the rule under the pick's heading standing for it, each group (`role="group"`, named by its `h3` title when it has one) set apart by a rule as the properties' groups are, and each field always open, its label above it (not floating, which is placed physically, see `rtl.md`), " *" after a `required` one's (with `aria-required`, never `required`, so a form the app has around it isn't held up): by its `renderEdit`, else the built-in control of its type (`PropertyInput`, shared with the properties' editor): text in a small outlined field, one line or a growing `textarea` of 2 to 8 rows, `dir` "auto" unless given; a number typed as text meanwhile, so "1." on its way to "1.5" isn't cut short; a date in the browser's own picker; a boolean as a checkbox with its label beside it; `options` as a native select, its first choice `propertiesNone`, its arrow and padding put on the end side, or with `multiple` chips over a select of the rest; a list typed in as chips over a field adding one with Enter or a comma (`propertiesRemoveTag`, `propertiesAddTag`); else, with no type, its `render`, whose `save` sets the pick's value at once (the playground's focal point). Enter in a field on one line goes no further, so it doesn't submit the app's form. Each change sets one key of the pick's `values` (`setChoiceValue`), kept with the pick as it's moved and as other libraries are shown, and handed back with it. Ids are made from the indexes, as the app's keys may hold spaces. The fields are remounted for each pick.

### The backend's errors

The media manager never saves a pick: the app does, with its own form, and its backend answers. So what it refuses comes back through the app, as `errors` (`FieldErrors`, `types/property-definition.ts`, public), the backend's answer as it came, by its own keys, a message or a list of them each, as Laravel's validation errors are (`{ "items.0.title.en": ["The title field is required."] }`). The user's design (2026-10-31): no prefix, nothing mapped by the media manager, each field finding its own.

- **`errorKey({ index, entry })`** on a definition (`PropertyErrorKeyParams`) is the backend's key for that field of a pick, made from the pick's place among those selected, as the app sent them (``({ index }) => `items.${index}.title.en` ``). The keys are the app's, so a backend naming things otherwise than the fields (`translations.en.title`) works. A pick's fields find their messages through it (`fieldMessages`, `utils/field-errors.ts`; `messagesAt` takes a string or a list, empty ones left out).
- **Shown**: the messages under the field, each on a line of its own, isolated, in `error.main` at 0.75rem, with an id (`errorId`); the label in `error.main`; the built-in control marked (`error`, so `aria-invalid`) and described by them (`PropertyInput`'s `describedBy`, after the label for a list's field, and on the checkbox with its own `aria-invalid`). A field that isn't `editable` still shows while it has one. Not an `alert`, as a backend's answer may hold many at once; the row's count and the description say them.
- **Fields the app draws** are handed what they need in their params (`PropertyParams`): `errors`, all of them as the app passed them, `index`, the pick's place, and, with an `errorKey`, `errorId` and `error` (for `render` as for `renderEdit`), so one reads its own key (``errors[`items.${index}.focus`]``), or several, such as a language per tab, and marks itself. Without an `errorKey` the media manager knows nothing of its error: no message under it, no colour on its label, and its row doesn't count it. In the properties, `errors` is empty (`NO_ERRORS`) and `index` undefined, their saves showing their own failures.
- **The row** counts the pick's fields whose `errorKey` finds one (`countFieldErrors`, the frame's `problemsOf`, only while `errors` isn't empty), in place of its library. One at a time, there's no row; the details show at once.
- **The order.** The backend's keys go by the order the picks were saved in. Moved since, they'd show on another pick, so the app clears them, or maps them again, as it would a Laravel form's rows reordered. Nothing clears them by itself, as the app holds them.

## The asset view

An asset opens in the library's place (`media-asset.tsx`, a `section` named by the asset, over the library's panel), from its tile's Open button, Alt+Enter, a pick's "Show in library", or without `onChoose` a double click or Enter, as the user asked (2026-10-27) in place of a properties sidebar, and as a page rather than a modal, since a picker is often in the app's own dialog already, an asset has much to show, and the selected column stays beside it. The grid stays under it, hidden (`visibility`) but laid out, so it's scrolled where it was; back, its tile takes the focus, when the view had it.

- **Its header**: back (`mediaBackToLibrary`, "Back to Images", `arrowBack`, mirrored right to left), the name (`h2`), Previous and Next (`mediaPreviousAsset`, `mediaNextAsset`, chevrons, mirrored) through the library as shown, disabled at its ends and while the search leaves it out, and while choosing, Select (`mediaSelectAsset`, `aria-pressed`, contained with a check while selected), which adds it, puts it in place of what was selected one at a time, or takes it out.
- **Its body** is a container of its own (`MEDIA_ASSET_CONTAINER`): from `assetWide` (680px) the stage fills the room beside the details (`ASSET_DETAILS_WIDTH`, 340px), each scrolling on its own; below it, the stage is over the details (`min(60cqi, 22rem)` tall), scrolling together.
- **The stage** shows the asset by the first previewer that accepts it (`FilePreviewer`, the file manager's own type, so one serves both), of the library's own `previewers` then the component's, among those that can get what they read: one reading "content" or "text" needs the adapter's `content`. It's handed what it reads as the preview hands it (`Preview`): nothing; the adapter's `content` (`purpose` "preview"), a blob made a URL revoked as it goes; or the start of it as text (`readText`, `utils/preview.ts`), with a spinner (`loading`) meanwhile, and it's rendered filling the stage, inside `Suspense` (a lazy previewer shows the spinner) and an error boundary (`PreviewBoundary`), so a previewer throwing or calling `onError`, or the content failing, shows the message, or `mediaPreviewFailed`, with Try again (`tryAgain`), which loads it afresh. With none accepting it, the stage shows the adapter's thumbnail at `ASSET_PICTURE` (40rem), `contain`, the tile's smaller one standing in while it loads, or its type's icon. The media manager plays and renders nothing itself.
- **Its details** are the shared `PropertiesPanel`, `embedded` (no header, picture or name, which the view has) and without its own rows (`ownRows={false}`: no type, size, location, dates or dimensions of its own), so it shows only the app's definitions (`definitions`: the library's `properties`, or else the component's `properties(asset, section)`; see "Defined properties" in `properties.md`) of the `values` the adapter's `properties` hands over, in the consumer's groups, order and wording, or without any, the adapter's own groups, editable where they're marked so and the library isn't `readOnly`, the library listed again once one is saved (`onUpdated`).
- **Keys**: it takes the focus as it opens, and again when going on took it away (Previous disabled at the first). Escape goes back, unless a field being edited took it.

## Text

`MediaManagerLocaleText` (public) has the media manager's own keys, named `media…` (`mediaPreviewFailed` for a previewer that failed without saying why), extends the properties panel's (`PropertiesLocaleText`, whose `propertiesNone`, `propertiesAddOption`, `propertiesAddTag`, `propertiesRemoveTag`, `propertiesYes` and `propertiesNo` a pick's fields read too, as they're drawn by the same controls), and picks the few of the file manager's both show (`loading`, `tryAgain`, `itemCount`, the type labels). The app's fields, groups, properties and previewers bring their own text, in the app's language. `enUS` has every key of both components (`LocaleText`, internal), and `Locale.text` is that, so the shared panels read theirs whichever component provides it (see `locale.md`).

## Playground

`?media` shows `playground/media-app.tsx` in place of the file manager: the media manager full-viewport over a footer saying what was last chosen, each pick as an app would store it (`videos:/videos/intro.webm`) with what its fields hold. It defines the libraries as an app would, on two backends from `mocks/mock-media.ts`: This site (`siteMediaAdapter`) with Images (36 pictures, an SVG, a TIFF and a hidden file), Videos (8), Audio (7) and Documents (PDFs and a spreadsheet), and Shared's Stock photos (`stockMediaAdapter`, `readOnly`) and Old archive, which fails to list.

- **The backend** (`withMedia`): each listing's assets carry `media` made up from the name (a picture's dimensions, a video's dimensions and length, a sound's length), and a video its delivery in `meta` (`hls`, a made-up manifest URL, `poster`, the frame in use, and `sample`, MDN's clip for the stand-in player); a video's thumbnail is its poster frame; and `properties` hands over only `values`, plain data by the backend's own keys (`propertiesOf`): the format and tags of each; a picture's alt text, caption, the day it was taken, its usage, whether it's for commercial use and its credit (Stock photos' licensed, credited, and commercial); a video's poster frames and the one in use (`PosterChoice`), its renditions as the backend's jobs (`RenditionJob`: done, waiting, failed with why, or under way with a percent; `release-teaser.mp4`'s made one after another, 12 s each, from when the page loaded, one video in five with one that failed), its audio tracks and subtitles (`Track`, marked default or forced), its manifest and caption; a sound's bit rate; a document's pages; with what's saved over them, by `updateProperties` in a map by backend and id, failing a value with "fail" in it. Stock photos' can't be edited.
- **The previewers** (`playground/media-previewers.tsx`): Videos' own `hlsPreviewer` (reads nothing, accepts what has `meta.hls`), a stand-in playing the MDN clip under the video's poster with an "HLS stand-in" badge, where an app would hand `meta.hls` to hls.js; and the component's `audioPreviewer`, for sound in any library, playing the adapter's `content`. Pictures and documents have none, and show their thumbnail.
- **The properties** (`playground/media-properties.tsx`): the component's `assetProperties`, by kind, and Videos' own `videoProperties`. Every kind's dimensions (a string put together by `valueGetter` from `entry.media`), length (`duration`), format, size (`size`, from the entry) and date added (`datetime`, from the entry); a video's quality (a height made "4K" or "Full HD" by a `valueFormatter`, typed `PropertyDefinition<number>`) and a sound's bit rate ("320 kbps"); a picture's day taken (`date`), Description (alt text, `maxLength` 250, and caption, `multiline`, editable), Rights (usage from `options`, commercial use, a `boolean`, and credit, editable); free Tags (`multiple`). Videos' own adds Delivery, drawn by the playground's components through `render`: the Poster (`PosterPicker`, a radio group of the frames, the one in use ringed, saving the choice through `save`, disabled without it), Renditions (`JobList`, which polls `pollRenditions` every second while any job is unfinished, as an app would poll its API, a bar under one under way), Audio tracks and Subtitles (`TrackList`), and the manifest (`url`, copyable), then a caption and Tags chosen from the site's own (`options` with `multiple`).
- **The fields** (`playground/media-fields.tsx`, `pickFields`), as a site's carousel would ask them, a field per language of the site's (English, Français, فارسی, each with its `lang` and `dir`, keyed `title.en` and so on): a picture's Title, Alt text (English `required`) and Layout (Decorative, a Fit from `options`, and a Focal point, nine points drawn by `render` and set through `save`); a video's Title (English `required`) and Playback (Play on its own, Loop, Start at, a number, and Show on, chosen from `options` with `multiple`); a sound's Title and Keywords (typed in, `multiple`); a document's Link text and Show until (a `date`).
- **Saving** (`playground/mocks/mock-save.ts`, `savePicks`): Choose saves the picks first, as an app saves a product's carousel, sent as `items` in the order set, and after 400 ms the mock answers as a Laravel form request would, a 422's `errors` by `items.N.…`, or nothing, when the footer shows what's chosen. It refuses a picture's missing English alt text unless it's decorative (`alt.en`), a focal point other than the centre while it's shown whole (`focus`), a video's missing English title (`title.en`), a start at or past its length (`start`), and a video playing on its own, not looped, with nowhere to show (`showOn`). The footer says how many it refused. Each field has its `errorKey` (`keyOf`, `items.${index}.…`), but the focal point, which reads `errors` with `index` itself, outlining its points and saying the message under them.
- `?single` shows Images alone, `?multiple` chooses several, from any of the libraries, `?browse` leaves out `onChoose`, and `?locale=` and `?rtl` work as for the file manager.

## Not yet

- **Holding Choose back** until a pick's `required` fields are filled, and saying so on its row; what the app gets to prefill a pick's fields from (the asset's own properties).
- **Errors no field claims**: those no `errorKey` names, and a pick's or the whole selection's own (`items.0`, `items`), shown nowhere yet; and a field the app draws, finding its own, isn't counted on its row.
- **Acting on an asset's parts**: choosing the poster in use, uploading into one (a custom poster, a subtitle file), picking an asset of another library to link (the media manager opened as a picker), "used by" before an asset others link to is deleted. They're property groups until then.
- **Uploading**, through the shared upload queue and panel, by a button, a drop and a paste, into the open library by its `acceptUploads`, files showing in the grid as they come and while they're processed; meanwhile files dropped on the media manager are left to the browser.
- **Processing and its jobs** (`jobs` and `watch`, above), and the job tracker and its panel, shaped like the upload queue, surviving a reload.
- **The props checklist** (`props.md`): the open library, the search, the selection (`value` / `onChange`, `MediaChoice[]` with their values; only `defaultValue` so far) and the asset open controlled (`x` / `defaultX` / `onXChange`), an `apiRef` (focus, refresh, open a library, open an asset, select, choose), `limits`, `relistAfter`, and announcements, such as the number of matches.

- **Virtualization**: every tile renders, so a library of thousands is slow; the grid needs the file manager's lines (see `virtualization.md`).
- **Sorting** other than newest first, and a list view.
- **Folders listed** by a library, now left out.
- **The selected column**: an optional `max`, or a check of the app's own disabling Choose with its message, should apps need them; resizing it (`ResizeEdge`, once shared).
- **A mixed view**, everything of every kind at once, if an app ever asks for one; by choice not now.
- **Resizing** the docked libraries (`ResizeEdge`, once shared).
- **Touch**: a long-press, and the check on every tile while selecting several.
