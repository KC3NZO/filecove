# Media manager

`MediaManager` (`src/components/media-manager/media-manager.tsx`, public) is libraries of media to look through and choose from, as a CMS's media library is, and a **media picker**: **each library holding one kind of asset**: pictures, videos, audio or documents, each shown in its own way, searched by name, each asset opened in the library's place, shown by the app's previewers with the properties its adapter hands over, and, while the app takes a choice, what's selected listed in a column beside them, put in order there, each pick with the app's own fields for this use of it, and Choose handing it over. It's a sibling of `FileManager`, not a mode of it. Its look and feel, browsing, choosing, uploading and processing are built (the first design 2026-10-27, its contract reworked, uploading and processing added 2026-10-31, processing again 2026-11-01).

**Not a file manager.** The user's direction (2026-10-27): it's dynamic, what's chosen carries what the app needs for each use of it, so it isn't laid out as the file manager is. What's selected is a list to work with on the end side, not a strip of thumbnails; an asset's details open in the library's place, not in a properties sidebar.

## Keeping apart from the file manager

Nothing under `components/media-manager/` imports from `components/file-manager/`. It's built from the shared parts: the adapter (`FileAdapter`, the same one, growing only by optional members), the folder store (`store/folder-store.ts`, through `useFolder` and `DataContext`), the thumbnail cache (`useThumbnail`), the properties panel and its cache (`components/properties/`), the icons, `TooltipIconButton`, the locale, the direction, and the style helpers (`styles/mixins.ts`, `styles/header-field.ts`). Something of the file manager's that the media manager needs, such as the preview dialog or a dialog's clash step, moves out of `file-manager/` first, in a change of its own that changes nothing else.

## Decided, for the contract

These were settled with the user before any code, and the code follows them:

- **The consumer defines what's shown, filled in and previewed** (the user's direction, 2026-10-31). The media manager hardcodes no fields, no properties and no player: what an asset shows is the app's definitions (`properties`, `PropertyDefinition`, as a data grid's columns: types, kinds, `options`, `multiple`, `valueGetter`, `valueFormatter`, `render`, `renderEdit`; see "Defined properties" in `properties.md`) of the values the adapter's `properties` hands over, and **how a property is drawn is the consumer's too** ("very important"): the built-in types are only the default, a formatter changes a little, and `render` draws it entirely (the playground's renditions as jobs with a percent); what's filled in is the app's own forms (see "Forms"); how an asset plays or renders is the app's `previewers`. There's no built-in HLS, nor anything else beyond the asset's thumbnail. The backend hands over data only, and each library defines what it shows of it, all of it, in code (the user, 2026-10-31: a backend describing properties at runtime wasn't wanted).
- **Backend-neutral** (the user, 2026-10-28). How a backend stores assets, their renditions, tracks and processing is never the media manager's business, nor mirrored in its contract. A Laravel backend was worked through on paper as an example (a 1080p MKV with three audio tracks, three subtitles and an HLS ladder) only to see what the media manager must cope with: parts of the backend's naming, each with its own state, work that isn't one-to-one with parts, an asset usable while it's being redone, delivery data the backend hands over.
- **Assets, not files.** What's chosen is one logical item. Its generated files (renditions, responsive sizes, other formats) are the backend's, kept out of the listing, and never selectable on their own. An asset is a listed `FileEntry`; what the backend delivers it by (an HLS manifest, a poster, a `srcset`) goes in `FileEntry.meta`, which the media manager carries without reading and hands back with the pick, so there's no reference type of the media manager's.
- **Flat libraries.** A library is a section's root, its files listed flat; folders it lists are left out. Organising is by tags (the properties' `updateProperties`) and the search, not folders. A library per client or project is a section of its own.
- **Sectionable, across backends.** `sections` (groups) or a single `section`, as `FileManager` takes them, each an independent library with its own `adapter` (or the media manager's), `readOnly`, `acceptUploads`, `uploadForm` and `processForm`. **What depends on the backend belongs to the library; what depends on the use belongs to the component**: a library's own `previewers` come first, then the media manager's, and its own `properties` in place of the media manager's, as each backend delivers and shapes its data in its own way; `pickForm` is the component's, handed the asset and its library, as what's asked of a pick depends on what the app picks it for, unless the library brings its own (`MediaSection.pickForm(asset)`), for what comes with its backend wherever it's picked, a stock photo's credit, say (the user's idea, built 2026-11-03).
- **One asset, one pick** (2026-10-31). An asset is the same wherever it's listed when it's from the same adapter with the same id, ids being unique only within an adapter: it shows selected in every library listing it, and is picked once. Two adapters never share an asset. So an app keeps a pick's `section.id` with its `asset.id` to find it again.
- **The selection spans libraries** (the user's case, 2026-10-27: a product's carousel taking pictures and videos). Libraries stay one kind each, for showing them; what's selected is what the app asked for, which may be of several kinds. The app passes only the libraries of the kinds it takes (`[images, videos]` for the carousel, `[images]` for a logo), so no prop says which kinds can be chosen. With `multiple`, what's selected stays as another library is shown, listed in the selected column, and handed over in the order set there; one at a time, selecting in another library replaces it. Rules such as "one video at most" are the app's, written in `canSelect` (see "Limiting the selection").
- **One kind of asset a library** (the user's idea, 2026-10-27, replacing a mixed library with a kind filter): a `MediaSection` declares its `kind`, which picks its tiles' shape and how it's shown by default (see "Layouts"), and which the app's `pickForm` and previewers can go by. The media manager trusts the listing and never sorts files into kinds itself.
- **What crosses kinds belongs to the asset**: a video's posters, renditions, subtitles and audio tracks, a piece of audio's transcript or cover, are the asset's, never assets of other libraries. For now they're shown as properties the app defines (the playground's "Delivery", drawn by its own `render`s, the poster picked in place); the draft `mediaSlots` was dropped (2026-10-31) until the media manager has to act on them (choosing a poster, uploading a subtitle).
- **Processing results are the consumer's.** Nothing is hardcoded about what processing makes. Images are quick requests, video transcoding long jobs.
- **Updates by polling and by push**, both: the adapter's optional `processing` asked how assets stand (polling), and its optional `watchProcessing` subscribing to them (push, the consumer's WebSocket or server-sent events inside the adapter); what's still running after a reload is in the listing itself. The component opens no socket itself. A job may cover several parts or none, so the backend weighs them into one progress for the asset, and an asset with work running on it may still be usable, which only the backend knows, so its listing says so (`usable`; see "Processing").

## What it shows

- **The library**: the section root's listing, files only, hidden ones left out (`isHidden`), newest first, then by name (`compareNames`), all taken to be of the section's kind. An app wanting only pictures passes only its image libraries.
- **The search** filters by name as the file manager's folder search does (`searchTerms`, `holdsTerms`, `foldLetters`): every word typed, anywhere, case and accents aside.
- **Its button and field** work as the file manager's do (the user's choice, 2026-11-02, over a field always shown): the header's search button (`search`, `aria-pressed`, `primary` while open), or Ctrl+F or ⌘F anywhere in the media manager in place of the browser's find, opens the field in the name's place, "Search in Images" (`searchIn`), and focuses it; the button stays where it is and closes it. Escape, or ✕ with nothing typed, closes it and clears what's typed, the focus going back to what had it, or else the button. ✕ with something typed only clears it, staying in the field. Down or Enter goes on to the assets. Leaving the field with nothing typed closes it, the focus staying where it went; with something typed it stays open, so what's filtered always shows why. Escape doesn't reach an app's dialog around it. Opening another library closes it. While an asset or a step is shown in the library's place, the button and the field are gone and Ctrl+F is the browser's, as there's nothing to filter, and a search under way comes back with the library. Ctrl+F isn't taken over the libraries' drawer or the selected column's overlay either.
- Assets the search leaves out stay selected, and stay in the selected column.

## Layouts

A library shows its assets as a grid of tiles or a list of rows, and it's the app's call which, as only it knows whether a library is browsed by looks or by name. Hard coding it made documents poor as tiles and wasted podcast covers in small rows, and leaving it only to the user would put a button in a narrow picker for libraries that gain nothing by it (the user's question, 2026-11-02).

- **`MediaSection.layouts`** is one option for all of it, so no second API arrives with the switch: `["list"]` fixes it, `["grid", "list"]` starts on the first with a button to the other, and leaving it out keeps the kind's own (`layoutsOf`, `utils/media.ts`): audio rows, the others tiles, with no button.
- **The kind and the layout are apart.** The kind gives a tile its shape, so audio's tiles are square (`TILE_LAYOUTS.audio`), and a row its icon. The layout is tile or row, for the grid (`media-grid.tsx`), `AssetOption`, the thumbnail's view and size, `UploadTile` (the picture being sent in a row's square) and the asset view's stand-in picture, so a thumbnail already loaded is what stands in.
- **The button** is in the header, between the search and Upload, named and shown for what it switches to (`gridView`, `listView`, shared with the file manager's header), and gone while an asset or a step is shown in the library's place. Its name changing on the focused button says it's done, so nothing is announced, as in the file manager's.
- **Public state**: `layout` / `defaultLayout` / `onLayoutChange` on `MediaManager`, through `useSetting`, one object (`MediaLayouts`) by library id, so an app can keep them across visits. The component writes to no storage. A library left out, or set to a layout it doesn't offer, shows the first it offers, so taking one away from `layouts` needs nothing else.
- **What's in view stays**: switching notes the first asset in view (`firstInView`, `utils/dom.ts`) and scrolls back to it in the new layout, as the rows and tiles aren't the same height; a list at its top stays at its top. Only the button does so: a `layout` changed by the app doesn't move the list.
- **`renderAsset`** is told `layout`, for a library offering both, and goes by it, as the playground's audio does. `layout` changing while `renderAsset` returns the same thing is its own to handle: a look fixed to one shape stays that shape inside the other's cell.
- **The playground**: Images and Videos `["grid", "list"]`, Audio `["list", "grid"]`, Documents `["list"]`, Stock photos none, its tiles being its own; the layouts are kept in local storage, and `?uncontrolled` only starts from them.

## Drawing assets

What a tile or a row looks like is the app's, as what's filled in and what's previewed are, and a small change shouldn't cost it the whole tile (the user's idea, 2026-11-02: keep the components used by default and export them, as a consumer may want only a little changed). So there are three steps, and most apps stop at the second:

1. **A style**: `<MediaTile {...params} sx={...} />`. Stable class names are still on the roadmap.
2. **A little changed**: `renderAsset` returning `MediaTile` or `MediaRow`, with `title`, `detail`, `badge`, `picture` or `sx` (`MediaAssetLookProps`): each left out stays as it is, and `null` takes it away. `undefined` leaving it as it is means an app can pass what an asset may not have, as the playground's audio does with `meta.title`.
3. **All its own**: `renderAsset` returning anything else.

- **`renderAsset`**, on `MediaSection`, then on `MediaManager` for the libraries without their own, as `previewers` and `properties` go, is handed `MediaAssetParams`: `asset`, `kind`, `section`, `adapter`, `thumbnail`, `selected` and `hold`.
- **The look is split from the behaviour.** `MediaTile` and `MediaRow` are looks only, with no props for selecting. What makes an asset one to select stays in `asset-option.tsx`, around whatever is drawn, so no app can break `role="option"`, the keys or the Tab stop. They only make sense inside `renderAsset`, as they read the locale and are marked by the `option` around them (`[role='option'][aria-selected='true'] &`, `[data-held='true'] &`).
- **Showing, not acting.** A button or a link inside an `option` is invalid for screen readers, and a click on it would also select, so what's drawn is for showing, and what acts belongs in the asset view (documented on `renderAsset`).
- **Hooks** are safe in `renderAsset`: it's drawn as a component of its own (`AssetBody`).
- **Thumbnails** arrive as a param, so apps don't bypass the cache, its limit on how many load at once or its cleanup. They're asked for at the kind's size whatever is drawn, so an app drawing a bigger picture has its adapter hand a bigger one, or uses its own URL in `meta`.
- **Why an asset can't be chosen can't be hidden.** `MediaTile` and `MediaRow` show `hold` as they always have. Under anything else the `option` shows it (`HoldLine`, `HoldBar`) and fades what's drawn. To tell the two apart, a look says it's there through `AssetLookContext` (`useAssetLook`), however deep in what's returned, in a layout effect, so nothing is painted first. `hold` is a required prop of the looks so spreading can't lose it.
- **Screen readers.** A look is read as it always was. An asset drawn entirely by the app is named by its name (`aria-label`), what's drawn being its description (`aria-describedby`), so it's never nameless, even if it's only a picture.
- **Height**: every asset of a library is drawn the same height (documented on `renderAsset`), as the grid is laid out in rows and, once virtualized, will go by one measured entry as `use-virtual-lines.ts` does. The user was told a size might be declared; measuring needs no new prop.
- **Memoizing.** `AssetOption` is memoized. An app's function that's new each render draws every asset again, so it's kept outside the component, as the playground's are. A section's object is only depended on while the library is drawn by the app (`drawAsset`), so the default tiles don't draw again if an app makes `sections` afresh.
- **`PropertyDisplay`** (public) is the same idea for a property: a `render` adding a little to how it's shown returns `<PropertyDisplay {...params} />` beside what it adds, rather than drawing the value again.
- **Not yet**: the selected column's rows and the asset view's picture aren't drawn by `renderAsset`; they still show the name and thumbnail.
- **The playground**: `playground/media-assets.tsx`, the Audio library a little changed (`MediaRow` or `MediaTile` by `layout`, with the episode's title and show, and a cover from the mock's `thumbnail`), Stock photos entirely its own (the expired ones show the fallback); `playground/media-properties.tsx`, "Format" using `PropertyDisplay` with a "Web-ready" chip.

## Selecting and choosing

- **What's kept** (`Picks` in `media-frame.tsx`): the assets selected in every library, each by the id of the library it was picked in, with its entry as it was listed when picked (`asset`) and what the app's form holds for it (`values`), `NO_VALUES` until it's changed, in the order set, and the anchor of a Shift-click, by library and id. What's shown (`choices`, `MediaChoice[]`) is made from it each render: a pick whose library has gone goes; one picked in the open library, once it's listed, is its entry as listed now, gone when it isn't listed any more; one picked in another is as the open library lists it when it does, through the same adapter, or else as it was picked. The open library's share is what its grid shows selected (`selectedIds`): every pick through its adapter (`inOpen`, `adapterOf`), whichever library it was picked in, so an asset two libraries list is selected in both and picked once (`samePick`, by adapter and id). Every change keeps a pick's values: moving it, selecting around it, Select in the asset view.
- **`defaultValue`**: what's selected as it mounts, with each one's values, in its order, such as a product's carousel being edited, each matched to its library by `section.id` (`picksGiven`).
- **`value` / `onChange`** (the user's call, 2026-11-03): what's selected kept by the app, `MediaChoice[]` with their values. `usePicks` (`hooks/use-picks.ts`) holds it, as `useSetting` can't: a pick holds more than the app's list says (its trail, `NO_VALUES`, the entry as last listed, the anchor), so the state stays `Picks` and the list goes in and out of it.
  - **Every change goes through its setter**, so all of `setPicks` report by the one way, and it decides. A change the app would see (`sameToApp`: another pick, order or values object, not a new entry for the same asset or a new trail) is told, and while `value` is passed only asked for, the anchor alone being kept; one it wouldn't see is made at once, so a listing refreshing a pick is never told. Two changes in one event build on each other (the state in `latest`), until the next render, which always follows, says what came of it, so what the app doesn't take is forgotten.
  - **Given back**: `onChange`'s and `onChoose`'s choices are copies (`handedCopy`) still marked with their trail and as defaulted (`PICK_TRAILS`, `DEFAULTED`), so what's handed back is the same pick. One the app copied or made finds its trail among those it was last asked to take and those kept (`known`), or has no known level, as one of `defaultValue` does, and its values count as changed, so they stop following the form's defaults. `value` new but holding the same objects changes nothing.
  - **Found gone** (`dropGone`): a pick whose library has gone, or no longer listed where it was picked, once its listing is complete, as a partial one is `loading` and finds nothing gone. It's now taken out and told, controlled or not, so the app isn't left holding what nothing shows; each once, so an app not taking it isn't told again.
  - `onChange` is called at every key typed in a form, from the event, or from an effect for what's gone or arrived, never while rendering.
- **Taking picks** (the user's call, 2026-11-03): any of `value`, `defaultValue`, `onChange` and `onChoose` turns on `choosing`, with the selected column, `maxChoices`, `canSelect`, and uploads selected as they arrive. **Finishing** needs `onChoose`, as MUI X's pickers have `onChange` and `onAccept`: without it there's no Choose or its foot, nothing said of what would hold it back (each row still says why), and a double click or Enter opens the asset, for picks that are a field in a form of the app's, saved by its own button.
- **One at a time** (the default): a click, or Space, selects the asset alone, in place of what was selected in any library.
- **`multiple`**: a click, or Space, adds the asset or takes it away, as a media picker does, and Shift adds those from the last one clicked to this one (`nextSelection` with `toggle` always on, on the open library's share); Shift and an arrow key add as they move; Ctrl+A selects all those shown. What's selected in other libraries stays in its place, and what's added goes at the end, in the order shown (`picksWith`).
- **Keys**: one Tab stop, the arrow keys moving by a tile or a line (`gridColumns`), Left and Right swapped right to left, Home and End. Alt+Enter opens the asset view.
- **What can't be chosen now** (`holds`, see "Processing") isn't selected by a click, Space, a Shift range or Ctrl+A, and a double click or Enter opens it instead; one selected already, as an upload still processed is, is taken out as any.
- **Choosing** (`onChoose(choices)`): Choose hands over everything selected, in every library, each a `MediaChoice` (`asset`, `meta` and all, `section`, whose `kind` says what it is, and `values`), in the order set in the column; a double click or Enter on one chooses it, alone, or after the rest selected when `multiple`. Browsing, with none of the props taking picks, there's no selected column and no choose bar, and a double click or Enter selects the asset alone and opens it.

## Limiting the selection

Two props of the component, as what's allowed depends on the use, not the backend, and only while the app takes a choice (2026-11-02). The app couldn't have done this itself: a library's `selectable(entry)` doesn't see the picks, and `onChange` only hears of them once they're made. The backend still has the last word, and the list's own errors stay the app's (see "The backend's errors").

- **`maxChoices`**, a number, with `multiple` only (one at a time always replaces): how many across the libraries, made whole and at least 1 (`countLimit`), `Infinity` or left out for none. It's a prop rather than a line in `canSelect`, as the component has to know the number to say "3 of 5", from nothing selected on: the column's badge (`mediaCountOf`), the choose bar's button and the `status` (`mediaSelectedOf`). It stops at 1 with `multiple` rather than replacing the pick, which is what leaving `multiple` out is for.
- **`canSelect(asset, section, choices)`**, the app's rule beside what's picked, such as one video at most, answering as `selectable` and `ready` do. `choices` leaves out the asset itself, and is none one at a time. Nothing shows before the rule applies, as the component can't read a function; an app wanting it known says so around the media manager. Both it and the library's `selectable` have to pass.
- **Adding** goes through one check (`fitting`, in the order given, each asked with those before it, so a range can't slip two videos in): a click, Space, a Shift range, Select all and arrivals. A range or Select all adds what fits and says so; a click with no room changes nothing, the anchor included, and says so; uploads still upload, those with no room only showing. Taking one out always works. A double click or Enter on one that can't be added opens it, as on one being processed. The asset view's Select is held, with why in its notice (`refusedNow`).
- **Shown**: refused by `canSelect`, an ordinary hold (`holds`, `refusalOf`): faded, its reason in place of its size. With no room (`full`), the tiles and rows not selected only dim, to 0.7 (`limited`, `data-limited`, `aria-disabled`), with no line of their own, as every tile saying it would be noise and taking any one out frees them all; it's said once, `mediaChoicesFull`, under the column's header, on the choose bar beside Choose (the column is an overlay there) and from the frame's own `status` as an add is refused (`useAnnouncer`). They can still be focused and opened. Selected tiles stay as they are.
- **Already too many** (`defaultValue`, a limit lowered, a rule changed): nothing is dropped, as what's filled in would go too. `choiceHolds` goes down the picks in order: those at or past the limit are refused (`mediaOverLimit`), and `canSelect` is asked of each with those before it, so of two videos the second is held, and moving them changes which. Their rows say why, and Choose is held by the existing "Take out the 2 that can't be chosen". Taking out a pick held for another reason can bring one past the limit back in, so that count may be one too many until then.
- **Browsing** (none of `value`, `defaultValue`, `onChange` and `onChoose`), neither applies.

## Forms

What's asked of files about to be uploaded, of an asset to be processed again and of a pick is a form of the app's. The user's objection (2026-11-01), to arrays of definitions handed the files or the asset: "the first thing we wanted was dynamicity, and this is not dynamic", as turning HLS off couldn't turn the renditions off and take their values; the user chose this over passing the values into those arrays, which would have gone on growing options (`disabled`, `visibleWhen`, `dependsOn`) into a form-builder language.

- **The shape** (`MediaForm<P>`, public): `{ defaults, render(params), ready(params) }`. `MediaSection.uploadForm(files)`, `MediaSection.processForm(asset)`, `MediaSection.pickForm(asset)` and `MediaManager`'s `pickForm(asset, section)` each return one, or `null` for nothing to ask, which is how the media manager, which can't see inside `render`, knows to send files at once or offer no Process. A pick's (`MediaPickForm`) also has `errorKeys`, an upload's (`MediaUploadForm`) `validate`. A pick's form is found by `pickFormOf` (`utils/media.ts`): the library's when it has `pickForm`, even when that returns `null`, so a library can ask nothing, or else the component's. So the check for it isn't a `??`, as `properties`' is. Any library having one gives picks their details, in `media-frame.tsx` as the component's prop does (`asksPicks`). A library's is typed `MediaPickForm<any>`, as `uploadForm` and `processForm` are, since `MediaSection` isn't generic over `V`, so an app whose forms have a shape of their own has only the component's prop checking it. Return the same form object each time, not one made in the function, as with `render`.
- **What it's handed** (`MediaFormParams<V>`, public): `values`, `setValues` (React's own setter's type, the whole values or a function of them), `section`, `adapter`, `errors` and `index`; an upload form `files` and `sending` (`MediaUploadFormParams`), a process form `asset` and `sending` (`MediaProcessFormParams`), a pick's `asset`, `choices` and `setChoiceValues` (`MediaPickFormParams<V>`). **The media manager keeps the values and never reads them**: the steps' `useState`, the picks' `values`. So a form follows itself in plain code: a field `disabled` or left out while another is off, and what it held dropped as `setValues` is called. Nothing is pruned for it, and what's there is sent.
- **Other picks** (the user's ask, 2026-11-02): `choices` is every pick as it stands, this one too, and `setChoiceValues(choice, next)` changes another's as `setValues` does its own, for rules across them, as the playground's "Cover of the carousel" takes the cover from whichever had it. `ready` reads `choices` too.
- **Types**: `V` may be the app's own shape on all three (`MediaUploadForm<VideoUpload>`), `MediaSection` taking them as `any` as a library doesn't know it. `defaults` is required exactly when `V` has required members (`FormDefaults`), so `values` doesn't promise what isn't there.
- **Drawn as a component of its own** (`MediaFormBody`), so hooks in `render` always belong to the same one. A component defined inside `render` would start over at each change, so one is kept outside it, as the playground's are, and `MediaFormBody` warns of it in the console, once, when `render` returns a different function of the same name; only the element it returns is looked at, not those inside it.
- **`defaults`** fill it as it's shown. A pick holds `NO_VALUES` until it's changed, and shows the form's defaults as they are now meanwhile (`defaultsOf`, in `choices`, and for one handed over without being picked first, by a double click or Enter), so `setChoiceValues` starts a function of the values from those. Selecting around it or moving it keeps it so (`DEFAULTED`, which `pickOf` reads, marks the choices made from defaults). At Choose each is handed its own copy (`handOver`), so an app changing one doesn't change another's, or the form's. A pick given with `defaultValue` keeps what it came with. Without a form, nothing is sent with an upload (`UploadOptions.values` undefined), from the step too.
- **`ready(params)`**, as `selectable` says it: `true`, `false` or why not, read from `MediaFormState<P>`, what it's drawn with less what changes it, as a pick's is asked while its form isn't open. Until it can, Upload and Process are held (`StepSend`, `aria-disabled`, so the focus stays), with why beside them (`MediaStep`'s `note`), and Choose is held, a pick's `AssetHold` being "unfilled" (`unfilledOf`): its row says why, or `mediaChoiceUnfilled`, and beside Choose one's why or `mediaChoicesUnfilled`, after those to take out and before those still processed. A double click or Enter on one not picked yet whose form isn't ready selects it instead. The user's `required` stays a star with `aria-required`, the form saying what it means; the backend still has the last word.
- **Refusals** (`MediaFormRefusal`, public): the adapter's `process`, or an upload form's `validate`, rejects with an `Error`, and `errors`, by the backend's keys, as Laravel's validation answers (`Object.assign(new Error(body.message), { errors: body.errors })`). `refusalOf` reads it by duck typing. The message always shows over the form (`FormFailure`, `role="alert"`, brought into view), as no field may name a key it has, and each field's under it by its `errorKey` with `index` 0, until it's sent again. `validate` is an upload's alone: files go one by one in the background once Upload is pressed, with the form gone, so a batch would be refused file by file with nothing left to fix it in. It's asked first, the step staying open, and leaving aborts it with nothing sent; without it, Upload goes at once.
- **While it's sent** (`useFormSend`, shared by both steps): `sending` is handed to the form, and to `MediaFields` through `{...form}`, where no field can be changed, a text field read-only with the focus kept, its label not greyed. One `disabled` is greyed as well.
- **A new batch starts afresh**: the upload step has a `key` of its own (`UploadStep.key`), so picking other files with the header's Upload while it's open draws the new form from its defaults.
- **A process form follows its asset**: it's handed the asset as listed now, and `processForm` asked again as it changes, a new object each time its backend's work moves on, so what's loaded from it goes by `asset.id`, as `poster-time.tsx` does. What's filled in stays. `null` by then holds Process back (`unavailable`, `mediaProcessUnavailable`), the form staying, as the one it opened with, rather than closing what's being filled in.
- **Escape in a step's form** only leaves the field, the step taking the focus, and a second goes back, as going back loses what's filled in (`MediaStep`).
- **`MediaFields`** (`media-fields.tsx`, public, with `MediaFieldsProps`) draws fields from their definitions for a form to be made of, in whole or part: `<MediaFields {...form} groups={groups} />`, with `setValues` overridden to change what a field's change sets, always the whole values, as they are by then (`latestRef`), so a field answering late, such as a poster being uploaded, doesn't undo what's changed meanwhile. `groups` are read only as they're drawn, so they may be made afresh from `values`. It draws them in a box of their own, so the first is its first child and drops its rule, each group (`role="group"`, named by its `h3` title when it has one) set apart by a rule as the properties' groups are, and each field always open, its label above it (not floating, which is placed physically, see `rtl.md`), " *" after a `required` one's (with `aria-required`, never `required`, so a form the app has around it isn't held up): by its `renderEdit`, else the built-in control of its type (`PropertyInput`, shared with the properties' editor): text in a small outlined field, one line or a growing `textarea` of 2 to 8 rows, `dir` "auto" unless given; a number typed as text meanwhile, so "1." on its way to "1.5" isn't cut short; a date in the browser's own picker; a boolean as a checkbox with its label beside it; `options` as a native select, its first choice `propertiesNone`, its arrow and padding put on the end side, or with `multiple` chips over a select of the rest; a list typed in as chips over a field adding one with Enter or a comma (`propertiesRemoveTag`, `propertiesAddTag`); else, with no type, its `render`, whose `save` sets its value at once (the playground's focal point). `editable: false` only shows what it holds (by `render` or as its type has it), left out while empty. Enter in a field on one line goes no further, so it doesn't submit the app's form. Ids are made from the indexes, as the app's keys may hold spaces. It finds each field's errors by its `errorKey`, from the `errors` and `index` a form spreads into it (see "The backend's errors"). In an upload form it hands the definitions' functions an entry standing in for the files (`uploadStandIn`: the first one's name and type, their size together, no id), as nothing is uploaded yet, and their params the files themselves (`PropertyParams.files`), so `entry` stays required everywhere (the user's choice).
- **`PropertyDefinition.disabled`**: in `MediaFields`, shown but off for now, its label greyed, handed on to `renderEdit` as `disabled`, with no `save` for `render`, and its control off (`PropertyInput`'s `off`, which unlike its `disabled` greys a text field too, rather than leaving it read-only with the focus kept in it, as while it's saved). The properties don't read it.

### The backend's errors

The media manager never saves a pick: the app does, with its own form, and its backend answers. So what it refuses comes back through the app, as `errors` (`FieldErrors`, `types/property-definition.ts`, public), the backend's answer as it came, by its own keys, a message or a list of them each, as Laravel's validation errors are (`{ "media.0.translations.en.title": ["The title field is required."] }`). The user's design (2026-10-31): no prefix, nothing mapped by the media manager, no key ever taken apart, only the keys the app names read. Forms (2026-11-01) leave the media manager no definitions to find a row's keys in, so a form names them (`errorKeys`, see "The row"). A `choiceErrorPrefix` stood in for a day and was taken out: it broke that design, and counted a field a form had just removed, "1 to fix" with nothing to fix.

- **`errorKey({ index, entry })`** on a definition (`PropertyErrorKeyParams`) is the backend's key for that field of a pick, or its keys, made from the pick's place (see "The order"): ``({ index }) => `media.${index}.loop` ``, or for a field holding several, such as a title a language under tabs, ``({ index }) => ["en", "ar"].map((code) => `media.${index}.translations.${code}.title`)``. The keys are the app's, in whatever shape its backend has (the user's are `media.0.translations.en.title`; never assume a shape in examples). `MediaFields` finds a field's messages through it (`fieldMessages`, `utils/field-errors.ts`: `messagesAt` takes a string or a list, empty ones left out, and several keys' messages are put together in their order, each once).
- **Shown**: the messages under the field, each on a line of its own, isolated, in `error.main` at 0.75rem, with an id (`errorId`); the label in `error.main`; the built-in control marked (`error`, so `aria-invalid`) and described by them (`PropertyInput`'s `describedBy`, after the label for a list's field, and on the checkbox with its own `aria-invalid`). A field that isn't `editable` still shows while it has one. Not an `alert`, as a backend's answer may hold many at once; the row's count and the description say them.
- **Fields the app draws** are handed what they need in their params (`PropertyParams`): `errors`, all of them as the app passed them, `index`, the pick's place, and, with an `errorKey`, `errorId` and `error` (for `render` as for `renderEdit`), so one marks itself as wrong and is described by the messages the media manager shows under it. `errorKey` is the only way `MediaFields` shows a field's messages (the user agreed, 2026-10-31): one reads `errors` itself only to mark finer parts of its own, as the playground's title marks the tab of each language with an error, and draws no messages, which would show twice. In the properties, `errors` is empty (`NO_ERRORS`) and `index` undefined, their saves showing their own failures.
- **A pick's own errors** (the user's ask, 2026-10-31: in both places), about it as a whole rather than one of its fields, such as "This video is still processing." or "The selected media no longer exists.", are found by `MediaManager`'s `choiceErrorKey({ index, entry })`, the backend's key for the pick, or its keys (``({ index }) => [`media.${index}`, `media.${index}.id`]``) (`choiceMessages`), one for every library, as every pick goes in one list. They show at the top of its details, under its heading and above its form (`ChoiceMessages`, isolated, in `error.main` at 0.8125rem, a 3px rule in the same colour at their start side, which forced colors keep), and its row counts them as one more to fix.
- **The list's own errors** (`media`, "You may choose at most 5") are the app's to show, around the media manager: they're about no pick, so the app shows them as easily, and the user declined (2026-10-31) a `selectionErrorKey` showing them above the picks. Nor does the media manager show keys nobody named, on purpose: the app may pass its whole form's errors (`name`, `price`), which it can't tell from its own without taking keys apart.
- **The row** counts each field with a message that the pick's form has now (`MediaPickForm.errorKeys`, `countErrorsAt`, the frame's `problemsOf`), asked with what it holds while it isn't open, one entry a field, a key or a field's keys, so a title with an error in two languages counts once, and its own errors as one more, in place of its library, only while `errors` isn't empty. What a form takes away, as Decorative takes the Alt text, isn't counted once it's gone, nor one off for now if it leaves that key out, as the playground's focal point does while it's shown whole. Without `errorKeys`, only a pick's own count. One at a time, there's no row; the details show at once.
- **The order** (the user's ask, 2026-10-31: the app does nothing for it). The backend's keys go by the order the app sent the picks in, which is the order it was handed them in at Choose, so the frame keeps that (`handedOrder`, the picks' `choiceKey`s, set by `handOver`, which every Choose, the button, the column's and a double click, goes through), and finds each pick's errors at its place there (`errorPlaces`), not its place now: moved from first to third, it still finds `media.0.…`. One taken out takes its errors with it; one added since has none (`errors` is `NO_ERRORS` for it, its `index` its place now), since the backend never saw it. Before any Choose, as with errors for picks the app gave as `defaultValue`, it's the order as the errors came (`errorsCame`, taken as `errors` changes, so the app passes the same object while they're the same). An app taking the picks without Choose (`value` and `onChange`) is never handed them, so it's always the order as the errors came.

## Processing
