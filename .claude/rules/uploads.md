# Uploads

The adapter's optional `upload(file, folderId, { signal, conflict, onProgress })` switches uploading on. It takes **one file per call**, so each file has its own progress, error and cancel, and the component decides how many run at once. The adapter reports progress with `onProgress(loaded, total)` (e.g. from `XMLHttpRequest`'s `upload.onprogress`), or never, and the file then shows as uploading with no figure. It may resolve with the file's entry as it now is (`Promise<FileEntry | void>`, so an adapter resolving with nothing still fits), which says where the file went even when it was kept under another name (see "Showing what arrived"). How the bytes travel (XHR, S3 multipart, tus, chunks) is the adapter's business. Folders are uploaded with the same call per file, each folder made first with the adapter's `createFolder` (see "Folders"), so the contract has nothing of its own for them.

## Shared with the media manager

A media manager will be built later as a sibling of `FileManager`, and it will upload too. So the upload code is split into what it can reuse and what belongs to the file manager:

- **Reusable**, and never importing from `components/file-manager/`: the queue (`store/upload-queue.ts`), its hook (`hooks/use-upload-queue.ts`), the panel (`components/uploads/upload-panel.tsx`, whose look, `styles/panel.ts`, the download panel shares), the types (`types/upload.ts`, `UploadOptions` in `types/adapter.ts`), and the panel's text, the keys of `UploadLocaleText` (`types/locale.ts`), which it reads with `useLocale()` and which is English outside a `FileManager` (see `locale.md`), with `keptBothName`, which the queue is handed (see "The queue").
- **The file manager's own**: the conflict check (`dialogs/upload-dialog.tsx`, which reads the folder store), the drop targets and the file picker in `file-manager.tsx`.

Keep it that way: `FileManager` imports the shared parts, never the other way round. Server-side processing (resizing, converting, HLS) is planned as a separate optional adapter surface, not as part of `upload`.

## The queue

`createUploadQueue(onChanged, keptBothName)` holds every upload added, in order, as `UploadItem`s (`types/upload.ts`): a file (`FileUploadItem`), or a folder with everything in it (`FolderUploadItem`), each `queued`, `uploading`, `done`, `failed` or `cancelled`. The item list is replaced, never mutated, for `useSyncExternalStore`.

- `add(adapter, folder, files, conflict)` queues files, one upload each, and `addFolders(adapter, folder, folders, conflict, accepts)` folders, one upload each (see "Folders"). Both return the ids of the uploads they queued, in order, for a host keeping something of its own per upload, as `FileManager` keeps where each went.
- An item's `entryId` is the id of what it put in its folder, once known: a file's when `upload` resolved with its entry, and a folder's once made, or found there to merge into.
- Inside, an upload is made of steps, each one call to the adapter: a file sent, a folder made, or a folder merged into listed. At most `MAX_ACTIVE` (3) calls run at once, across every upload; the rest wait, and start in the order their uploads were added.
- `cancel(id)` and `cancelAll()` abort the `signal` of what's under way. `retry(id)` queues a failed or cancelled upload again: a file from the start, a folder for what of it isn't done, so the folders already made and files already sent aren't made or sent again. `clear()` forgets the ended ones. `abortAll()` runs on unmount.
- `onChanged(adapter, folderIds)` is told the folders that calls reaching the adapter ended in, whether done, failed or cancelled, since a cancelled upload may have made the file anyway, and for a folder made, its own id too, in case a listing of that id is cached. It's throttled to once a second (`REPORT_INTERVAL`, first one at once), so a folder taking many small files isn't listed again for each. In `FileManager` it is `relist`, so the folder updates in every section sharing the adapter.
- `keptBothName` words the free name of a folder made beside a file of its name (see "Folders"), as `UploadLocaleText`'s does, so the queue holds no text of its own.
- `useUploadQueue(onChanged, keptBothName)` owns a queue for the life of the component and reads both through refs, so they may change every render. `FileManager` passes its own locale's `keptBothName`, since it provides the locale rather than reading it, and `useLocale()` in its own body would give English.

## Starting an upload

Every route ends in `askUpload` in `file-manager.tsx`, with a `DroppedFiles` (`files`, and `folders` as `FolderSource`s, see "Folders"):

- **`ActionContext.upload(files?)`** uploads into the context's `folder`. Without `files` it opens the browser's file picker, a hidden `<input type="file" multiple>` in the root, which only opens from a click or key press (an action's `onSelect` runs in one). It offers only the types the section takes, and is missing when the adapter has no `upload`, the section takes no uploads (see "Sections limiting uploads"), or while another upload is being checked. The consumer places and labels the action, as with every other one.
- **`ActionContext.uploadFolder()`** opens the same input as a folder picker (`webkitdirectory`, set by `pickFiles` as it opens), and uploads the folder picked. It's missing when `upload` is, when the adapter has no `createFolder`, or when the browser can't pick folders (`picksFolders`). The playground's "Upload folder…" sits beside "Upload files…".
- **Dropping files and folders from the desktop** onto the same targets that take dragged entries: a folder in the content, the open folder's empty space or a file in it, a tree folder, or a section row. `use-drop-target.ts` handles both kinds of drag. Dragged files show only as `"Files"` in `dataTransfer.types` until the drop, so they're offered by adapter alone (`DragContext.uploadInto`) and taken on drop (`filesIn`). The highlight, the panel outline and the 700 ms hold to expand all work as they do for entries. A drag from outside never says how it ended, so a target unmarks itself on `dragleave` and `drop`.
- **Pasting files from the system clipboard** (files copied in the desktop's file manager, a copied picture or screenshot) with the browser's paste key, Ctrl+V, ⌘V or Shift+Insert, into the folder Ctrl+V pastes into: the open folder from the content, or a tree row's folder (a section row's root). `folder-view.tsx` and the tree rows (`TreeItem`, on the item itself) hand their `paste` event to `pasteFiles` (`PasteFiles`, `types/menu.ts`) in `file-manager.tsx`, which uploads what `filesIn` (`utils/files.ts`, shared with drops) reads from `clipboardData`, through `offerUpload`, so a section refusing uploads and one upload being checked count as for a drop.
  - **The file manager's own entries come first**: while the clipboard of cut or copied entries can be pasted into that folder (`canPaste`, a paste running or not), or is being looked for again after a change (`lookup`, through that folder's adapter; see "Cut, copy and paste" in `file-manager.md`), nothing is uploaded, since the page can't tell which was copied last without asking for permission. Ctrl+V reaches the browser only when no action took it: the consumer's paste action runs and prevents it, and a disabled action lets the paste key through (`pastes` in `utils/shortcut.ts`, `runShortcut`), so the playground's Paste, greyed out with nothing to paste, still lets files be pasted. Shift+Insert always reaches the browser, which is why `pasteFiles` checks the clipboard itself.
  - Only the key pastes files. The menu's Paste can't, since a click reads the system clipboard only through `navigator.clipboard.read()`, which asks for permission and gives images alone.
  - What reaches the page is the browser's: some browsers and systems hand over files copied in a file manager, some only their paths as text, which can't be read, and some nothing at all (a paste with no types, seen copying from GNOME Files). A copied picture comes through either way. A picture comes as "image.png" every time, so a second one clashes and is asked about. Copied folders are uploaded as dropped ones are, when the browser hands them over as folders.
  - Text fields are left alone, as the paste goes only to the content and the tree.
- Files dropped anywhere the views don't take them are refused on the root (`refuseFiles`, dropEffect "none"), or the browser would open them in place of the page.

## Sections limiting uploads

A section's optional `acceptUploads` (`types/section.ts`, public, default `true`) says which files can be uploaded into its folders, though its adapter has `upload`: any (`true`), none (`false`, for a section the user may browse but not add files to), or those matching a string in the file input's `accept` syntax (`"image/*,.pdf"`). Unlike `importFrom`, it's about files from outside, not entries from other sections, and the two are independent. The helpers are in `utils/files.ts`, which imports nothing from `components/file-manager/`, so the media manager can use them too.

- **None:** `offerUpload` in `file-manager.tsx` checks `takesUploads`, the one place every route asks, so `ActionContext.upload` is missing in its folders (the playground's "Upload files…" hides), and its drop targets don't take files dragged from the desktop, showing the no-drop cursor, with the root refusing the drop so the browser doesn't open them.
- **Some:** `uploadPatterns` reads the string as a file input reads `accept`: comma-separated, trimmed and lowercased, extensions (".pdf"), MIME types ("image/png") and wildcards ("image/*"). A string with no pattern, or with `*/*`, takes any file. `acceptsFile` matches a file by its name's extension or its MIME type, without parameters; a file the browser gives no type, as for an extension it doesn't know, only matches an extension.
  - The picker offers only those types (`accept` on the hidden input, set by `pickFiles` as it opens), but most systems' pickers let the user pick any, so it's a convenience.
  - The upload check (below) leaves out what doesn't match, however it came: picked, dropped, pasted or handed to `ActionContext.upload(files)`, and so does reading a folder, for the files in it (see "Folders").
  - A drag only tells each file's type before the drop, not its name, so a target refuses it, with the no-drop cursor, only when no pattern is an extension and every file dragged has a type no pattern takes (`mayAccept`, through `DragContext.uploadInto`'s `items`). A folder, or a file of no type, may match, and the drop's check decides.
  - The adapter's `upload` still has the final say, and its error shows in the panel.
- It goes by the section, not the folder, so the same folder shown in another section takes what that section takes, as with `importFrom`, since sections are independent. Folders have no rule of their own, by choice: backends don't limit types per folder, a folder that needs a rule can be a section of its own (one can be rooted anywhere), and an adapter whose rule depends on the folder rejects the file in `upload` before sending anything, which shows in the panel.
- The playground's Design assets takes no uploads, as it takes no entries from other sections, and the Media bucket only pictures, videos and sound (`"image/*,video/*,audio/*"`).

## The check before queueing

`dialogs/upload-dialog.tsx` works like the paste dialog: it runs unseen, listing the folder first if it isn't cached, and only shows when it has something to ask or say.

- Names the folder's listing already has get the clash step the transfer and paste dialogs share (`conflict-step.tsx`, see "Name clashes" in `file-manager.md`): Skip, Replace or Merge, and Keep both as the main action; otherwise `conflict` is "keepBoth", so a clash the cache missed never overwrites anything.
- **Skip leaves the clashing files out of the queue** instead of sending them for the adapter to skip, since sending a large file for nothing could take minutes. "skip" still goes to the adapter for clashes the cache missed.
- A folder's name counts as a file's does, and only the folder's own: what's in it isn't read yet. **Replace merges it** into the folder of its name there (`FolderUpload.mergeInto`, see "Folders"), and reads Merge when no file clashes with a file. Keep both, and Replace where a file has the folder's name, make it under a free name (`freeName` in `utils/names.ts`, from `keptBothName`, "photos (2)"), one neither in the folder nor among the files and folders uploaded with it, since `createFolder` can neither replace nor keep both. Skip leaves it out.
- **A file never replaces a folder**: with Replace, a file whose name a folder has in the listing is queued with "keepBoth" (`startUpload` in `file-manager.tsx`), so the adapter is never asked to put it in the folder's place, and it has no name to be found by once it's there (see "Showing what arrived"). When every clash is between a file and a folder, there's no Replace to choose.
- Folders, when the adapter has no `createFolder`, and files of types the section doesn't take (`acceptUploads`) aren't uploaded. Both are named as left out (`uploadFoldersLeftOut`, `uploadTypesLeftOut`), with Cancel and Upload for the rest, or, when nothing is left, a "Couldn't upload" notice saying why (`uploadFoldersOnly`, `uploadTypesOnly`). The types are told by the section's label and the type labels the list shows ("Image, Video, and Audio", `Locale.describeAccepted`), as a list in the locale's way. Clashes are only looked for among the files that are uploaded.

## The panel

`components/uploads/upload-panel.tsx` takes the items and the queue's callbacks, and knows nothing of where it's shown. `FileManager` shows it as an inset panel under the content (`taskPanelSx`), below the download panel when both show, only while the queue has items, so it never covers files or the touch selection bar.

- The summary has a status icon (a progress ring while active, a check, or an error), a title ("Uploading 3 files", "Couldn't upload 1 file", "Uploaded 4 files") and the bytes sent, or the counts the title leaves out.
- The chevron folds the list away. The ✕ cancels everything still uploading, which stays listed to retry; once nothing is, ✕ forgets the list and the panel goes.
- Each row has the file's type icon, its name, a progress bar while uploading, and its status with the destination folder's name, or the adapter's error. An error without a message is kept as undefined in the queue, and the panel says `uploadFailed` in its place. Active rows can be cancelled, failed and cancelled ones retried, and done ones show a check, with "Show in folder" (`folderOpen`, `uploadShow`) before it when the host passes `onShow`, on the rows its `canShow` takes (see "Showing what arrived").
- A folder is one row, with its folder icon, its name, a bar of the bytes sent of all its files, and its status: Preparing while it's read (`uploadPreparing`), "12 of 340 files" (`uploadFolderProgress`), "340 files" once done, with how many were left out for their type (`uploadFolderSkipped`), Cancelled with how far it got, or how many files couldn't be uploaded (`uploadFolderFailed`) and the first error.
- Once something inside a folder has failed, its row has a chevron that unfolds what did (`FolderUploadItem.failures`): each file or folder below it by its path inside the folder, joined by " / ", with the adapter's error, a folder's saying how many files went with it (`uploadFailedFolder`). The queue lists the first `LISTED_FAILURES` (100) and counts the rest (`moreFailures`, "And 240 more"), so a backend failing every file of a large folder doesn't have the list copied for each. Retry empties it. The folder uploaded isn't listed under its own row, which already says why it failed, so a folder that couldn't be made at all, as one dropped onto the playground's `restricted`, has no chevron. The playground's adapter refuses any file with "fail" in its name, to see the list.
- The title counts files, a folder's one by one ("Uploading 338 files"), and says "Preparing to upload" (`uploadsPreparing`) while only folders are being read or empty ones made. A folder that failed or was cancelled with no file of it left counts as one.

## Folders

A folder dropped, pasted or picked is uploaded with everything in it when the section's adapter has `createFolder` as well as `upload`; without it, folders are left out, saying so (see "The check before queueing"). Each folder is made with `createFolder` in the one above it, as New folder makes one, and each file is sent into its folder's id with `upload`, so the component never joins paths, and a backend without real folders, such as a bucket, makes them in `createFolder` as it does for New folder.

- **Reading.** Each folder is a `FolderSource` (`types/upload.ts`): its name at once, for the check, and `read()` for what's in it, a `FolderContents` tree, called as its upload starts, since a large folder takes a while to read. A dropped or pasted one is the drop's `FileSystemDirectoryEntry` (`webkitGetAsEntry` in `filesIn`), taken while the event lasts and read later (`readFolder`, `utils/files.ts`), a batch of at most a hundred entries a call, as browsers hand them over. A picked one comes as every file below it with its path inside it (`webkitRelativePath`), put back together by `pickedFolder`. The picker leaves out folders with no file below them, so an empty one can't be picked, while dropped folders come as they are, empty ones included. The browser may ask first whether to upload that many files.
- **Order.** A folder is made before what goes in it, and once it is, its folders are queued before its files, as they're quick to make, so the folders show in the file manager early. Empty folders are made too.
- **Clashes inside.** A folder made for the upload is new, so its files go with "keepBoth", having nothing to clash with. A folder merged into is listed first with `list`, every page, whenever anything goes in it (`holds`), and the names it has settle what goes in, as `ConflictPolicy`'s "replace" says, at every depth:
  - A folder whose name a folder has there is merged into it the same way.
  - A folder whose name a file has there is made under a free name (`freeName`, worded by `keptBothName`, "images (2)"), one neither there nor among the files and folders going in beside it, since a folder never takes a file's place and `createFolder` can't keep both (`opened`). What fails in it is listed under that name.
  - A file whose name a folder has there goes with "keepBoth" in place of "replace", so the adapter is never asked to put it in the folder's place.
  - Other files go with the upload's choice, so with "replace", those with names already there replace them.
  - What the listing missed, made there meanwhile, is the adapter's to settle by the same rule.
- **Types.** Files of types the section doesn't take are left out as the folder is read (`accepts`, from `acceptUploads`), and so are folders left with nothing, unless they were empty to start with; the folder uploaded is always made. The row says how many files were left out.
- **Failures.** A folder that can't be made fails with everything in it, and the upload ends failed, counting the files that couldn't be uploaded and listing what failed (see "The panel"). A cancel leaves what was made and sent. Retry goes on from where either stopped.
- **Tried before.** A call cut short by a cancel, or one that failed on the way back, may have done its work all the same. So a folder whose making was tried before (`tried`) looks in the folder it goes in first, and takes a folder of its name there as the one made, merged into in case anything went in since, rather than failing as its name is taken. A file tried before in a folder the upload made goes with "replace", since the only thing there to clash with is its own earlier try, rather than being kept twice. A file on its own, or in a folder merged into, keeps the upload's choice. A folder whose `createFolder` resolves after the cancel counts as made at once.

## Showing what arrived

What an upload put in a folder is highlighted there for a moment, never selected, since an upload can end while the user is acting on other files, and "Show in folder" on its finished row goes there to see it. All of it is the file manager's: the panel only offers the button.

- **Finding it.** `FileManager` keeps where each upload went (`uploadPlaces`, an `UploadPlace` per upload id from what `add` and `addFolders` return): the location, and the name to find it by. What it put there is found by its `entryId`, or by that name when the adapter didn't say. A file kept beside one of its name (Keep both, with its name in the folder's cached listing as it's queued, or Replace, with a folder's name there) may have been given another, which only the adapter knows, so it has no name to be found by, and only its id finds it.
- **Arrivals.** As an upload is done, an `Arrival` (`types/view.ts`) is made for its folder (`arrive`), by adapter and folder id, so any section showing that folder highlights it. It waits `ARRIVAL_WAIT` (10 s) for a folder view to show it, as the folder may not be open, or be listed again only a moment later, since the queue reports at most once a second. The view that shows it tells the file manager (`onArrived`), which drops it. An upload whose folder isn't shown within the wait isn't highlighted.
- **The highlight.** `FolderView` looks for its folder's arrivals among the entries it shows and marks them `data-arrived` for `ARRIVED_FOR` (2.5 s). `arrivedMarker` (`styles/mixins.ts`) lays an accent tint over the row or tile, held and then faded out, as an inset box shadow, so it lies over the stripe, hover or selection, under the contents; in forced colors, which drop shadows, it's a `Highlight` outline (`forcedArrived`). Nothing is scrolled to for it. An entry hidden, or left out by a folder search, isn't shown, so it's only highlighted if it shows within the wait. A search's results show no highlight.
- **Show in folder** (`showUpload`) opens the folder the upload went into, ending a search even in the open folder, as "Open item location" does, with an arrival marked `show`, which the folder view also scrolls to and gives the Tab stop. The focus stays on the button, so the panel's other uploads can be shown in turn, and it's announced (`uploadShown`), since nothing else says it.
- It's offered (`canShowUpload`) while the section is there, served by the same adapter, and the folder hasn't gone: the places are rewritten with the history's (`revise`), so a folder renamed is followed, and one whose trail is cut short, by a folder deleted above it, one above it renamed with path ids, or its section going back to its root, can't be shown any more. Clearing the panel forgets the places of what it cleared (`clearUploads`).
- The playground's adapter resolves `upload` with the entry, under the name it kept the file as.

## Not yet
