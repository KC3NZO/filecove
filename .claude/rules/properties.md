# Properties

The properties are a **panel, not a dialog**: docked beside the content where there's room, over it where there isn't, as the sidebar is on the other side. It shows what's selected in the content and follows the selection, or the open folder itself while nothing is selected, as web file managers (Drive, OneDrive, Dropbox, Nextcloud) show details. A panel rather than GNOME's dialog, as the user prefers non-modal panels (see the download panel's history), and since the media manager to come needs the same panel for its details (WordPress's "Attachment details" beside the grid).

## What the adapter hands over

What a listing brings (`FileEntry`) is shown with nothing more of the adapter, so the panel works with any adapter. Two optional members, and two optional entry fields, add to it:

- **`FileEntry.createdAt`** and **`FileEntry.media`** (`MediaInfo`: `width`, `height`, `duration`), shown when the listing has them. `media` is only the basics for now, and is where the media manager's renditions will grow, by addition. The store compares `media` one level down, as `meta` (`sameEntry`).
- **`properties(entry, { signal })`** hands over one entry's `EntryProperties`: `entry`, the entry with fields the listing left out as too costly (`createdAt`, `media`), shown over the listed one (merged, `{ ...listed, ...fuller }`), the listing left as it is, and `groups` of the backend's own `PropertyField`s (an owner, permissions, a checksum, a link), each with an `id`, a `label` in the consumer's language, as action labels are, and a typed value the panel writes out in the `locale`: `text` (with an optional copy button), `number` (grouped), `size`, `date`, `link` (a new tab) or `tags` (chips). Text and tags fields marked `editable` are changed in the panel and saved through `updateProperties` (see "Editing fields"). Or, for the app's own definitions (see "Defined properties"), `values`, the entry's values by their keys, plain data as JSON brings it.
- **`updateProperties(entry, values, { signal })`** saves what the user changed of an entry's editable fields: `values` is a `PropertyValues` by the fields' ids or the definitions' `field` (`Record<string, unknown>`: a text field's string, a tags field's strings, a defined property's value as its type has it, or as its own editor or `render` saves it) (an editable field's `id` is unique among the entry's groups, its comment says), text trimmed, tags trimmed, each once, none empty, one field a call from the panel. It may resolve with the entry's `EntryProperties` as they now are, shown at once, or with nothing, and the panel shows the value as it was given; it rejects with an `Error` whose message shows under the field. Without it, nothing is editable, whatever the fields say. It's generic, so the media manager's alt text and caption are only text fields of a picture's (the user chose editing fields over tabs on 2026-10-26).
- **`measure(folders, { signal, showHidden, onProgress })`** counts what's in folders, all the way down, as `EntryTotals` (`files`, `folders`, `size`). It's separate from `properties` because it's the slow part (S3 has no folder sizes), so a backend can offer one without the other, and the panel shows the facts while the totals count. The folders may be in different folders (a search's results) and may come bare. `showHidden` matches `download`'s. `onProgress(totals)` is optional to call, and shows the totals counting up. Without `measure`, a folder shows how many entries it holds (`childCount`), and the component never walks folders with `list`, the same choice as for search everywhere.
- A folder shown itself, the open folder or one whose menu asked, comes as its entry in its parent's cached listing, or as a bare `{ id, name, kind }` when no listing holds it, a section's root named after the section, as `download` has them. Bare entries are kept by section, id and name (`bare` in the pane), so the same folder stays the same object.

## The cache

`store/properties-cache.ts` keeps what came, one per `FileManager` (`propertiesCache`), outliving the panel as it shows and hides. It imports nothing from the file manager.

- An entry's properties are kept by its entry object (a `WeakMap`), which a listing keeps for as long as the entry is as it was (`withUnchanged`), so an unchanged entry isn't asked again and a changed or renamed one is.
- A changed entry, one asked about before by its id and adapter, is asked about again once it has stayed the same for `SETTLE_AFTER` (1.5 s) rather than `ASK_AFTER`, so the open folder, whose entry its parent's listing makes anew as uploads into it finish once a second, is asked about once they've stopped. Meanwhile the latest properties that came for its id (`latest`, up to `MAX_STAND_INS`, 100, per adapter) stand in, as the progress of its loading, quietly: the backend's groups show as they were, with no spinner, and their fuller entry only fills in what the listing leaves out, so the listing's new size and date show at once. A file replaced under the same id shows its old properties until then.
- Counts are kept by their folders' ids and adapters (ids are unique within an adapter, so a folder listed anew with a new entry object, as for its item count, is the same folder), `showHidden`, and the host's count of its changes (`changes`, the file manager's `searchVersion`, which goes up with every change made through it and every refresh), so what a change made is counted again. Up to `MAX_KEPT_COUNTS` (30) are kept that nothing shows.
- Folders counted before are counted again for a change once `SETTLE_AFTER` has passed, each further change making them wait anew, so uploads finishing once a second (the upload queue's `REPORT_INTERVAL`) count a folder again once, after the last, rather than every second. Until the new count starts, the totals counted before show as they are, with no spinner; while it counts with nothing reported yet, they stand in as its progress, under the spinner. A count under way as a change comes carries on, standing in for the next one while that waits, and stops once it starts.
- Each is asked for once it has been wanted for `ASK_AFTER` (200 ms), so moving through a list with the arrow keys asks only about where it stops, and stopped if it stops being wanted first. A count no panel wants any more, nor stands in for one, is aborted and forgotten, checked once the commit is over (`prune`, in a microtask), so a count wanted again straight away, as under StrictMode, carries on.
- A selection's folders served by different adapters, as a search's results may be, are counted by each adapter, and the totals added up, as are the totals each reports on the way. Counting needs every one of their adapters to have `measure`.
- **Saves** (`saveProperty`, `save`, `dropSave`) are kept by adapter, then the entry's id and the field's (`saveKey`), not by the entry object, so they outlive the entry being listed anew and the panel moving on to something else or closing: a save the focus leaving a field started as the user clicked another entry finishes, and one that failed shows again, with what was typed and the message, as the panel comes back to that entry. Each is a `PropertySave` (`types/properties.ts`), "saving" or "error", with the value given. Saved, it goes, and what the adapter resolved with, or what showed with the field's value replaced (`withValue`), is set as the entry's properties and its stand-in (`latest`), so the field shows its new value at once and isn't asked about again; a request for the entry's properties that comes back after that is dropped, as it may be older. It's then told to the item's `onUpdated`. Nothing calls a save off once sent, as the change may have been made. `dropSave` forgets one that failed, as the user cancels it.
- `useProperties` (`hooks/use-properties.ts`) reads it for the panel, with `useSyncExternalStore`: `details` (one item, when its adapter has `properties`) and `totals` (when the items have folders and every adapter has `measure`), each a `Requested` (`loading` with optional `progress`, `ready`, `error`), and their retries, which forget what came, and what stands in for it, and ask again at once. The folders are told apart by their ids and adapters in a key, so a count under way carries on however often the items are made anew and the folders listed anew.

## The panel

`components/properties/properties-panel.tsx` takes `PropertiesItem`s (`types/properties.ts`: the entry, its adapter, its location written out, for an entry in a trash where it was moved there from and when (`trashed`), a folder's count from its own listing, its Rename, "Open item location" and "Open original location", when it has them, whether its fields can't be edited here (`readOnly`), and `onUpdated`, told once its properties are saved), and knows nothing of sections or the file manager, so the media manager can use it. It's an `aside` named by its title, focusable (`tabIndex={-1}`), ringed on `:focus-visible`.

- **One entry:** its picture, a large thumbnail across the panel's width (`useThumbnail` with the grid's view, at the smallest of `PICTURE_SIZES`, 18rem and 28rem, as wide as the panel's body, measured by a `ResizeObserver`, so 18rem docked at first or as the overlay and larger a step at a time as a resized panel widens, rather than asking again for every pixel; never taller than wide, `100cqi` of its own box, shrunk to fit, with the smaller grid thumbnail, or the smaller picture, standing in, drawn at the same size, while the larger loads) or else its type icon, its name, Rename… and "Open item location" when given, then rows: Type (with the MIME type, `propertiesTypeWithMime`), Size ("4.2 MB (4,213,045 bytes)", `formatBytes`, from 1 kB up) or Contents, Location, Modified, Created, Dimensions and Duration, then the backend's groups, each under its title, set apart by a rule.
- **Contents:** one folder's totals ("12 files and 3 folders, totalling 4.5 MB", "Empty"), with a spinner while counting, showing how many entries it holds meanwhile; or how many it holds without `measure`. Several entries: files alone add up at once from their own sizes; with folders, the selected files are added to the totals and the selected folders counted among the folders; without `measure`, "2 files and 1 folder" (`propertiesKinds`). A count that fails shows the adapter's message, or `propertiesCountFailed`, with Try again.
- **In a trash:** an item with `trashed` shows "Original location" in the Location's place, and for one, "Trashed" with when after it, and "Open original location" under the name (see "The section" in `trash.md`).
- **Several entries:** the copy icon, "3 items", Contents, and the Location when they share one, or "Several folders". No backend groups, which are one entry's.
- **None:** "Select an item to see its properties", as for a search everywhere with nothing selected.
- The backend's properties show a spinner while they come, and the adapter's message, or `propertiesFailed`, with Try again, as an `alert`, when they fail, in their place only: the listing's rows still show.
- Values the panel formats, and the backend's, are in `<bdi>`; texts built around them take them isolated, and the location is joined by `joinIsolated` with " / ", as a search's results show it (see `rtl.md`).
- Copying a value says so from the panel's own live region (`propertiesCopied`), so it isn't announced by the file manager, and so does saving one (`propertiesSaved`), while the panel is there.
- Its text is `PropertiesLocaleText` (`types/locale.ts`), kept apart as the upload, download and transfer panels' are; it reads none of the file manager's own keys (see `locale.md`).
- `takeFocus` focuses it as it's set, or as it mounts with it set.
- **`embedded`**: inside a host's own view of one entry, which shows its picture, its name and a way back itself, as the media manager's asset view does, it has no header (named `properties` by `aria-label`), picture or name, is as tall as what it holds, and leaves its first group's rule out; `onClose` is optional, its ✕ shown only with it.
- **`ownRows`** (true by default): false leaves out the panel's own rows (type, size or contents, location, dates, dimensions, length), so it shows only the backend's groups, as the media manager's asset view does, what an asset shows being the consumer's.
- **`definitions`**: the app's own definitions of what one entry shows, in groups, in place of the backend's (see "Defined properties").
- **Editable fields** show an Edit button after their value (see "Editing fields").
- **The header's actions** (`actions`, `ToolbarGroup`s already bound to what it shows) sit between the title and the ✕, through `ToolbarActions` (`components/buttons/toolbar-actions.tsx`, shared with the preview's header, see `preview.md`): two with icons as buttons at most, the rest, and those without an icon, in a "More actions" ⋮ menu (`propertiesMoreActions`, the panel's own key).

## Defined properties

The user's requirement (2026-10-31, "very important"): the built-in typed values are the default, and the app must be able to show any property its own way, such as renditions as jobs with how far each is along rather than tags. The user's model for it (2026-10-31) is MUI's data grid's columns: fixed types and a custom one, a function for what only needs casting or changing, and the app's own drawing for the rest. So the app defines in code what an entry shows, in groups of `PropertyDefinition`s (`types/property-definition.ts`, public), the panel's `definitions`, as columns read a row: each reads its value from the `values` the adapter's `properties` hands over by its `field`, or from the entry. The backend hands over data only, never how it's shown. The media manager takes a library's own (`MediaSection.properties`) in place of its own (`properties(asset, section)`), and the file manager takes none yet. Without them, the backend's `groups` show as before. The user declined (2026-10-31) the backend describing properties at runtime and a function adjusting them: each library defines its own, all of them.

- **Types** are what a value is, and only that: `string`, `number`, `boolean`, `date` (the user's correction: a language, a URL, a select or tags are no types). **Kinds** refine how a type is shown and entered: `url` on a string (a link, `safeHref` letting only the web's, mail's and phones' through, a field for a URL running left to right), `size` (bytes, `formatSize`) and `duration` (seconds, `formatDuration`) on a number, neither with an editor of its own, and `datetime` on a date (with its time, `formatDate`; a day alone is `formatDay`). A string also takes `multiline`, `maxLength`, `placeholder`, `lang` and `dir`; a number `min`, `max` and `step`.
- **`options`**, on any type but boolean, make it a choice: shown by the option's label, edited with a native select whose first choice is `propertiesNone`. **`multiple`**, on any type but boolean, makes it a list (a flag rather than a list type, so a list of numbers or URLs is shown and edited as its type is): chosen from `options`, as chips over a select of the rest (`propertiesAddOption`), or without them typed in, as chips over a field adding one with Enter, a comma between texts, or the focus leaving, a date as it's picked, Backspace with nothing typed removing the last.
- **No type** is a property entirely the app's (`CustomProperty`), whose `render` is required, as nothing else can draw it.
- **Functions**, methods so a definition of its own `V` fits a plain list: `valueGetter(value, entry)`, its value from the raw one or from the entry (cast, reached into, put together, such as a picture's size from `entry.media`), undefined where there's none; `valueFormatter(value, entry)`, its text, asked only while it has a value; `render(params)`, drawing it, as the app's own component returned as an element, so it holds hooks and state (`PropertyRenderParams`: the definition, `value`, `formattedValue`, the entry, its adapter, `labelId`, `errors` and `index`, `saving`, and `save(value)` while it can be saved); `renderEdit(params)`, its editor (`PropertyEditParams`: those, `id`, `onChange`, `disabled`, `error`); `errorKey({ index, entry })`, for a media manager's pick field only, its key in the app's `errors`, or its keys (see "The backend's errors" in `media-manager.md`). In the properties `errors` is always empty and `index` undefined. A media manager's forms draw fields from definitions too (`MediaFields`, see "Forms" in `media-manager.md`), where `disabled` turns one off for now; in an upload form they're handed an entry standing in for the files about to be uploaded and the files themselves (`PropertyParams.files`, undefined elsewhere), so `entry` stays required (see "Uploading" in `media-manager.md`). `valueParser` and kinds of the app's own were left out (no case yet; spreading a shared definition does what a kind of its own would).
- **Shown** (`utils/property-value.ts`): by `render`, else as its type has it (`components/properties/property-display.tsx`, `PropertyDisplay`, public, so a `render` adding a little can draw the default beside it): `valueFormatter`'s text, else a list's chips, a URL's link, or its text, written by its option's label, its kind or its type (`formatItem`: grouped numbers, Yes or No, `propertiesYes` and `propertiesNo`, a date read from a `Date`, milliseconds or an ISO string, a day alone being that day where the user is, `toDate`). `formattedValue` (`formatValue`), a list's listed the locale's way (`formatList`), is what Copy copies (`copyable`). A property with no value (nothing, an empty text or list, `isEmptyValue`) isn't shown, unless it can be edited, which shows "Not set"; a group with nothing shown isn't either. A row with no label is its value alone. `render` is keyed by the entry, so its state is that entry's.
- **Edited**, while it's `editable` (false by default for properties), the adapter has `updateProperties` and the item isn't `readOnly`: one with an editor (`renderEdit`, or the built-in one of its type, `hasEditor`) has the Edit button and is edited in `PropertyEditor`, as the backend's fields are (see "Editing fields"), through `renderEdit` or `PropertyInput` (`components/properties/property-input.tsx`, the built-in control by type, shared with the media manager's pick fields); a boolean with neither `render` nor `renderEdit` is a checkbox saving as it's toggled; one with `render` is handed `save`, for a control changing it in place, as a poster's frames to pick from, its failure under it as an `alert`, and keeps the focus where it is. Values are saved as their type has them: text trimmed, a number, a boolean, a date as an ISO string (a day as "2026-10-31", a time as the instant it is, `dateFromInput`), a list of those.
- **Saving** goes through the cache as an edit does (`saveProperty`, by the `field`, kept so a failure outlives the panel moving on): `{ [field]: value }`, `propertiesSaved` said once saved, the value shown being what the adapter resolved with, or else the value saved, set in the cached `values` (`withValue`), and `onUpdated` told. An adapter without `properties` shows what its definitions read from the entry, and a value saved shows once the entry is listed again.

## Editing fields

A field the backend marks `editable`, text (`multiline` and `maxLength` optional) or tags (`EditableField`, `types/properties.ts`), or a property the app defines as `editable` (see "Defined properties"), is changed in place in the panel, for one entry, when its adapter has `updateProperties` and the item isn't `readOnly`, as WordPress's attachment details and Drive's description are, rather than in a dialog. Only the backend says which fields can change, entry by entry; the file manager adds that the entry's folder can change and that no move holds it.

- **Shown**, its value, or "Not set" (`propertiesNotSet`) in `--_fm-text-secondary` while it has none, then an Edit button (`propertiesEdit`, "Edit Alt text", the `edit` icon). An editable tags field with no tags still shows, to add some.
- **Edited** (`components/properties/property-editor.tsx`, `PropertyEditor`, which takes a definition: a backend's field is made one, `definitionOf`, text a string, tags a string list), the row's value gives way to the definition's `renderEdit` or the built-in control of its type (`PropertyInput`), taking the focus at its first field, or else its first control: for text and tags, a field, small and outlined, named by the row's label (`aria-labelledby`, the label's id made from the panel's `useId` and the indexes, as the consumer's ids may hold spaces), `dir="auto"`, with no label of its own, as the row's label names it, then Cancel and Save (`propertiesCancel`, `propertiesSave`, Save contained with the kit `Button`'s `loading` while it saves). Text is one line, or a growing `textarea` of 2 to 8 rows for `multiline`. Tags are chips, each a button that removes it (`propertiesRemoveTag`, clicked, Enter, Delete or Backspace, or its ✕), over a field adding one (`propertiesAddTag`) as Enter or a comma is typed; Backspace in it with nothing typed removes the last. One field is edited at a time, the field taking the focus with the caret at its end (a number's or a date's field has none).
- **Saved** by Save, Enter (Ctrl+Enter or ⌘Enter over several lines; in the tags' field with nothing typed, a tag typed first being added, which the editor asks of the list's field as it saves, `PropertyInputHandle.flush`; never from a button, a link, a chip or a radio of the app's own editor, which Enter acts on), and by the focus leaving the field for anything else, as a details panel on the web does, unless the window lost it, which leaves it as it is; a value the same as the field's closes it without asking the adapter. The buttons and chips cancel `mousedown`, so a press on them keeps the focus in the field and isn't taken as leaving it, which matters in Safari, where a button pressed doesn't take the focus. The focus leaving doesn't try again a value that just failed as it is; Save does.
- **While it saves** the field is read-only and the buttons disabled, and Escape goes on to the panel. Saved, the value shows, its Edit button taking the focus back when the focus was in the field (`returnFocus`, to the button once it mounts, while the focus has gone nowhere else), "Alt text saved" is said, and the entry's folder is listed again (`onUpdated`, the pane's `relist`), as a backend may change what's listed of it, such as its date modified.
- **Failing**, it stays open with what was typed and the adapter's message, or `propertiesSaveFailed`, under it as an `alert`, and the field marked as an error. Save tries again; Cancel or Escape leaves the field as it was and forgets the failure.
- **Cancelled** with Cancel or Escape (which goes no further, so it doesn't leave the panel), the Edit button taking the focus back.
- **Moving on**: the field being edited closes as the panel shows another entry (`editing`, kept by entry id), its save, if leaving it started one, going on in the cache; a failed save shows again on coming back.
- **Where it's read-only.** The pane sets `readOnly` from the context menu's context for the entry (`readOnly`, its folder can't change, as in a `readOnly` section or the trash or a folder whose permissions refuse writing, or `moving`), and for a section's root from `sectionLocked`, so nothing is edited in the trash or a read-only section, nor while a move holds the entry. Several entries show no backend fields, so nothing is edited for them.
- **Keys**: Enter and Ctrl+Enter save and Escape cancels in the field, listed in the keyboard shortcuts window's General as "Save a property being edited" (`shortcutSaveProperty`) when any section's adapter has `updateProperties` (`canEditProperties`). The header's action shortcuts don't run in a field (`typesInField`).

## In the file manager

`components/file-manager/properties-pane.tsx` places the panel and feeds it:

- **Layout.** Under the header bar, `file-manager.tsx` has a row (`.body`): the content with the transfer, download and upload panels under it (`.column`), and the pane. From `rootExtraWide` (1100px, which leaves the content room for the list's size and date columns beside a docked sidebar) the pane docks on the content's end side, as wide as the user made it (see "Resizing"), `PROPERTIES_WIDTH` (300px) at first, as an inset `--_fm-surface` card like the content, shown while `propertiesOpen` (`data-shown`). The panel inside is clipped to its rounded corners by a box of its own (`.clip`), so the pane isn't, and its edge can reach out over the gap. Below it, it's an overlay over the whole file manager from the end side, `min(320px, 85%)` wide, sliding in by `translate` with `--closed-shift` (the sidebar's way, see `rtl.md`), over its own backdrop (`.propertiesBackdrop`, hidden from `rootExtraWide`), while `propertiesOverlay` (`data-open`). The row isn't positioned, so the overlay is placed by the root, as the sidebar's is.
- **Docked or not** is read from the pane's computed `position`, as the sidebar's is (`overlays`): by the file manager as keys and buttons ask (`propertiesDocked`), and by the pane itself with a `ResizeObserver` on the row, since the panel is only mounted while it shows (`visible`: docked and shown, or the overlay open), so nothing is asked of the adapter while it's hidden. The docked state outlives the root narrowing: widened again, it shows again. The overlay doesn't: docking closes it (`handlePropertiesDocking`, which the pane's `onDockedChange` tells from its `ResizeObserver`), so narrowing again doesn't bring it back, as it would have, unseen while docked. A panel that goes as the width changes, the overlay docking while the docked panel is hidden, or the docked panel collapsing, drops the pin and hands the focus it had to the content.
- **What it shows** (`propertiesSubject` in `file-manager.tsx`, a `PropertiesSubject`): what `ActionContext.properties` asked for (`pinned`), while its sections are the file manager's as they were (`subjectHolds`); or else a search everywhere's selection while its results show (`SearchResults`' `onSelectionChange`, an internal prop, since that selection isn't public); or the content's selection, as `FolderView` reports it (`handleSelectionChange`, which also tells the consumer, kept by the open folder's key); or with nothing selected, the open folder itself. The pane reads each entry from its folder's listing now (`listed`), subscribing to the store, so a change made meanwhile shows, and asks `contextFor` for Rename, "Open item location" and "Open original location", for one entry only, and never for a section's root, which is the consumer's. An entry right in a trash's root gets where it came from from `locateTrashed` (the frame's `locateIn`).
- **The header's actions** are `FileManager`'s optional `propertiesActions` (`ActionGroup[]`), bound by `toolbarGroups` to what `contextFor` gives for what the panel shows: its entries as they're listed now (`target` "selection", with `inResults` for a search's results), grouped by folder for a search's results from several, of one section or more (`groupByFolder`, `selectionRequest`), as the context menu's are, so only actions marked `acrossFolders` show for those, or the folder it shows (`target` "folder"). None show with nothing to show. An action's `shortcut` works while the focus is in the panel, except in a field typed in (`runToolbarShortcut` in the pane's `handleKeyDown`, after Escape), and is listed in the keyboard shortcuts window's Actions.
- **The pin** is dropped as the location changes (in `shownPlace`'s render), as the content's selection changes ids in the open folder (not as its entries are listed again), as a search's results show or go or their selection changes, and as the panel hides or the overlay closes, by the user or as the width changes.

### Resizing

The docked panel is resized by its edge, as the docked sidebar is (see "Resizing the docked panels" in `file-manager.md`, which holds the edge, its keys and what the panels give way to). The overlay isn't: it's a passing panel over the content, as the overlay sidebar is.

- **The width** is `propertiesWidth` / `defaultPropertiesWidth` / `onPropertiesWidthChange` (see `props.md`), through `useSetting`, from `PROPERTIES_MIN_WIDTH` (240px) to `PROPERTIES_MAX_WIDTH` (480px), 300px when omitted. The pane sets it as `--properties-width` in its `style`, and its docked `width` reads it.
- **Beside the content.** The docked pane shrinks (`flexShrink: 1`, down to its `min-width`, 240px) while its row is too narrow for it and the content's room (`.column`), so a width asked for that doesn't fit shows narrower, and wider again as the room comes back. It gives way before the sidebar does. `widestOf` reads how wide it can go from the same CSS: the row's width less the pane's margins and the `min-width` of what's beside it. The sidebar is outside the row, so whatever width it has is out of it already, and dragging the pane never squeezes the sidebar.
- **Its edge** is on its start side, over the gap between the content and the pane (`placement="start"`), in the Tab order between the content and the panel. Left and Right on it swap right to left, so it moves the way the arrow points: toward the start widens the pane.
- **For screen readers** it's named `resizeProperties` ("Resize properties").

### Opening and closing

- **Alt+Enter** (anywhere in the file manager, the root's handler, `toggleProperties`), as Windows, GNOME and Dolphin open properties; Enter names the same key on every layout, and on a Mac it's ⌥Return. Docked, it shows and hides the panel and leaves the focus where it is, so the arrow keys keep moving through the content as the panel follows, announcing `propertiesShown` or `propertiesHidden` unless the focus was in the panel, which hands it to the content as it hides. Collapsed, it opens the overlay, which takes the focus, and closes it, giving the focus back. The content, its search results and the tree leave Alt with Enter to it (the tree's error row included), and a consumer's action bound to Alt+Enter runs instead in the content and the tree, as any shortcut does.
- **`ActionContext.properties()`** (always there, for any target: entries, or with none, the folder itself, in the content, the tree, a search's results or `apiRef.actionContext`) pins what the context names, shows the panel, docked (asking for `propertiesOpen`) or as the overlay, and moves the focus into it (`focusProperties`, one render, as `focusContent`). Its focus effect runs after the context menu has given the focus back to where it opened, so the menu doesn't take it back (checked in the browser on 2026-11-11, with the menu on Base UI). The overlay keeps the menu's opener (`menuOpener`) to give the focus back to.
- **The view menu** offers "Show properties" with Alt+Enter beside it, read as it opens (`propertiesDocked`): docked, a checkbox showing and hiding the panel, the menu staying open; collapsed, an item that closes the menu and opens the overlay, which gives the focus back to the menu's button.
- **The panel's ✕** hides the docked panel (the focus going to the content) or closes the overlay. **Escape** in it goes back to the content from the docked panel, and closes the overlay. Escape in a menu or dialog that portals out is theirs.
- **The overlay** closes as the focus moves on to the rest of the file manager (Tab, F6, a click behind its backdrop), leaving the focus where it went, while a menu or a dialog, outside the file manager, keeps it open; closed otherwise, it gives the focus back to what had it as it opened, or to the content when that's gone.
- **F6** goes sidebar, content, docked panel, and back to the sidebar (see `keyboard.md`).
- **Props:** `propertiesOpen` / `defaultPropertiesOpen` / `onPropertiesOpenChange` for the docked panel, and `propertiesWidth` / `defaultPropertiesWidth` / `onPropertiesWidthChange` for its width (see `props.md`). The overlay's open state is a passing one, closed by most things done elsewhere, as the sidebar's is. There's no `apiRef` method: `actionContext(entries?, location?).properties()` does it from a toolbar.

## The playground

The mock adapter's `properties` makes the rest up from each entry's name: a created date before its modified date, a picture's dimensions (logos 512 × 512), a video's dimensions and length, a sound's length (none for an uploaded file, which isn't read), then an owner by root ("you", "deploy-bot", "Design team"), permissions ("Read only" for what the mock locks, API service's `migrations` and everything in it, see "Permissions" in `file-manager.md`), the path and, for a file, a SHA-256, both copyable, a link to share on `files.example.com` with a view count, and some tags. `restricted` and `docs/contract.pdf` fail, to show the error. Its `measure` walks the tree `COUNT_STEP` (250) entries a step, 40 ms each, reporting the totals so far, so `archive` (10,000 files) and API service's root count up; folders it can't read are counted but not looked in, dotfiles are left out while hidden files aren't shown, and `restricted` itself fails. The demo "Properties" action calls `context.properties()`, the footer's "Properties" calls `apiRef.actionContext(...)?.properties()` for the selection or the open folder, and `propertiesOpen` and `propertiesWidth` are kept in local storage with the view settings. `createPropertiesActions` (`mock-data.tsx`) puts Download and Share in the panel's header as buttons, and "Copy link" in its menu, for one entry. A picture (`isPicture`, by its type or extension, uploaded ones too) has a "Description" group of "Alt text" (`maxLength` 250) and "Caption" (`multiline`), and every entry an editable "Tags" field, its made-up tags until some are saved, all editable unless it's read-only (`migrations`, `go.sum`) or in the trash. `updateProperties` keeps what's saved on the node (`MockNode.properties`), so it goes with a move, a rename and a copy, refuses read-only and trashed entries, and fails any value with "fail" in it, to see a save fail; it resolves with nothing.

## Not yet

Definitions in the file manager (`FileManager` passes none yet), several entries' fields at once, and checking a value as it's typed (as `checkName` does names) rather than on saving. Saving a property isn't in the undo history, nor does it end it, as it changes no entry the history holds.

Tabs for activity, versions and sharing are left out by choice: they're backend features (edit history, stored versions, permissions) the component can't supply, and an app adds its own through `propertiesActions`.
