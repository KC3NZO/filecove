# Copies and moves in the background

Every copy and move, from "Copy to…" and "Move to…", a paste or a drop, runs in the background while the user browses, never in a modal, as uploads and downloads do. The dialogs only ask what needs an answer (a destination, names the destination has), then hand it to a queue and close. One that takes a moment shows in a panel under the content, and one that's done leaves it. Entries go between sections of one adapter, which copies or moves them itself, and between sections of different adapters, which the file manager copies across itself (see "Between adapters").

## What the adapter does

The same `copy(entries, targetId, options)` and `move(...)` as ever, for a folder the same adapter serves: one call per transfer, with `TransferOptions` (`signal`, `conflict`, `onProgress(loaded, total)`, in bytes, and `onEntryDone(entry, made?)`). Calling `onProgress` is optional, as `upload`'s is: without it the row's bar sweeps, as for a move that only renames on the backend. A total of 0 or less is ignored. Several may run at once, which the adapter's comments say. Each may resolve with a `TransferResult`, the entries as they now are in the target, which is what lets the user undo it (see `undo.md`).

- **`onEntryDone(entry, made?)`**, optional to call too, reports an entry given that has gone into the target, all of it, as soon as it has, with what it became there when the backend can say, the skipped left out. It's how a transfer that then fails, or is cancelled, says which of its entries went, though it's one call: the queue keeps them (`TransferItem.went`), the panel says how many, Try again leaves them out, the moves among them leave the source as moved entries do, and what went goes in the undo history when each came with `made` (see "Failing partway" in `undo.md`). Without it, a copy that failed is tried again for every entry, and a move for those still in their folder. A transfer resolving with nothing, every entry reported with `made`, counts as having said what it made.

## Between adapters

Ids only mean something to the adapter they came from, and two backends don't know each other, so entries going into a folder another adapter serves are copied there by the file manager itself, as a desktop copies between disks: it reads through one adapter and writes through the other, with no member of the contract for it.

- **What it takes** (`carries`, `utils/transfer.ts`): of the adapter serving the entries, `content`, every file being read through it (`purpose` "copy", see "What the adapter hands over" in `download.md`), and for a move `delete`; of the target's, `upload`, and `createFolder` when there are folders among them. Folders are listed with `list`, all the way down. A move also needs the entries' own `delete` permission, besides `move`, as it deletes them from their backend. `canCarry` says whether an adapter's entries can be dragged at all: `move`, `copy` or `content`.
- **Where it runs**: the transfer queue, as any copy or move. A `TransferItem` has its `targetAdapter` beside its `adapter`, the entries'; when they differ, the queue's `call` runs `transferAcross` (`store/transfer-across.ts`) rather than the adapter's `copy` or `move`, with the same `TransferOptions`, so it's shown, cancelled, failed and tried again as any is, and reports its own entries and bytes.
- **`transferAcross`** first lists every folder below the entries through the entries' adapter, every page, four at a time (`gather`, `LISTED_AT_ONCE`), so it knows the bytes to go and a folder that can't be listed stops it before anything is sent, then the target folder, every page (`listAll`, shared with the upload queue). Then it goes through the entries in order, one file at a time: each file read through `content` (a URL fetched by the page, so it needs CORS, a server's error worded by `serverError`), turned into a `File` with the entry's name, type and date, and handed to the target's `upload`; each folder made with `createFolder`, then its folders and files, as a folder upload goes. The progress is the bytes read and sent of all the files, half each.
- **Names** are settled as `ConflictPolicy` says, as an adapter's own `copy` would: a file replaces a file there that can be written, with "replace", and goes with "keepBoth" otherwise, as `upload` keeps both; a folder merges into a folder of its name that can change, its own listing asked, all the way down, with "replace" there, and is made under a free name otherwise (`freeName`, worded by `keptBothName`, clear of the names there and going in beside it), as `createFolder` can't keep both; "skip" leaves an entry whose name the folder has out. A folder just made has nothing to clash with. The target's `checkName` is asked before each name is sent, and a name it refuses fails the step with its message.
- **Each entry, once all of it is there**, is deleted from its own backend for a move (`delete`, one entry a call) and reported (`onEntryDone`), with the folder made, the folder merged into, or the file `upload` resolved with. It resolves with them all (`TransferResult`), unless `upload` said nothing of a file, so a copy or move between adapters is undone as any is. Something failing stops it there, with the entries before it gone and reported, and the one it stopped at in part where it was going; a move leaves that one where it was.
- **The text** it needs, `keptBothName` and `serverError`, comes with the queue (`createTransferQueue(onEnded, text)`, `AcrossText`), as the upload queue is handed `keptBothName`; `FileManager` passes its locale's.
- **The sections it goes between** are any whose `importFrom` takes the entries' section, as within an adapter. `acceptUploads` is about files from outside the file manager, so it doesn't apply, but the target's `upload` has the final say, and can refuse what it won't take (see "Sections limiting uploads" in `uploads.md`).
- **The picker** offers every section the entries can go into (`destinationsFor` in `contextFor`, by `carries`, `importsFrom` and, for a move across, the entries' `delete` permission), whichever adapter serves it, listing each through its own, its New folder made through it, its folders being moved disabled by its own adapter's moving ids, and the entries' own folders disabled only in their own adapter's sections (`pickedIds`). Entries of another adapter are never "already there" (`incoming`, the picker's, the paste dialog's and `startTransfer`'s `there`).
- **The clipboard and drags** hold each folder's entries with the adapter serving them (`ClipboardPart.adapter`), so a search's results from sections of different adapters are cut, copied, dragged and pasted together, each part its own transfer, through its own adapter or across. Cut and dragged entries are marked by adapter (`AdapterIds`, `CutContext`, `DragContext.dragged`).
- **Dropping** into a folder another adapter serves copies, as dropping onto another disk does on a desktop, unless Shift or ⌘ is held, which moves (`DropKeys`); Ctrl or Option copies anywhere, as before (see "Drag and drop" in `file-manager.md`).

## Handing off

- **The picker** (`dialogs/transfer-dialog.tsx`): "Copy here" / "Move here", or a choice in its clash step, calls `onStart(request, destination, conflict, skipped, mergedIds)` and the file manager closes it. A folder that can't change isn't chosen (see "Permissions" in `file-manager.md`). There's no spinner and no error in it any more. Its `onChanged` is only for the New folder button's name dialog.
- **Pasting and dropping** (`dialogs/paste-dialog.tsx`): it lists the target if it isn't cached, looks for clashes, and only shows to ask about them, then calls `onStart(request, conflict, skipped, mergedIds)`. Cancel just closes. A drop is a paste of the dragged entries (see "Drag and drop" in `file-manager.md`).
- `skipped` are the entries the user chose to skip, those whose names clash (`EntryClash`), for the announcement, and `mergedIds` the folders a Replace or Merge merges others into (`mergedFolders`, `utils/transfer.ts`, with `findClashes`), read from the listing as the choice is made, to list them again all the way down once it ends.
- One paste is checked at a time (`offerPaste`'s `!pasting?.open`), as one upload is, but a paste or drop no longer waits for the copies and moves under way.

## The queue

`store/transfer-queue.ts`, with `hooks/use-transfer-queue.ts` holding one for the life of `FileManager` (unmounting cancels what's under way, telling nothing), handed `onEnded` and the text a copy between adapters needs (`AcrossText`), both through refs. It's shaped like the download queue, and like it imports nothing from `components/file-manager/`, so the media manager can use it too.

- An item (`TransferItem`, `types/transfer.ts`, internal) is `queued`, `running` or `failed`, with its `kind`, `adapter` (the entries'), `targetAdapter` (the target's, the same one or another), `entries`, `source` and `target` folders (`FolderRef`s), `conflict`, and `went`, the entries reported gone so far (`WentEntry`: the entry and what it became, `onEntryDone`), each of its own once, kept by a failed one. One that's done, or cancelled, leaves the queue, so there are no "done" or "cancelled" states.
- At most `MAX_ACTIVE` (3) run at once, as uploads' calls do, or as many as `setMaxActive` says (`limits.transfers`, see "Limits" in `props.md`); the rest wait in the order asked for. `add` returns the id, for the host's own record.
- One added with `after`, another's id (`TransferItem.after`), waits until that one has ended, done, failed or cancelled (`waits` in `pump`). `startTransfer` chains a batch's transfers that way when entries of its folders share names (`sharesNames`), so each lands before the next is settled against it by its `conflict` (see "Acting on several folders" in `file-manager.md`).
- `progress` keeps the last `loaded` and `total` reported, within the total, told at most every `PROGRESS_INTERVAL` (100 ms).
- `shown` is set once it has taken `SHOW_AFTER` (500 ms), waiting included, or at once when it fails, so a quick one is never shown.
- `onEnded(item, outcome, items, made)` (`TransferEnded`) is told as each ends: "done", "failed", or "cancelled", with the item's status saying whether it had reached the adapter ("running") or was still waiting ("queued"), and its `went`, the items as they are now, and for one done, `made`, the `TransferResult`'s entries when the adapter gave them, or else what it reported of each entry, when every one came with `made` (`madeBy`). `cancel`, `cancelAll`, `forget` (a failed one, as it's tried again), `clear` (every failed one) and `abortAll` are the rest.

## The panel

`components/transfers/transfer-panel.tsx` shows the shown items, and knows nothing of where it's shown. `FileManager` places it as an inset panel under the content, above the download and upload panels (`styles.taskPanel`), only while it has items. Its look is theirs, from `styles/panel.module.css`.

- The summary has a status icon (a ring while any wait or run, filling with the bytes done of their totals once every one of them has reported, spinning until then, an error otherwise), a title counting entries, not transfers ("Copying 3 items", "Moving 1 item", "Copying 3 items and moving 2 items", "Couldn't copy 3 items"; `transfersActive` and `transfersFailed` take both counts, as one sentence), the entries a failed one reported gone left out of what couldn't be, announced politely, and under it the bytes done of the total and how many failed (`transfersFailedCount`).
- The chevron folds the list away. The ✕ cancels everything waiting or under way; once nothing is, it forgets the failed ones and the panel goes.
- Each row has the entry's type icon (or the copy or move icon for several), its name or "3 items", a bar while it runs (filling with the bytes once the adapter reports them, else with the entries gone once it reports any, sweeping until then, from the start side, `panel.bar`), and its status: "Waiting to copy to “Photos”", "Copying to “Photos”" with "1.5 MB of 4 MB" once it reports, or "2 of 5 items" (`transferItemsDone`) when it reports entries but no bytes, or the adapter's error (`transferCopyFailed` without one), with "2 of 5 items copied" (`transferCopiedSome`, `transferMovedSome`) when some went first. A failed row names what's left of it (`leftOf`), which Try again goes for. Waiting and running rows can be cancelled, and failed ones tried again, when the host's `canRetry` takes them.
- Its text is `TransferLocaleText` (`types/locale.ts`), kept apart as the other panels' is (see `locale.md`).

## In the file manager

`FileManager` keeps what each transfer is of (`transferPlaces`, a `TransferPlace` per id, set by `startTransfer`): the request as a `PasteRequest` (the entries as a clipboard, cut for a move, and where they go), the names skipped, the folders merged into, and whether it can be tried again.

- **Starting.** `startTransfer` adds it to the queue, for the user's change or an undo or redo (`TransferStart`: the `batch` an undo moving entries back to several folders starts each with, and the `names` they take back), one transfer per folder the entries are in, as the adapter takes entries sharing a folder (a search's results from several, of one section or more, see "Acting on several folders" in `file-manager.md`), each through its own part's adapter into the target section's (`intoAdapter`), with a `TransferPlace` of its own folder's entries, so it's shown, fails and is tried again by itself, one after another when their names are shared (`after`). Entries already in the destination, of its own adapter (`there`), are left out of a move and kept both by a copy. A cut leaves the clipboard as its paste starts (when the clipboard is still the one pasted), so it isn't pasted twice while it runs; a copy can be pasted again.
- **Ending** (`handleTransferEnded`). Whatever reached the adapter, done, failed or cancelled, has what it may have changed listed again (`relistTransferred`: the target through its adapter, the source after a move through the entries', and after a "replace", the folders merged into, all the way down). A move's entries that went, all of them once it's done, or those reported before it failed or was called off (`went`), go through `handleMoved` (moved folders out of the cache, the open place following a moved folder it's in, moved entries out of the clipboard and the preview). Once the last of those it was started with has ended (`TransferBatch`, `settleBatch`), it's announced (`copyDone`, `moveDone`, leaving the skipped out), counting the entries that went, or, when one stopped partway, how many of all those asked for went ("Copied 3 of 5 items to “Photos”", `copyPartlyDone`, `movePartlyDone`), and goes in the undo history, or ends it, or ends the undo or redo it carried out (see `undo.md`). A failure is announced (`copyFailedNotice`, `moveFailedNotice`) only when no other transfer was shown, since a panel just shown isn't read out, while its live title is once it shows, and nothing of it went, which the batch's announcement says.
- **Trying again** (`retryTransfer`) is a paste of what's still to go, through `offerPaste`, so the destination's names are checked again, as part of it may have gone through, and the user chooses afresh: the entries the adapter reported gone left out (`went`), and of the rest, only those their folder's listing still has, when it's listed, so a move doesn't ask again for what it moved; with none left, it's forgotten. An entry it stopped at partway clashes with what of it went, so Merge finishes it. It's offered (`canRetryTransfer`) while its sections are there, each served by the adapter it was, and no trail has been cut short: `revise` rewrites both trails with the history's, as it does uploads' places, and a folder gone from either marks it not `retriable`.
- **The progress bar** over the content (`busy`) shows while a copy or move waits or runs that changes the open folder, in whichever section, by the adapter serving it: its target (`targetAdapter`), the folder listing the target (dropped onto, or pasted into from its menu), or for a move its source (`adapter`); and while a paste is checked (`pasteIds`, by adapter too).
- Clearing the panel forgets the places of what it cleared (`clearTransfers`).

## While a move runs

Entries a move is moving, waiting its turn or under way, are marked and left alone until it ends, done, failed or cancelled, since their ids may soon name nothing, and acting on them meanwhile would race the move. A copy's entries are only read, and aren't held. Entries going to the trash or coming back from it are held the same way, through the same `moving`, each marked with what holds it (see "Moving to the trash" in `trash.md`).

- **What's moving** is `moving` in `file-manager.tsx`, a `MovingIds` (`types/transfer.ts`: the ids by the adapter serving them, each with its `MovingKind`, "move" for the queue's, "trash" or "restore" for the trash's work, in `MovingKinds`), made by `movingIds` (`utils/transfer.ts`) from the queue's moves that haven't failed (`isMoving`), and the entries `held` beside them (the trash's work, `trashWork`), and made afresh only as moves start and end (`movesKey`, the moves' ids) or that work does, not with every bit of progress. So the queue is made early in the frame (`useTransferQueue`, handed `handleTransferEnded` through a ref once that's made), before the paste, drag and context code that reads it. `movingThrough(moving, adapter)` gives one adapter's ids.
- **Everything in a folder being moved goes with it**: `folderMoving` (`utils/permissions.ts`) is the folder or one in its trail, its section's root included, being moved, and `entriesMoving` that, or any of the entries. They go by the trail, so a section rooted further below a folder being moved, which nothing ties to it, isn't known to be; the adapter has the final say there.
- **What's refused** (see "Permissions" in `file-manager.md`): a folder being moved can't change (`folderWritable`, given the ids), so nothing is created, uploaded, pasted or dropped into it, and none of its entries is renamed, moved out or deleted (`entriesAllow`); entries being moved can't be renamed, moved, cut or deleted, nor copied or copied to (`contextFor`), since a copy's ids would name nothing once they've moved, and aren't dragged (`useEntryDrag`'s `held`, `heldUp`); a clipboard holding entries being moved isn't pasted (`canPaste`, given `moving`), however they were cut or copied before; and a failed transfer isn't tried again while its entries or its destination are (`canRetryTransfer`). Opening, previewing, downloading and the properties are only reading, and stay. `ActionContext.moving` says so for an app's own actions, and `readOnly` is true for a folder being moved.
- **The picker** disables folders being moved, as it does the entries it was opened for, read "Being moved" (`entryMoving`), and a place it reaches inside one, such as a section rooted in one, can't be chosen: "This folder is being moved" (`pickerMoving`) in place of `pickerReadOnly`. A folder the trash's work holds says so instead, "Being moved to the trash" and "This folder is being moved to the trash" (`heldText`, `pickerHeldText`, by `heldBy`).
- **The mark**: `MovingContext` (`contexts/moving-context.ts`) carries `moving` to every view, and `useMovingIds` (`hooks/use-moving-ids.ts`) gives a section its adapter's ids, as `useCutIds` does for cut ones. List rows, grid tiles and tree rows set `data-moving` for `movingMarker` (see `component-styling.md`): the folder view marks the entries being moved, or every entry while the open folder is being moved itself (`movedHere`), a search's results by their trails (`movingKeys`), and the tree a folder row by its trail and a section row whose root is being moved, each with what holds it, the entry's own or the nearest folder's it's in (`heldBy`, `utils/permissions.ts`). Screen readers hear "Being moved" (`entryMoving`) after the name, or for the trash's work "Being moved to the trash" or "Being restored" (`heldText`), in place of the lock's "Read-only" (`drawnState`).
- The playground's moves within a root only rename, at once, so to see it, move a large folder between roots, such as `archive` from API service into Website, or several, as three run at once and the rest wait marked.

## The playground

The mock adapter's `copy` goes at 8 MB/s (`COPY_SPEED`), from 0.25 to 10 s in all (`COPY_TIME`), an entry at a time, each put where it goes once its bytes have come and reported (`carry`, `onEntryDone`), with the progress, so a large folder such as `archive` or `datasets` shows the panel and a small file doesn't. Something below an entry that can't be read (`contract.pdf`, in Website's `docs`) stops it halfway through that entry with "Couldn't read …", the entries before it copied and reported, as a backend failing partway would: copy Website's `docs` with another folder before it, say `.github` with hidden files shown, to see "1 of 2 items copied" and Try again for `docs` alone. A `move` within a root only renames, at once; between roots (Website into API service, say) it goes as a copy does. Copying or moving `restricted` itself, or anything into it, fails at once.

Between adapters, the server's sections and the Media bucket: Website's `public/images` copied or dropped into the Media bucket goes through the bucket's `upload`, its files read through the server's `content` (`purpose` "copy", a simulated fetch at `DOWNLOAD_SPEED`), and Shift held as it's dropped moves it, deleting it from Website. The bucket's adapter refuses anything but pictures, video and sound in `upload` (`refuses` in `createMockAdapter`, `MEDIA_TYPES` and `MEDIA_EXTENSIONS` in `mock-data.tsx`), so copying Website's `docs` there fails at its first file, to see a copy between adapters fail. The bucket's videos copied into API service, whose `importFrom` takes them, go the other way.
