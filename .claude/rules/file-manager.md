# File manager internals

`src/components/file-manager/file-manager.tsx` is the frame (sidebar, header bar, inset content panel). It owns navigation, tree expansion, the sort order, touch selection mode and the context menu state. Selection has its own rule, `selection.md`, and the public props that control or drive these (the location, the view settings, the selection, `apiRef`, the root element, props changing after mounting) have `props.md`.

## Data

`store/folder-store.ts` caches listings per `folderKey(sectionId, folderId)`. The cache is shared by the sidebar tree, the content view and the dialogs, with request de-duplication and abort-on-unmount. `file-manager.tsx` provides the store through `DataContext` (`contexts/data-context.ts`), with `relistAfter`, and components read it with `useFolder` (`hooks/use-folder.ts`), which uses `useSyncExternalStore` with per-folder snapshots.

- `load(..., force)` lists a folder unless it's listed or loading, and with `force` again even while a request is in flight, replacing it, since that request's result could predate a change just made.
- `relist(sectionId, adapter, folderIds)` lists again the section's cached listings of those folders, and every cached listing holding one of them, for its item count. It looks through all of the section's listings, found by the section's part of their key, so none is missed and no folder id is parsed.
- `cachedTree(sectionId, folderId)` gives the ids of a folder and of every folder below it whose listing the section has cached, found by walking the cached listings, so the folders below one are known without parsing ids.
- `forget(sectionId, folderIds)` drops the listings of those folders and of everything cached below them (`cachedTree`). What still shows one lists it afresh: `useFolder` once its listing is gone (`dropped`), the tree for a folder it shows with none (see `virtualization.md`), so a section's root dropped while the content shows it is listed again with nothing else asking.
- `relist` without folder ids lists again every listing the section has cached, for `FileManagerApi.refresh()`. `forgetSection(sectionId)` drops all of a section's listings, for a section another adapter now serves; `useFolder` and the tree list what they show again, since they follow the adapter (see "Props changing after mounting" in `props.md`).
- In the sidebar, a folder's listing, once there is one, overrides the adapter's `hasSubfolders` hint for its chevron.
- A listing that comes back with entries as they were keeps those entry objects, and the whole listing keeps its array when nothing changed (`withUnchanged`, comparing each field, dates by time and `meta`, `media` and `permissions` one level down), so rows don't render again and a selection isn't told again for a listing refreshed unchanged.
- A listing's own `permissions` (`ListResult.permissions`, the folder's, from its first page) are kept with it (`FolderState.permissions`), through a refresh, quiet or not, and kept as the same object while they're the same (see "Permissions").

### Listing again as a folder opens

A folder opened again shows its saved listing at once and is listed again in the background, so what changed elsewhere (another user, another tab) shows without a refresh, as GNOME Files shows a folder's changes. `relistAfter` (`FileManager`, default 0) is how old, in ms, the listing may be before that; `Infinity` never re-lists, for a backend where listing costs, and leaves such changes to `apiRef.refresh`.

- "Opened" is the content opening a folder (`FolderView`), the tree coming to show a folder's folders (expanding it, or one above it), and the transfer picker opening one: `useFolder(..., open)` and the tree call `store.open(key, adapter, folderId, maxAge)`. The paste, upload and name dialogs only read a listing for its names, with `load`, and don't re-list, since a clash the cache misses is kept as both anyway.
- `open` lists a folder not listed or whose listing failed as `load` does, and otherwise lists it again `quiet`ly once its listing was asked for `maxAge` ago or more (`checkedAt`, the time it was asked for), or has no time, being maybe out of date (`stale`).
- Quietly, the listing stays `ready` with `checking` set (`FolderState`), so nothing shows a progress bar or a spinner, and whatever waits for all of a folder (the dialogs' clash checks, "Folder is empty", Create's suggested name) goes by the listing saved. What gives up on an entry the listing lacks waits for the check: the content's selection drops ids it doesn't list (`retain`), a reveal is given up on (`revealLost`), and a selection set from outside is revealed (`revealSelected`), each once `checking` is gone, so `reveal()` of a file made elsewhere finds it.
- A check that fails shows the error, as any listing again does, since the folder may be gone.
- React's development double mount aborts it (`abortAll`), which keeps the listing as maybe out of date, so the remount checks it again.

### Keeping listings

Listings are kept while the file manager is mounted, but not without end: those nothing shows are dropped beyond `MAX_KEPT` (20,000) entries, or `limits.keptEntries` (`setMaxKept`; see "Limits" in `props.md`), each listing counting as one more than its entries, those shown longest ago first (`recent`), checked as each listing comes (`evict`).

- What shows a listing says so: `useFolder` while enabled, so the content, the picker and the dialogs, and the tree for every folder whose folders it shows (`store.show(key)`, which returns the function that hides it). A listing shown, or with a request in flight, is never dropped.
- A listing only goes once no listing kept is found right below it, through the folders it lists, so `cachedTree` still reaches every listing cached below a folder that changes, and `dropFolders` drops them all.
- A dropped listing is listed afresh when its folder opens again, as one never listed is.

### Paging

An adapter may list a large folder in pages: `list` resolves with a `nextCursor`, and the store calls it again with that as `cursor`, page after page, until one comes without it. Every page is fetched, so a listing in the cache is always the whole folder, and sorting, clash checks, Select all and type-ahead stay right. Paging lets a backend cap its responses and shows the first entries sooner; it doesn't load less.

- Listed for the first time, a folder shows what has come so far as `{ status: "loading", partial: true }` (`FolderState`), never with no entries, at most every `PAGE_INTERVAL` (500 ms) after the first page, since every showing sorts it again in the content and the tree. Listed again, it keeps its listing until the new one is complete, as it always has.
- Whatever needs the whole folder waits until `partial` is gone: the paste and upload dialogs before looking for clashes, and the transfer picker's "Copy here" / "Move here" button. "Folder is empty" and the tree's "No folders" only show once the folder is `ready`, and a tree row keeps its spinner while pages come.
- An entry a later page repeats, as offset paging can while the folder changes, is listed once. A page handing back the cursor it was given is an error, rather than a request loop.
- `abortAll` keeps a complete listing being refreshed, but drops a partial one, so it's listed again. React's development double mount runs it.
- The playground's mock adapter lists 2,500 entries a page, with the next offset as the cursor, so `archive` comes in four.

### Changes show in every section sharing the adapter

Sections served by the same adapter object can show the same folders, under the same ids (ids are unique within an adapter), so whatever a dialog changes is handled in all of them, through two helpers in `file-manager.tsx`:

- `relist(adapter, folderIds)` is every dialog's `onChanged`, called done, failed or cancelled with the folders the adapter may have changed: the one created or renamed in, the one deleted from. The upload queue calls it too, for the folders uploads ended in, at most once a second (see `uploads.md`). It runs the store's `relist` in each section. A copy or move ending, done, failed or cancelled, calls `relistTransferred` with its destination and, for a move, its source (see `transfers.md`), which also takes the folders a Replace or Merge merged others into (`mergedFolders` in `utils/transfer.ts`: the destination's folders with a folder's name among the entries, read as the choice is made), and lists again every listing cached at or below them, in each section listing them, since what's in them may have changed at any depth while their ids still name them. A section that lists none of them may be rooted below one, so what it shows is listed again at once (`store.recheck`).
- `dropFolders(adapter, folderIds, goneIds)` is for folders whose ids may now name other folders, as path ids do: deleted and moved folders, a renamed folder's old and new id, and a new folder's id. Their cached listings, and those of every folder any section has cached below them, are dropped in each section (`forget`), and what still shows one lists it afresh. A section rooted in one of them can't follow it, since its root is the consumer's: its places, in the history too, go back to its root, to show what the adapter has there now.
- Of those, the `goneIds`, the folders no longer where they were (all but a new folder and a renamed folder's new id), can take with them a section rooted further below, which no cached listing ties to them, since ids are never parsed. A section none of whose listings lists one of them (`store.lists`) may be rooted below it, so the listings it shows are listed again at once (`store.recheck`: quietly those ready, afresh those still loading, failed ones left), and so fail if its root went. Every other listing of every section the adapter serves is marked maybe out of date (`store.stale`), and listed again as it opens, whatever `relistAfter` says, since the change may have touched it in ways the cache can't tell.
- Places in the history, the sidebar's expanded folders, selecting a new entry and a copy's or move's progress bar go by folder id in every such section too.
- The playground's Website source bookmark is rooted in Website's `src`, to try these out.

## Navigation

`hooks/use-location-history.ts` holds the current place, a `FileManagerLocation` (a section plus a trail of `FolderRef`s), and the back/forward history, and lets the consumer control it (see `props.md`). `utils/navigation.ts` has `folderOf`, which returns the folder a place points at, and `samePlace` and `equalPlace`, which compare places by id, and by name too.

- Breadcrumbs come from the trail, not from parsing ids. The path bar starts with the section label, followed by the folders below its root. Its empty space edits the path (see "Going to a path").
- Navigating never expands or collapses the sidebar tree; only its chevrons, Right and Left on a row, and a drag resting on a row do (see "Drag and drop"), and the path bar shows where you are. Only the first section shown starts expanded, unless the consumer says otherwise: the expanded folders can be controlled too (`expandedFolders`; see `props.md`).
- Going up to a folder the open one is in, by any route, the consumer's included, selects the folder left through, worked out during rendering as the place changes (`shownPlace`), and opening a folder from the content takes the focus into it (`leaveFor`; see `keyboard.md`). The header's back and forward go through `goBack` and `goForward` for this, which read where they lead from `useLocationHistory`'s `previous` and `next`.
- **The history lists.** Right-clicking, the menu key on, or a long-press on (touch and pen, `useLongPress` with `onButtons`) the header's back or forward button opens a menu (`header-bar/history-menu.tsx`) of the places it leads to, nearest first, as GNOME Files shows them, hanging from the button's start edge. Each item has an icon (a folder's, or the section's at its root), the folder's name, or its section's label at the root, and under it the section and the folders above it joined by " / " (`joinIsolated`), so folders of one name in different sections or parents are told apart, with a divider between items (`historyStops` in `file-manager.tsx`, read as the menu opens, each a `HistoryStop`). Picking one goes there at once (`goInHistoryBy`, `useLocationHistory`'s `go(by)`, told as "back" or "forward" like the buttons, and asked of the consumer when the location is controlled), taking the focus into the content as they do (`leaveFor`). A disabled button has no list. Not yet: an `apiRef` method for it.
- Places in the history are rewritten with `revise` after a rename, a delete or a section changing, told as "replace", and the current one is the first section's root whenever its section is missing (see `props.md`).

## Going to a path

A path typed goes to the folder it names, as GNOME Files' location bar does (Ctrl+L). Ids are opaque and never parsed, so the file manager reads no path into an id: it looks for each name in the listing of the folder before it. The adapter needs no new member for it.

- **Opening** (`openPath`): Ctrl+L or ⌘L anywhere in the file manager while a section is shown (see `keyboard.md`), a click on the path bar's empty space, not on a segment or a button (the bar has the text cursor there, and cancels `mousedown` on it so the focus stays where it was, to go back to), the edit button at the path bar's end on touch screens (`@media (hover: none)`, as the Select button is, since they have no Ctrl+L), and `apiRef.editPath()`. The transfer picker's path bar, which is not given `onEdit`, has neither the click nor the button. The path field (`header-bar/path-field.tsx`) takes the path bar's place, in the pill the search field has (`styles/header-field.ts`), so nothing in the header moves. Search and the path field share that place, so opening one ends the other (`openSearch`, `openPath`), and the focus is given back to what had it before either (`searchOpener`, `pathOpener`).
- **The field** is a folder icon, an input named `editPath` ("Go to path") with the placeholder `pathPlaceholder`, a spinner while a path is looked for, and a ✕ ("Cancel", `cancel`). It starts with the open folder's path, selected: "/", the section's label and the folders' names, joined by "/", as the path bar writes it (`pathOf`, `utils/path.ts`). It runs as its own letters do (`unicode-bidi: plaintext`).
- **Closing**: Escape from any part of the field, or the ✕, gives the focus back, or else to the content; the focus leaving it closes it where the focus went, checked once it's gone so the window losing the focus doesn't count (the search field's way). Another folder opening, by any route, the consumer's included, closes it too, handing the focus to the content when it was in the field (a layout effect over the place, as the search's is). Closing while a path is looked for gives up on it (its `AbortSignal`).
- **Enter** looks for where the path leads (`submitPath`, then `followPath`, which the API's `goToPath` shares, then `resolvePath`), the input read-only meanwhile. Found, the field closes, the focus goes on to the content, and the place is gone to as the user opening a folder does (`goTo`, so a controlled `location` is asked for it, and the path bar shows where it is; the sidebar tree isn't expanded). Not found, what's wrong shows under the field (an `alert`, the input `aria-invalid` and described by it, outlined in `error`, over the content, so the header doesn't grow), the path kept to put right; typing clears it. Nothing is announced beyond that: the folder opening is said by the focus, the problem by the alert.
- **The grammar** (`resolvePath`):
  - Names are split on "/", the spaces around them and empty ones left out (`//` is `/`).
  - A path starting with "/" begins with a section's label, as the path bar shows it ("/Website/src/components"). The label is read as the names it holds, so one with a slash in it works, the longest label wins, and a label the same as typed before one the same by letters alone (`sectionNamed`). A first name that is no section's label is `pathNoSection`. "/" alone, like nothing, is the open place.
  - Any other path begins in the open folder: "src" goes into it, "." stays and ".." goes up a folder, stopping at the section's root.
  - A name is the entry called exactly that, a folder before a file of the same name, or else the only one called that by letters alone, case and accents aside (`Locale.foldLetters`), so "documents" finds "Documents". Several that differ only so aren't found, rather than one guessed (`entryNamed`). Hidden entries are found as the rest are, whatever "Show hidden files" says.
  - The last name may be a file, which goes to its folder and selects it there, scrolled to, as a created folder is (`revealEntry`). A file before the end is `pathNotFolder`.
- **Looking.** Each name is looked for in its folder's whole listing from the store (`listingOf`, shared with the clipboard's lookup and the undo's checks), so the cached listing is used, a paged folder is whole, and a section's own `adapter` serves it. A name it lacks lists the folder afresh and is looked for again before it is called missing (`pathNotFound`), since a saved listing may be from before a change. A folder on the way that can't be listed is `pathListFailed` with the adapter's message (`restricted` as the last name is gone to and shows its error, as clicking it does, since it's only listed once its contents show). Failures of `resolvePath` are `PathProblem`s, written out by `pathProblemText` with the names isolated.
- **From outside**, `apiRef.goToPath(path)` is the same without the field: it resolves with a `GoToPathResult` (public) instead of showing the problem, and moves no focus. It's aborted with the file manager unmounting.
- Not yet: completing a path as it's typed, a "/" typed in the content starting the field, and an optional adapter `resolve` for a backend where listing every folder on the way costs (see the roadmap).
- The playground's footer has "Go to path". Try "/Website/src/components", then "../.." from there, "docs" from Website's root, "/Website/docs/architecture.pdf" (a file, selected in `docs`), "/website/SRC" (found by letters), "/API service/cmd/server", "/Website/مستندات/صور" (names running both ways), "/API service/archive/missing" (isn't in “archive”, after listing its 10,000 entries again) and "/Website/restricted/x" (couldn't be opened).

## Hiding the docked sidebar

Below `rootWide` the sidebar is an overlay, opened and closed with `sidebarOpen`. Docked, it can be hidden instead, with `sidebarHidden` in `file-manager.tsx`, as in GNOME Files. The consumer can control it, or set where it starts (`sidebarHidden`, `defaultSidebarHidden`, `onSidebarHiddenChange`; see `props.md`):

- F9 hides and shows it (see `keyboard.md`), as does "Show sidebar" in the header's view menu, with F9 beside it. The menu portals out of the file manager, where its container queries don't reach, so it reads whether the sidebar docks as it opens (`sidebarDocked`, from the sidebar's computed `position`), and only offers the item then.
- While it's hidden, the header shows the "Show sidebar" button and search, as it does while the sidebar is collapsed.
- The sidebar takes `display: none` through `data-hidden`, only from `rootWide`, so a narrower root still has its overlay. The frame's `data-sidebar-hidden` gives the content and upload panels back their margin on its side (`besideSidebar`).
- The state outlives the root's width changing: hidden, then narrowed and widened again, it's still hidden. The overlay's doesn't: docking closes it (`handleSidebarDocking`, from a `ResizeObserver` on the frame), so narrowing again doesn't bring it back, as it would have, unseen while docked.

## Resizing the docked panels

The docked sidebar and the docked properties are each resized by their edge, as the panes of GNOME Files and Drive's side panel are. The overlays aren't (the overlay sidebar, the properties' overlay, and the hidden sidebar shown over the content for a drag), since they're passing panels over the content. Both go through `file-manager/resize-edge.tsx` (`ResizeEdge`), so they behave alike, and are the width settings the consumer can control or start (`sidebarWidth` / `defaultSidebarWidth` / `onSidebarWidthChange`, 248px, from `SIDEBAR_MIN_WIDTH` 200px to `SIDEBAR_MAX_WIDTH` 360px, and `propertiesWidth` and its two, 300px, from 240px to 480px; see `props.md` and "Resizing" in `properties.md`).

- **The edge** (`ResizeEdge`) is a strip along the panel's side: over the gap beside the properties, so it never lies over the content's scrollbar, and centred on the boundary with the content for the sidebar, which touches it, a few pixels over each side, so it covers only the edge of the tree's scrollbar. It is 10px wide (8px for the sidebar's), wider on a touch screen (`hover: none`), with the `col-resize` pointer, and shows a grip in the middle, a 4px pill in `text.disabled` as it's pointed at, taller and in `primary` while focused from the keyboard or dragged (`data-dragging`); `CanvasText` and `Highlight` under forced colors. The sidebar's edge is always rendered and shown by CSS only while the sidebar docks, and isn't while the hidden sidebar peeks over the content; the properties' is rendered while the docked panel shows. Both drop out of the Tab order when they're not shown.
- **Dragging** (by mouse, pen or finger, with pointer capture, `touch-action: none`): the panel follows the pointer from the width shown as it went down, within its limits and `widest`, widening as the pointer goes away from the panel (the way read with `isRtl`). Meanwhile the panel's custom property (`--sidebar-width`, `--properties-width`) and the edge's `aria-valuenow` are set on the elements without rendering anything, and the width is asked for once, as the drag ends (`endDrag`, which calls `onChange` unless nothing moved). The value the file manager has is set back at the same time, so a width the consumer refuses snaps back, and one they take renders in the same commit. `pointercancel`, the capture lost, Escape, or the edge going while it's dragged (the panel hidden or no longer docked) calls the drag off, putting back the width it had. A press on the edge doesn't take the focus from where it is, nor select text (`mousedown` is cancelled too, which cancelling `pointerdown` alone may not do).
- **Keys** on the edge, focused with Tab (the sidebar's after its tree, the properties' between the content and the panel): the arrow keys move it the way they point by `RESIZE_STEP` (16px), swapped right to left, Home and End make the panel as narrow and as wide as it goes, as the window splitter pattern has them, each asked for at once. Escape calls a drag off, and otherwise is the pane's. A double click puts the width back to the `default…` one.
- **For screen readers** it's a focusable `separator` (`aria-orientation="vertical"`), named `resizeSidebar` or `resizeProperties`, controlling its panel, with the width shown as `aria-valuenow` between `aria-valuemin` and `aria-valuemax` (`widest`), in px, which they read as it changes, so a resize by key needs no announcement of its own. They're measured by a `ResizeObserver` on the panel and its parent, and again as the edge takes the focus, since what's left beside the panel also changes with the other one.
- **Both panels at their widest.** Both can't be, in a root that's too narrow for them and the content, and the content comes first. It keeps `CONTENT_ROOM` (540px, `viewMedium`, so the list keeps its size and date columns), with its margins (`contentRoom`), as the content column's `min-width` and the main part's, from `rootWide`; with the properties docked beside it, the main part's also holds the properties' least width and margin, so the panels give way in an order, with nothing worked out in JS:
  1. The properties narrow first, as their row is too narrow, down to their 240px.
  2. Then the sidebar narrows (`flexShrink: 1`, its `width` a custom property, down to its 200px), as the main part keeps its `min-width`.

  Together with the content's room and the margins, the least widths always fit a root that docks them (900px and 1100px, as the breakpoints are set), and both panels at their widest (360px and 480px, kept low on purpose, as a side panel that wide is a split pane) fit beside the content in a root 1400px wide, so only a narrower one has them give way. A width asked for that doesn't fit only shows narrower, and wider again as the room comes back; what the user made isn't changed. At `rootExtraWide` itself, beside the sidebar's 248px, the properties have exactly their 300px.
- **Dragging never squeezes the other panel**, so one that was just made wider isn't undone by the next. `widest` is how much the room around the panel leaves it, with the other panel as it is now: the properties' (`widestOf` in `properties-pane.tsx`) is their row's width less the content's least width, the sidebar's outside it already; the sidebar's (`widestSidebar` in `file-manager.tsx`) is the frame's width less the content's least width and the docked properties' width as shown, with their margin, or none while they're hidden or an overlay. Drag the sidebar to a width and the properties keep theirs; the other way, the same.
- The tree's rows and the content's lines follow with no work of their own: nothing in the tree depends on its width, and the content measures itself as its panel resizes (see `virtualization.md`).
- Right to left: the edges sit on the panel's logical sides and the arrows and the drag swap with the direction (see `rtl.md`).
- Not yet: kept widths for the media manager's own panels, which will need the same edge.

## Search

A folder search filters the open folder's listing as it's typed (see "Searching the open folder"). A search everywhere asks each section's adapter, through its optional `search`, and shows what they find in the content panel, with a tab per section (see "Searching everywhere"). Searching is a passing state, not a dialog, so the results show where the content does, and selection, the menus, dragging and opening work on them.

There are two scopes (`SearchScope`, `types/search.ts`, public), as in GNOME Files 46:

| | Folder search (`"folder"`) | Search everywhere (`"everywhere"`) |
|---|---|---|
| Button | right after the path bar, in its grid area, so it stays beside the path bar or the field | the magnifier at the top of the sidebar, and the header bar's while the sidebar is collapsed or hidden; neither, nor the keys, when no section's adapter has `search` |
| Icon | `searchFolder` (`ManageSearch`; Material has no folder with a magnifier) | `search` |
| Keys | Ctrl+F or ⌘F | Ctrl+Shift+F or ⌘⇧F |
| Covers | the open folder | every section checked in the field's sections menu whose adapter has `search` |
| Placeholder | "Search in ‹folder›" (`searchIn`) | "Search everywhere", "Search in ‹section›" with one checked, "Search in 3 sections" (`searchInSections`) |

- While `searchScope` is set (`file-manager.tsx`), the search field (`header-bar/search-field.tsx`) takes the path bar's place, the same pill in the same place, so nothing in the header moves: on its own row below the buttons when narrow, centred between them from `rootMedium`. It's a `search` landmark holding a `type="search"` input named "Search", led by the scope's icon, with a ✕ that clears what's typed, or closes the search when nothing is ("Clear search" / "Close search"). The browser's own clear button is hidden.
- The buttons are toggles (`aria-pressed`, `primary.main` while pressed): one closes its own scope's search, and opens it or switches an open search to it otherwise, keeping what's typed. The keys open or switch the same way, and focus the field with what's typed selected. The keys are kept from the browser's find while the focus is in the file manager (see `keyboard.md`); found from outside it, through the browser's own find, every entry is found, rendered or not (see "Find in page" in `virtualization.md`).
- The field takes the focus as it opens. Escape, from any part of the field, the ✕ with nothing typed, or the open scope's button closes it and gives the focus back to what had it before (`searchOpener`), or to the content when that's gone or hidden, as the header's magnifier is once the sidebar docks. The ✕, the sections button and the search buttons keep the focus in the field as they're pressed (`preventDefault` on `mousedown`), so a press doesn't first blur it.
- Down or Enter in the input goes on to the content (`focusContent`). The focus leaving the field, all of it, with nothing typed closes the search and leaves the focus where it went, checked once it's gone so the window losing the focus doesn't count, nor the sections menu having it; with something typed, the field stays.
- Opening another folder, by any route, the consumer's included, ends the search and drops what's typed, as in GNOME Files, a search everywhere too: opening a folder among its results goes there. It's worked out as the place changes during rendering, with the folder left through (`shownPlace`); a place rewritten to the same folders, as after a rename, keeps it.
- Typing in the content is still type-ahead and doesn't start a search.
- The query runs as its own letters do (`unicode-bidi: plaintext`), and names in the placeholder are isolated (`isolate`).

### Searching the open folder

While the scope is `"folder"`, `file-manager.tsx` hands the query to `FolderView` (`query`, empty in the other scope), which lists only the entries whose names hold every word typed, anywhere and in any order. It's a filter of the listing the store already has, the open folder's own entries and not its subfolders', which a search everywhere reaches.

- Words are split on spaces, and names and words are folded alike by `Locale.foldLetters` (`utils/format.ts`): lowercased the `locale`'s way, then NFKD with the marks dropped, so case, accents and full-width forms don't count. Unlike `sameLetters`, it leaves out every language's accents, since collation can't find text within text (`searchTerms` and `holdsTerms`, `utils/search.ts`). Nothing but spaces is no search.
- The folder view filters after hiding and sorting (`shown`, then `entries`), so it never sorts again per letter, and folds the names once per listing (`foldedNames`). As with hidden files, everything that goes by what's listed goes by the results: the arrow keys, type-ahead, Select all, the marquee, the selection bar's total, the preview's stepping, and actions and shortcuts, which act on the selected entries shown.
- Selected entries the search leaves out stay in the selection's ids but don't count, as hidden ones do, so they come back selected once the search ends, and nothing is done to an entry that isn't shown.
- Each change to the words typed starts the results over: the Tab stop goes back to the first match, or the first one selected, and the panel scrolls to the top. Ending the search, or clearing what's typed, shows the whole folder scrolled to the entry with the Tab stop, so a file found and picked stays in view.
- While a folder is still coming in page by page, its matches show as they come, under the progress bar. With none shown yet it waits with the spinner, so "No results found" ("Try a different search", `searchNoResults` and `searchNoResultsHint`, with the search icon) shows only once all of it has come, as "Folder is empty" does.
- Screen readers hear the number of results (`searchResultCount`) from a `status` region of its own as it changes, once all of the folder has come.
- An entry to reveal (a folder made or renamed, `FileManagerApi.reveal`, the preview's stepping) that the search leaves out ends the search (`onRevealUnmatched`, which is `closeSearch`), and is then revealed in the whole folder, rather than given up on.
- The open folder's empty space refuses entries it lists, shown or not (`listsDragged` reads the whole listing), so a tree folder hidden by the search can't be dropped into its own parent.

### Sections searched everywhere

A search everywhere covers every section whose adapter has `search` (`searchTargets` in `file-manager.tsx`), but the trash (see `trash.md`), unless some are unchecked in the field's sections menu (`header-bar/search-sections-menu.tsx`), which is only there when more than one section can be searched. The others aren't searched, nor in the menu (`searchGroups`), since crawling them with `list` would be a request per folder. With none that can be, there's no search everywhere, and a search everywhere left with none, as the sections change, searches the open folder instead.

- Its button sits between the input and the ✕ and says what's covered: "All sections" or "3 sections" (`allSections`, `sectionCount`), with a chevron, named "Sections to search" (`searchSections`). Alt+Down in the input opens it too, as a combobox's list.
- The menu is built as the view menu is (`dense`, `menuitemcheckbox` items with a display-only `Checkbox`, unsticky subheaders, hanging from the button's end edge by its element direction): "All sections" first, checked when all are and mixed (`aria-checked="mixed"`, indeterminate) otherwise, then each `SectionGroup`'s `title` as a subheader, when it has one, and its sections with their icons and isolated labels. Picking "All sections" checks them all.
- It stays open while sections are toggled, and gives the focus back to the field as it closes. The last checked section is disabled, so a search never covers nothing.
- `file-manager.tsx` keeps the unchecked ids (`searchExcluded`) while it's mounted, across searches, so a section added later is checked. Ids of sections gone, or that can't be searched, don't count, and every section left unchecked counts as none (`excludedSections`).
- The scope, the query and the sections left out are public state (`search`, `searchExcludedSections` and their `default…` and `on…Change`; see "Controlled or not" in `props.md`), as is opening and closing from `apiRef`.

### Searching everywhere

The adapter's optional `search(rootId, query, { signal, cursor, showHidden })` resolves with a `SearchResult`: `matches`, each a `SearchMatch` of the `entry` and its `trail` (the folders from the root down to the one holding it, as `FolderRef`s, the root not counted), and an optional `nextCursor`. How entries match is the backend's call; its comment suggests the folder search's every word anywhere in the name.

- It's called once per section searched, with the section's `rootId`, so two sections on one adapter are searched apart. `query` is what's typed, trimmed. The `trail` is there since ids are never parsed: the Location column, opening the folder and every action's `folder` come from it.
- `hooks/use-search.ts` runs it, a section at a time and all at once, `SEARCH_DELAY` (300 ms, or `limits.searchDelay`, handed down as `SearchResults`' `delay`) after the typing stops, each with its own `AbortController`, aborted as soon as the query, `showHidden` or the sections change. It fetches every page, as the store does a listing's, showing what's come at most every 500 ms; a backend that caps its results stops handing a cursor back, and one handing back the cursor it was given fails the section. A match a later page repeats is listed once (by `resultKey`). Each section's `SectionSearch` is "searching", "ready" or "error", and a section searched again keeps showing what it found before, under the progress bar, until its first page comes, so typing doesn't flash the spinner. `retry` searches some sections again at once.
- `searchVersion` in `file-manager.tsx` counts the changes made through the file manager (`relist`, every dialog's `onChanged` and the upload queue's, `refresh` and `ActionContext.refresh`), and a new count searches again, keeping what's shown, so a result renamed, moved or deleted updates.
- `showHidden` goes to the adapter, which leaves out hidden entries and what's in hidden folders while they don't show; entries it hands back that `isHidden` says are hidden are left out of the results anyway.

`content/search-results.tsx` shows them in the content panel while the scope is "everywhere" and something other than spaces is typed (`showsResults`). The folder view stays mounted under it, hidden, so it comes back as it was, selection and all, and doesn't take the focus meanwhile.

- **Tabs** (`content/search-tabs.tsx`), when more than one section is searched: "All" (`searchAll`), then each section in the sidebar's order, with its count once it's done, a spinner while it's searched and an error icon when it failed. They only choose which results show; the sections menu chooses what's searched, so unchecking a section takes its tab away, and a tab whose section goes falls back to "All". It's a `tablist` named "Results by section" (`searchTabs`), above the scrolling view so it never scrolls away, built of `ButtonBase`s rather than MUI's `Tabs`, whose indicator and scroll buttons follow the theme's direction (see `rtl.md`). The open one is underlined in `primary`, and the strip scrolls sideways without a scrollbar when they don't fit. The view is its `tabpanel`.
- **The results** are one list, or grid, as the view setting says, sorted by the content's order (`entryComparator`) across sections. Entries of different sections may share ids, and one entry may be found in two sections sharing an adapter (the Website source bookmark's inside Website), so each result is a `SearchHit` keyed by `resultKey(sectionId, entryId)`, and shows once per section it's found in. The views get copies of the entries with the key as `id`, and `FileViewProps.origins` with each one's own entry, adapter and location, so icons and thumbnails ask the right adapter for the right entry, and selection, cut and dragged marks and drop targets go by key.
- **Location**: the section's label and the trail's names joined by " / " (`joinIsolated`), the section left out inside its own tab but for an entry right in its root. In the list it's a column after the name from `viewMedium`, headed "Location" (`searchLocation`), sorted by as the other columns are (`location`; see "Sorting"), and the line under the name below it, in place of the size and date. In the grid it's an outlined pill under the name (a `divider` border, since forced colors drops a fill), a small `folder` icon and the location in `text.secondary` at 0.6875rem, so it doesn't read as more of the name; the text takes two lines, like the name, and the pill is as tall whether or not it fills them, so every tile is still as tall as the others (see `virtualization.md`).
- **States**: a spinner until something shows, "No results found" once the tab's sections are done, a failed section's "Couldn't search ‹section›" (`searchFailed`) with the adapter's message and Try again, and in "All", with nothing found and some sections failed, "Some sections couldn't be searched" (`searchSomeFailed`) with Try again for them. The progress bar shows while something is shown and still searched, and screen readers hear the count once it's done.
- **Selection** is the results' own (`useSelection` over the keys): clicks, the keys, Ctrl+A, the marquee and type-ahead work as in a folder, and every new query or tab starts the Tab stop on the first result, scrolled to the top. There's no touch selection mode; a tap opens. `onSelectionChange` isn't told it (see `props.md`).
- **Acting on results**: the selection is acted on as a whole. A right-click, ⋮ or the Menu key on a selected result opens the menu for all of them; on an unselected one, the result is selected alone first. Shortcuts run for the selection, and a drag carries it, or else the grabbed result alone. Results of one folder make the `MenuRequest` of that folder (`section`, `trail`), with that folder's results as the `listing` the preview steps through; results of several, of one section or more, are grouped by folder (`groupByFolder`, `utils/groups.ts`) into one request with `groups`, as "Acting on several folders" below says. `inResults` is set either way. The results have no folder of their own, so their empty space has no menu, takes no drop and runs no shortcut; folders among them take drops by the paste rules.
- **Opening**: a folder result opens its folder, which ends the search; a file opens as in a folder (`openFile`). `ActionContext.openLocation()`, only for a single result, opens the folder it's in and reveals it there, selected, ending the search even when that's the open folder. The playground's "Open item location" shows only then.
- The playground's mock `search` walks its tree below the root, matching as the folder search does, leaves dotfiles and dot folders out while hidden files don't show and doesn't look in folders that fail, and hands back 200 results a page, so "record" in API service comes in pages from `archive`'s 10,000.
- **Relevance** is the order the results start in (`RELEVANCE_SORT`, the `sort` key `"relevance"`; see "Sorting"): best first, by the adapter's `SearchMatch.score` when it ranks its matches, else by `relevanceOf` (`utils/search.ts`) on the names folded as the words are: a name that is the words, extension aside, first, then one starting with them, then each word counting for more where it starts a word of the name than inside one, a shorter name ahead of a longer one scoring alike, and ties by name. Folders aren't put first. Scores are compared across sections.

### Acting on several folders

Every adapter call that takes entries takes entries sharing a folder (`copy`, `move`, `delete`, `download`), so a search's selection from several folders, of one section or several, is carried by folder, as `EntryGroup`s (`types/menu.ts`: a section, a trail and its entries), and the file manager asks each folder's adapter for its entries. `groupByFolder` (`utils/groups.ts`) makes them from the results, keyed by adapter and folder id, as ids are unique within an adapter: a folder shown by two sections sharing an adapter is one group, in the first section it comes in, and an entry found in both is acted on once. A `MenuRequest` has them as `groups` (missing for one folder, `requestGroups` filling in), with `section` the first group's and `trail` the nearest folder of that section holding its own (`selectionRequest`, `commonTrail`), and `contextFor` hands them to the app as `ActionContext.byFolder` (`ContextFolder`, public: each section, folder and entries).

- **What's offered.** Only an app's actions marked `acrossFolders` (`FileAction`, public), left out otherwise by `visibleActionGroups`, since an action written for one folder would act on `folder` and `section`, where the entries aren't all. Every member for entries takes them: `copyTo`, `moveTo`, `cut`, `copy`, `delete`, `download`, `preview`, `properties` and `refresh` (each folder of theirs); `createFolder`, `upload`, `uploadFolder` and `paste` are for a folder, which they have none of, and those for a single entry go by their count. `readOnly`, `moving` and the permissions go by every folder of theirs, each through its own section and adapter: one that can't change, or one entry that refuses, keeps the rest from it too.
- **Copying and moving** (the picker, a paste, a drop): the clipboard and a drag carry `parts` (`ClipboardPart`, an `EntryGroup` with the adapter serving it and its own `lookup`), and `startTransfer` queues one transfer per folder, each through its own adapter, or across into another's (see "Between adapters" in `transfers.md`). The picker offers the sections that take entries from each of theirs (`importsFrom`) and that every part can go into (`carries`), whichever adapter serves them, starting where they are, or in the first of those. Entries already in the destination are left there by a move and kept both by a copy, so collecting a search's files into the folder one of them is in works, and they're not counted as clashes (the picker's and the paste dialog's `incoming`); "Move here" is only disabled when every one is there already. What's done is announced once, as the last of them ends (`TransferBatch`). Each is one transfer in the panel, failing and tried again by itself. Results of sections served by different adapters go together, each part through its own.
- **Names shared among them.** Entries of different folders may share a name, which one folder can't hold twice. `entryClashes` (`utils/transfer.ts`) counts each such entry after the first as a clash (`Clash.shared`, an `EntryClash` with the entry), so the clash step asks about them as about names the destination has: "Another item going into “docs” is also named “README.md”." (`conflictSharedMessage`), or beside the destination's own clashes, `conflictSharedToo`. Keep both, Skip and Replace then do to each what they do to a name the folder has, as each lands in turn: the batch's transfers run one after another (`TransferItem.after`, see `transfers.md`), so the first is there before the next is settled against it. The entries skipped are handed over as entries rather than names (`skipped`), so the announcement counts the first one, which went in.
- **Deleting** asks once, then deletes a folder's entries at a time, each through its own adapter (`DeleteRequest.groups`, `DeleteGroup`). One that fails stops it, showing the message, and Delete tries only the folders not yet deleted; closing then finishes with those deleted (`onDone` with only them), so the clipboard, the cache and the history follow what went, adapter by adapter (`handleDeleted`).
- **Downloading** is one file per adapter from its optional `downloadAcross(groups, options)` (`EntriesInFolder`, public: each folder and its entries), or without it, one file per folder through `download` and `content` as for any folder's entries (`downloadSpread` in `contextFor`). A download from `downloadAcross` is a `DownloadItem` with `groups`, named, when the blob comes without a name, after the folder holding them (see `download.md`).
- **Previewing** steps through the files among them, each with its own section, adapter and folder (`PreviewFile`), following its own folder's listing (see "Following changes" in `preview.md`).
- **The properties** show them as several entries, "Several folders" for their location, counting folders through each adapter's `measure`, and the header's `propertiesActions` marked `acrossFolders`.
- The playground's Preview, Download, Cut, Copy, Copy to…, Move to…, Share, Delete… and Properties are `acrossFolders`, and Download and Share in the properties' header; Compress… isn't, as its archive goes beside the entries. Its mock adapter's `downloadAcross` zips each folder's entries in a folder of its name, numbered when two share one.

## The main menu

The ☰ button at the sidebar header's end (`sidebar/main-menu.tsx`) opens the main menu: the file manager's own Undo and Redo at the top, named by the change ("Undo rename", "Redo move", or disabled "Undo" with nothing to; see `undo.md`), shown while anything can be undone, then the consumer's `mainMenu` (`MainMenuGroup[]` of `MainMenuItem`s, `types/main-menu.ts`, public), for what belongs to the app rather than to entries, such as preferences, help or about, then a rule and the file manager's own "Keyboard shortcuts" (Ctrl+?, see "The keyboard shortcuts window" in `keyboard.md`). It's built as the context menu is: dense, a rule between groups, labels inset when others have icons, shortcuts beside them in `<bdi>` with `aria-keyshortcuts`. It hangs from the button's end edge by its element direction, as the view menu does.

- An item has `id`, `label`, an optional `icon`, `shortcut` and `disabled`, and `onSelect()`, with no context, since it's about no entry. Empty groups are left out. Picking an item closes the menu first.
- An item's `shortcut` works anywhere in the file manager (see `keyboard.md`), and shows in the keyboard shortcuts window with the actions'.
- The sidebar's Escape, which closes the overlay, only counts from inside the sidebar, since the menu portals out but its key presses still bubble through the sidebar.
- The menu is reached from the sidebar only: while the docked sidebar is hidden, or the collapsed one closed, its items run by their shortcuts, and the shortcuts by Ctrl+?.
- The playground has Preferences (Ctrl+,) and About Files, which report that they ran.

## Context menu and actions

An `ActionContext` says whether `entries` ("selection") or a folder's empty space ("folder") was targeted, whether its folder is `readOnly` (see "Permissions"), and offers `refresh()` and `openFolder()`. It also offers `open()`, `preview()`, `download()`, `properties()` (always there; see `properties.md`), `createFolder()`, `createFolderInto()`, `rename()`, `copyTo()`, `moveTo()`, `cut()`, `copy()`, `delete()`, `trash()`, `restore()`, `openOrigin()`, `emptyTrash()` (see `trash.md`), `select()` (only in a menu a long-press on a tree folder opened, see "In the sidebar tree" in `selection.md`), `upload()`, `uploadFolder()`, `paste()` and `pasteInto()`, which are left out when the section's adapter lacks the matching method (`preview` when the entries hold no file the preview can show, which without `content` is only one a previewer reading nothing takes; `download` lacking `download`, unless the entries are a single file and there's `content`, and downloading the folder itself when there are no entries; `open` unless there's exactly one entry, and for a file nothing can open; `rename` also when there isn't exactly one entry, `copyTo`, `moveTo`, `cut`, `copy` and `delete` when there are none, `upload` when the section's `acceptUploads` is false or while another upload is being checked, `uploadFolder` also when the adapter has no `createFolder` or the browser can't pick folders, `paste` and `pasteInto` when there's nothing to paste there, `pasteInto` and `createFolderInto` also unless the entries are a single folder, and whatever changes a folder or the entries when the permissions refuse it, see "Permissions"), so actions hide with `visible: (context) => !!context.rename`, or grey out with `disabled`. The consumer still places, labels and gates these actions; the file manager adds nothing to the menu itself.

- Actions apply to any number of selected entries (copy, move, delete, compress...). Only actions marked `single: true`, such as rename, hide while several entries are selected, and only those marked `acrossFolders` show for a search's selection from several folders, of one section or more (see "Acting on several folders").
- The menu opens on right-click (items, content background, sidebar rows), from the ⋮ buttons (list rows, path bar), with the Menu key or Shift+F10 on a focused entry, tree row or the view (see `keyboard.md`), and on touch, from a long-press on a tree row or a search everywhere's result once the finger lifts (see "Drag and drop"), a tree folder's with `select()`; a long-press in a folder starts selection mode instead (see `selection.md`), as one on a tree folder does once the tree is in it.
- When no action applies, the browser's own menu is left alone.
- The same `ActionContext`, for the file shown, goes to the actions in the preview's header (`previewActions`), with `closePreview` added and `preview` left out, and for what the properties show, to those in the panel's header (`propertiesActions`); both headers show them through `ToolbarActions` (see `preview.md` and `properties.md`).
- `FileManagerApi.actionContext(entries?, location?)` builds the same context through `contextFor`, for a consumer's own toolbar (see "The API" in `props.md`).
- `context-menu/` renders the grouped menu from the groups that `utils/action-groups.ts` leaves visible.
- An action's `shortcut` is also a key binding (`utils/shortcut.ts`; Ctrl matches ⌘ too), matched on any keyboard layout (see "Keyboard layouts" in `keyboard.md`). `folder-view.tsx` takes focus on any press and hands key presses to `runShortcut` in `file-manager.tsx`, which tries the selection first and then the open folder, through the same `contextFor` and visibility rules as the menu. Sidebar tree rows do the same with the row (or the tree's selection) and then the row's own folder, and a section row with its root. Shortcuts come before the component's own keys. Browsers keep some keys for themselves: Chrome never passes Shift+Ctrl+N (or Ctrl+N, Ctrl+T, Ctrl+W) to a page.

## Creating and renaming

Both use one small modal, `dialogs/name-dialog.tsx`, rather than editing names inline, because the listing only holds what the adapter returned, and an inline edit has nowhere to keep a failed name. The adapter's optional `createFolder(parentId, name, { signal })` and `rename(entry, name, { signal })` resolve with the entry as it now is.

- `createFolder()` makes the folder in the one the menu is for: the open folder (its empty space, or the path bar's ⋮) or a section's root. A menu on a folder itself, in the content or on a sidebar tree row, has the folder as its `entries` and its parent as `folder`, so it offers `createFolderInto()` instead, for a "New folder inside…" action beside "Paste into folder" (the playground's, with no shortcut: Shift+Ctrl+N is for the open folder). It asks for the same dialog with the folder's trail.
- The name is trimmed and checked as it's typed (`nameProblem`, `utils/names.ts`): not ".", "..", or containing "/", then the backend's own rules, then no clash with the folder's cached listing. An empty name only disables the button. The adapter has the final say, and the message of an `Error` it rejects with shows under the field, with the name kept.
- **The backend's own rules** are the adapter's optional `checkName(name, { kind, parentId, entry })` (`NameCheck`, `types/adapter.ts`, public), for what only some backends refuse, such as Windows' `\:*?"<>|`, its reserved names, or a length limit. It returns the message, in the consumer's language as action labels are, shown isolated under the field with the button disabled, or nothing when the name is fine. It's synchronous, as it runs on every keystroke, and never sees an empty name or one the built-in rules refuse. A rename's unchanged name isn't checked, since the entry has it already, so one made elsewhere under other rules can still be closed with Rename. The transfer picker's New folder goes through the same dialog. Uploads go by it too, before anything is sent (see "The check before queueing" and "Folders" in `uploads.md`).
- The playground's server adapter (Website, API service and their bookmarks) holds names to Windows' rules (`windowsNames` in `mock-adapter.ts`), refusing them in `createFolder`, `rename` and `upload` too; the media bucket takes any name.
- The field is focused with the name selected once the dialog has faded in (the transition's `onEntered`), not with `autoFocus`, which the closing context menu steals focus back from. Rename selects a file's name up to its extension. New folder starts with the first unused `untitledFolder` name, "New folder" then "New folder (2)" in English (`newFolderName`). Until something is typed, the suggestion follows the folder's listing as it comes (and is selected again if it changes), and Create waits for all of it unless listing failed, since a folder created in from its own menu (`createFolderInto`) may never have been listed. Submitting keeps the name as it is, so it doesn't move on as the folder is listed again during the fade-out. An unchanged name just closes.
- While the adapter works, the button shows a spinner and the field is read-only. Cancelling aborts the `signal`, but the folder is listed again anyway, since the change may already have been made.
- Afterwards the folder is listed again, with every listing holding it, for the item count (`relist`). If the folder is open, in whichever section, `file-manager.tsx` asks `FolderView` (`revealId`) to select the entry and scroll to it once the refreshed listing has it. `FileManagerApi.reveal` goes the same way; a reveal is dropped once another folder opens, or when the folder's whole listing has come without the entry (`revealLost`).
- A new folder is also scrolled to in the sidebar tree (`treeReveal`, a `TreeReveal`, from `revealInTree`, which a folder made in the transfer picker goes through too), in the first section whose tree has its row. It waits for the row, which comes with the refreshed listing, and scrolls the tree just far enough to show it (see `virtualization.md`). Nothing is expanded or selected for it, and the focus stays where it is, so navigation still never opens the tree. It's given up on when the folder it was made in isn't shown expanded in the tree, as when the sidebar has it collapsed, and for a hidden name while hidden files are off. A rename isn't scrolled to.
- A rename, and a folder made, here or in the picker, go in the undo history (`recordNamed`), and the notice over the content says so with Undo (see `undo.md`). `applyNamed` does what follows a rename or a new folder, for the dialog and for an undo or redo alike.
- A renamed folder keeps its place in every section showing it: `renameInPlace` (`utils/navigation.ts`) rewrites every place in the history, and its expanded state carries over. When its id changed, as path ids do, the ids below it can't be worked out, so trails into it end at the renamed folder, and the old id and the new one go through `dropFolders`, since either could hold another folder's contents. A section rooted in the folder stays where it is, under the old id.

## Copying and moving

"Copy to…" and "Move to…" ask for a destination in `dialogs/transfer-dialog.tsx`, then hand the adapter's optional `copy(entries, targetId, { signal, conflict, onProgress, onEntryDone })` or `move(...)` to the transfer queue, which runs it in the background, shown in a panel once it takes a moment, as a paste and a drop are (see `transfers.md`). Into a section another adapter serves, the queue copies them across itself, reading through their adapter's `list` and `content` and writing through the other's `upload` and `createFolder`, and for a move deleting each from theirs once it's there (see "Between adapters" in `transfers.md`). The step asking about names the destination has is `dialogs/conflict-step.tsx` (see "Name clashes").

- The picker browses folders only, starting in the entries' own folder (for a search's results from several, the nearest holding them all), with the path bar and a back arrow to the folder above. Its folder list is one tab stop, moved through with the arrows (see `keyboard.md`). The sections offered are those the entries can go into (`destinationsFor` in `contextFor`): served by their own adapter, which copies or moves them itself, or by another, which takes them across (`carries`: their adapter's `content`, and `delete` for a move, with the entries' own `delete` permission; the other's `upload`, and `createFolder` for folders), each listed through its own adapter. Of those, only the ones whose `importFrom` takes the entries' section (see "Sections taking entries from each other") and that aren't `readOnly`, but for the entries' own, and never the trash; with more than one, going back from a root reaches a list of them.
- A folder that can't change (`folderWritable`, see "Permissions") can be gone through but not chosen: "Copy here" / "Move here" and New folder are disabled, and "This folder is read-only" (`pickerReadOnly`) shows at the start of the buttons' row, describing the disabled button.
- The entries being copied or moved can't be opened, so a folder can never go into itself or below itself, without the component parsing ids. Moving into the entries' own folder is disabled (for several folders' entries, only into a folder every one is in already).
- Before running, the destination's cached listing is checked for names the entries share, so "Copy here" / "Move here" is disabled until all of it has come (see "Paging"). Clashes get a second step (see "Name clashes"), whose choice is passed as `conflict`; otherwise `conflict` is "keepBoth", so a clash the cache missed never overwrites anything. Copying into the entries' own folder keeps both without asking, as a duplicate.
- Its folder list renders only the rows in or near view (see `virtualization.md`).
- When the adapter has `createFolder`, a New folder button at the end of the picker's toolbar opens `name-dialog.tsx` over it, for the folder the picker shows, once that folder's listing is complete (so the name starts unused and clashes are caught). The name dialog is rendered beside the picker's `Dialog`, not inside it, so its key presses don't bubble through the picker. Once created, the folder it was made in is listed again as any create is, the new id goes through `dropFolders` (`onFolderCreated`, `handleFolderCreated` in `file-manager.tsx`) before the picker lists it, and the picker opens it, since its destination is the folder it shows and a folder made there is meant to take the entries, as in GTK's file chooser. Going back up lands on it as the folder left through, scrolled to wherever it sorts. It isn't selected in the content, even when its parent is open there.
- Choosing hands it off and closes the picker: progress, cancelling and errors are the transfer panel's. However it ends, the destination is listed again, and for a move the source too, with the listings holding them (`relistTransferred`).
- After a move, moved folders go through `dropFolders`, and the open place, if it's inside one in any section showing it, goes to the destination instead.
- Once done, a copy or move goes in the undo history, when the adapter says what it made (see `undo.md`), between adapters as within one.

### Name clashes

The transfer, paste and upload dialogs ask about names the destination's listing already has through `dialogs/conflict-step.tsx`: `ConflictMessage` names them and says what each choice does, and `ConflictChoices` offers the choices. `findClashes` (`utils/transfer.ts`) finds them, each a `Clash` (`types/folder.ts`) of the name, what comes in and what's there, by kind, and whether what's there is `locked`: not `replaceable` (`utils/permissions.ts`), as a file whose `write` is false, or a folder whose entry's or own cached listing's `write` is false, is. One choice covers every clash, passed to the adapter as its `ConflictPolicy`, whose comment is the adapter's rule:

- **Replace** puts a file in the place of a file and **merges a folder into a folder**: what's in it goes in the same way, all the way down, so only files with the same names are replaced, as Windows and GNOME Files do it, rather than a whole folder going. A file and a folder never take each other's place, and nothing takes the place of, or is merged into, what its permissions keep from changing; they're kept both, whatever was chosen but Skip.
- The button reads **Merge** (`merge`) when no file clashes with a file it can replace but a folder does with a folder it can merge into, and is **left out** when nothing can be replaced, every clash being between a file and a folder or with what can't change, leaving Skip and Keep both.
- **Keep both** is the main, contained button, last in the row, since it loses nothing; Skip and Replace are `inherit`. The order is Skip, Replace, Keep both, after Cancel (or the picker's Back) and a spacer.
- The hint under the message follows what Replace does: `conflictHint` while a file can replace a file, `conflictMergeHint` while only folders merge into folders, and when nothing can be replaced, `conflictKindHint` for clashes of a file and a folder, `conflictLockedHint` for clashes with what can't change, or `conflictNothingReplacedHint` for both. Beside `conflictHint`, `conflictReplaceMerges` says that folders are merged, and beside either, `conflictKindKept` and `conflictLockedKept` say which entries would be kept with new names, as a file and a folder can't replace each other, and what's read-only there can't be replaced.
- Skip passes "skip" for clashes the cache missed; the entries skipped go to `onStart`, so the announcement leaves them out. Uploads leave skipped files out of the queue rather than sending them (see `uploads.md`).
- After a Replace or Merge, the folders merged into, those `replaceable`, are listed again all the way down (`mergedFolders`, see "Changes show in every section sharing the adapter").
- What's below a folder merged into is the adapter's to settle by the same rule, as the clash step only sees the destination's own listing. Uploads settle it themselves, as they list what they merge into (see "Folders" in `uploads.md`), and so do copies and moves between adapters (see "Between adapters" in `transfers.md`).
- The playground's mock adapter merges as the rule says, keeps both beside what's read-only, and fails merging into `restricted`. API service's `migrations` and `go.sum` are read-only, to see it: copy `go.sum` into `cmd` and back, or a folder named `migrations` into API service's root.

## Deleting

`ActionContext.delete()` asks to confirm in `dialogs/delete-dialog.tsx`, then calls the adapter's optional `delete(entries, { signal })`, which deletes for good, folders with everything in them, once per folder, through each one's adapter, for a search's results from several (see "Acting on several folders"). Nothing is deleted without asking, shortcut included. Where the adapter has a trash, `ActionContext.trash()` moves entries there at once instead, as a desktop's Delete key does, and the trash section restores them, deletes them for good, and is emptied through this same dialog (`emptiesTrash`; see `trash.md`).

- The dialog names the entry, or counts them, says folders go with their contents, and that it can't be undone. Delete is focused once the dialog has faded in (`onEntered`, as in the name dialog), so the Delete key then Enter deletes, and Escape cancels.
- Progress, cancelling and errors work as in the name dialog. A rejected call leaves the dialog open to try again, with the folder listed again in case some entries went anyway.
- Done, failed or cancelled, the entries' folder is listed again, with the listings holding it (`relist`).
- Deleting can't be undone, so it ends the undo history (see `undo.md`), unless it's the copies undoing a copy deletes, which the same dialog confirms (`undoesCopy`). `applyDeleted` does what follows, for both, through `applyGone`, which a move to the trash and a restore share.
- Once done, deleted folders go through `dropFolders`, and `outsideDeleted` (`utils/navigation.ts`) ends every trail in the history that goes into one at the folder that held it, in every section showing it, so deleting the open folder from the sidebar opens its parent. Deleted entries leave the clipboard (`withoutEntries`, shared with moving), and the rest are looked for again when they may be below a deleted folder (see "Cut, copy and paste").

## Sections taking entries from each other

Entries move or copy between sections served by the same adapter object, which does it itself, and into sections another adapter serves, which the file manager copies them across into (see "Between adapters" in `transfers.md`). A section's optional `importFrom` (`SectionImports` in `types/section.ts`, public) narrows which sections it takes entries from, of either kind: `true` (the default) every one, `false` none, `{ allow }` only the sections with those ids, `{ deny }` all but those. The type lets a section give `allow` or `deny`, not both. Moving or copying within a section is always allowed as far as `importFrom` goes (permissions may still refuse it, see "Permissions"), and unknown ids are ignored. `acceptUploads` doesn't come into it, being about files from outside the file manager, though entries from another adapter arrive through `upload`, which can refuse them.

- `importsFrom(target, source)` in `utils/sections.ts` decides it, by section id. The source is the section the entries were listed in when they were cut, copied, dragged or picked for "Move to…" / "Copy to…", even when the same folders show in other sections too.
- It's checked wherever entries go into a section: in `canPaste`, so pasting and drag and drop, where a refused target shows the no-drop cursor, and in the destinations `contextFor` hands the transfer picker.
- It only covers entries coming in. Stopping entries from being moved out is the permissions' (see "Permissions"); copying them out is only reading.
- The playground shows each kind on the server sections: Website takes only from API service, API service from anything but Design assets, the Media bucket among them, and Design assets from nothing else, nor takes uploads (`acceptUploads`, see `uploads.md`). The Media bucket takes from every section.

## Permissions

A backend says what it refuses, so the file manager doesn't offer what would only fail; the adapter keeps the final say, and an error it rejects with shows as ever. `EntryPermissions` (`types/adapter.ts`, public) has `write`, `rename`, `move` and `delete`, each allowed unless it's false, so an adapter that sets none allows everything. Copying out, downloading and previewing are only reading, and never refused.

- **Where they come from.** An entry's own (`FileEntry.permissions`), as its folder's listing brings it, and a folder's own, from its listing (`ListResult.permissions`, kept as `FolderState.permissions`), which is how a section's root, in no listing, says what it allows. A consumer can also make a whole section read-only (`Section.readOnly`), whatever its adapter allows, as `importFrom` and `acceptUploads` are the section's; the same folders shown in another section still change there.
- **A folder that can change** (`folderWritable`, `utils/permissions.ts`): its section isn't `readOnly` or the trash (`sectionLocked`, `utils/sections.ts`; see `trash.md`), no move under way is moving it or a folder it's in (`folderMoving`, see "While a move runs" in `transfers.md`), and neither its own listing's permissions nor its entry's, in the cached listing of the folder above (found through the trail, so no id is parsed), set `write` to false; what either refuses is refused (`allows`, `folderPermits`, which a restore asks of the folders entries go back to without the section's `readOnly`; see `trash.md`). A folder neither is cached for counts as writable. Into one that can't, no folder is created, nothing is uploaded, dropped, pasted, moved or copied, and none of its entries is renamed, moved out or deleted, whatever their own permissions, as a read-only folder is on a desktop.
- **Entries** (`entriesAllow`): renamed, moved out or deleted when their folder can change, none is being moved, and each one's own `rename`, `move` or `delete` allows it. Entries being moved can't be copied either, nor dragged, nor pasted from the clipboard (see "While a move runs" in `transfers.md`). A file's `write` keeps Replace from putting another in its place (see "Name clashes"), and is otherwise for the app's own actions, such as an editor's, since the file manager changes no file's contents itself.
- **What follows from them.** `contextFor` leaves out `createFolder`, `createFolderInto` (by the folder inside's), `rename`, `moveTo`, `cut` and `delete`, and `upload` and `uploadFolder` go through `offerUpload`, which asks `folderWritable` as every route of an upload does (the picker, a drop, a paste of files). `copyTo` is left out only when every section the entries could go into is `readOnly`. `canPaste` (`utils/clipboard.ts`, given the store) refuses a folder that can't change and, for a cut, entries that can no longer be moved out, so pasting, drop targets, retrying a transfer and Ctrl+V's files from the desktop all follow it. `ActionContext.readOnly` says the folder can't change, for an app's own action changing it ("Compress…", "New file") to hide by.
- **Dragging.** `useEntryDrag` is given `carries` (`carried` in `file-manager.tsx`: whether the entries can be moved, by their adapter's `move`, or `content` and `delete` across, with `entriesAllow`, or only copied): entries that can't be moved are copied with no key held, the browser's `effectAllowed` is "copy", `dropInto` says each drop copies (`movableInto`), and a touch drag shows its "+" from the start; through an adapter with no `copy` nor `content`, nothing that can't be moved is dragged.
- **The picker** goes through folders that can't change but can't choose them (see "Copying and moving").
- **The lock.** A folder whose own entry says nothing can be put in it (`lockedFolder`: `write` false) shows a lock at its icon's bottom end corner, as GNOME Files marks what can't be written: in the list, the grid, a search's results, the drag image (`ItemIcon`), the sidebar tree's folder rows and the picker's rows, through `LockedIcon` (`components/icons/locked-icon.tsx`, the `lock` icon on a `background.paper` disc, half the icon's size and at least 0.625rem). It's drawn only, so the item says it to screen readers itself, with `aria-description` (`folderLocked`, "Read-only"). It gives way to the touch selection mode's check badge, which takes the same corner. It goes by the entry alone: a `readOnly` section's folders, and folders refused only by the folder above, aren't marked one by one, as every folder of the section would carry one; nor are files, whose `write` is the app's.
- `takesUploads` (`utils/files.ts`) is false for a `readOnly` section and the trash, so the keyboard shortcuts window doesn't list pasting files when only such sections could take them.
- The playground's API service has `migrations` and `go.sum` read-only, by the mock's permissions (`MockNode.readOnly`, which the mock adapter reports on the folder, everything in it and its listing, and enforces, saying "This folder is read-only."), and a "Server logs" bookmark, rooted in API service's `logs`, as a `readOnly` section, while API service still changes the same folder. Its "Compress…" hides by `readOnly`, the preview's "Open in editor" by a file's `write`, and the footer's New folder says "This folder is read-only" there.
- **Name clashes**: Replace keeps what comes in beside an entry the destination has whose permissions refuse writing, a file not replaced, a folder not merged into (`replaceable`, see "Name clashes").

## Cut, copy and paste

`ActionContext.cut()` and `copy()` put the entries on a clipboard held in `file-manager.tsx` (`Clipboard`, `types/clipboard.ts`), not the system clipboard, since ids mean nothing outside their adapter. It holds them by folder (`parts`, each with its section and the adapter serving it): one, or several for a search's results (see "Acting on several folders"), of one adapter or several, each followed by the rules below by its own trail and adapter, and a part none of whose entries is left goes, as does one whose adapter no section serves any more. `paste()` moves (cut) or copies them into the context's `folder`, and `pasteInto()` into the one folder in `entries`, so a folder's menu can offer "Paste into folder", in the content and the sidebar tree alike. Both go as "Move to…" and "Copy to…" do, through the entries' adapter or across into another's. `cut` takes an adapter that moves them itself or hands them over and deletes them (`move`, or `content` and `delete`), and `copy` one that copies them or hands them over (`copy` or `content`). The consumer's actions bind Ctrl+X, Ctrl+C and Ctrl+V like any other shortcut.

- `paste` is offered (`utils/clipboard.ts`, `canPaste`) into a folder every part can go into (`carries`, through its own adapter or across, a cut across taking the entries' `delete` permission too), in a section whose `importFrom` takes each part's section, never into one of them or below one (the target's trail holds every folder above it, so no id is parsed, and only the target's own adapter's ids count), not into cut entries' own folder, and not while another paste is being checked (`offerPaste`). Copies and moves under way don't hold it up. Copying into the entries' own folder duplicates them, as "keep both".
- `dialogs/paste-dialog.tsx` checks the paste unseen and only shows to ask about clashing names, then hands it to the transfer queue (see `transfers.md`). Clashes are looked for in the target's listing, which it loads first when it isn't cached (a folder pasted into from its menu, or dropped onto, may never have been opened). However it ends, the target is listed again, and the source after a cut, with the listings holding them, such as the target's parent (`relistTransferred`).
- While a paste is checked, and while its copy or move waits or runs, the open folder shows its progress bar (`busy`) if it changes it, in whichever section: it's the target, the folder listing the target, or the folder a cut leaves.
- A cut is pasted once, leaving the clipboard as its paste starts; a copy can be pasted again. Entries moved by any route leave the clipboard once moved (their ids may have changed), as do deleted ones, and a renamed entry is replaced by its new self (`withRenamed`, `withoutEntries` in `utils/clipboard.ts`).
- A change that may leave the entries' ids naming nothing, or other entries, as path ids do, has them looked for again (`lookup`, a `ClipboardLookup`), by `hooks/use-clipboard-follow.ts`, through the store's listings, waiting out one being `checking`. The clipboard takes them as they are now, those not found leave it, and a part with none found goes, the clipboard emptying once no part is left; another change to the clipboard meanwhile stops it. Meanwhile nothing is pasted (`canPaste`), and Ctrl+V doesn't upload files from the system clipboard in their place (`pasteFiles`).
  - **By name**, when a folder in the trail is renamed to a new id: it keeps its place there under its new name, and the folders below it, then the entries (a file and a folder by their kind too), are found by name, a listing at a time, as Finder follows them. A rename leaves the names below as they were, so they can be trusted. Cut entries aren't marked meanwhile, as their old ids may name others. A folder on the way gone drops the part. A folder in the trail renamed keeping its id only has its name changed.
  - **By id**, when a folder they may be below is moved or deleted, or renamed to a new id outside the trail: their folder is listed again, quietly (`store.open` with no age), and the entries still in it are kept. Names can't be trusted there, since a moved folder may have taken a free name, or been merged where a same-named entry was kept both. With path ids the folder has gone, so the part goes; with database ids, or a move that skipped the folder, it stays. A listing that fails drops the part too, as the folder may be gone.
  - "May be below" (`reaches` in `utils/clipboard.ts`) is one of the folders, or of those any section has cached below them (`dropFolders`' ids), among the section's root and the trail's known steps, or the entries' section listing none of them, so that it may be rooted further below (`mayBeRootedBelow` in `file-manager.tsx`, read before their listings go, as `dropFolders` has it). That covers a section rooted below a folder another section changes, such as a bookmark, which no id in the trail ties to it.
  - A change found while entries are being found by name that may reach them drops their part.
- Cut entries are marked wherever they're listed: `CutContext` (`contexts/cut-context.ts`) carries their ids by adapter (`AdapterIds`), `hooks/use-cut-ids.ts` gives a section the ids of its adapter, and list rows, grid tiles and sidebar tree rows set `data-cut` for `cutMarker` (see `component-styling.md`). Entries a move under way is moving are marked the same way, by `MovingContext` and `data-moving` (see "While a move runs" in `transfers.md`).
- Ctrl+V pastes into the open folder even with a folder selected, as in GNOME; the playground's "Paste into folder" has no shortcut. On a sidebar tree row, Ctrl+V pastes into that folder. With nothing of the file manager's to paste there, Ctrl+V uploads files copied on the desktop instead (see "Starting an upload" in `uploads.md`).

## Drag and drop

Entries in the content and folders in the sidebar tree can be dragged into a folder in either: a folder in the content, the open folder's empty space, a tree folder, a section row, for its root, or a segment of the path bar. Dropped on the trash's root, they're moved to the trash instead (`offerTrash`), through their own adapter's trash only, and nothing is dragged out of the trash (see `trash.md`). The drop moves them, or copies them while Ctrl or Option (Alt) is held over the target, or where they can't be moved: their adapter can't move them there (`movableInto`, by `carries`), or their folder or their own permissions refuse it (see "Permissions"). Into a folder another adapter serves it copies them, as a drop onto another disk does on a desktop, unless Shift or ⌘ is held, which moves them, as Windows, GNOME and the Finder do. The keys held go to the file manager's `dropInto` (`DropKeys`), which says what the drop does (`Drop`, with whether it copies), and the drop target shows it as the browser's `dropEffect`. It's native HTML5 drag and drop. `hooks/use-entry-drag.ts`, used by `file-manager.tsx`, holds the drag under way and hands it to every view through `DragContext` (`contexts/drag-context.ts`), since a `dataTransfer` can't be read before the drop. Views take drops with `hooks/use-drop-target.ts`: `folder-view.tsx` once on its surface, finding entries by `data-entry-id`, and the tree once per row. A drop runs as a paste (`DropInto` in `types/drag.ts`, `dropInto` in `file-manager.tsx`): the dragged entries become a clipboard of their own, offered by the same `canPaste` rules and run by `paste-dialog.tsx`, so clashes, the transfer panel, refreshing and leaving the real clipboard work as they do there, and the real clipboard is left alone. There's no consumer action for it. What a drag can do is `carried` in `file-manager.tsx` ("move", "copy" or nothing, which `useEntryDrag` takes as `carries`): an adapter with neither `move` nor `copy` nor `content` has nothing draggable (`canCarry`), and entries that can be neither moved out nor copied don't start a drag.

- A drag carries its pane's selection when it starts on a selected entry or tree folder; otherwise that one is selected and dragged alone, as with the context menu. In the tree, the open folder alone counts as selected until something else is.
- Entries drag by any part of their list row or grid tile, which also take drops for a folder; a marquee starts only from the empty space around them. Tree rows drag by any part too, so their main part is a plain div rather than a button, since Firefox starts no drag from a `<button>`.
- Section rows take drops but are never dragged: a section is the consumer's root, not an entry.
- The open folder's empty space, or a file in it, takes only entries it doesn't list already, so a drag from the content that ends there does nothing, Ctrl or not. Dropping a folder onto its own parent in the tree with Ctrl does duplicate it, as pasting a copy there does.
- A drag resting on a collapsed tree folder or section row for 700 ms (`HOLD_DELAY`) expands it (`onHold`, and `expand` in `file-manager.tsx`, which never collapses), whether it takes the entries or not.
- A drag resting on a folder in the content, the list, the grid or a search everywhere's results, for as long opens it, as spring-loaded folders do in GNOME and the Finder, whether it takes the entries or not, but for one of the folders dragged, whose insides they can't go into. It's an ordinary opening, into the history, ending a search, and the drag goes on in the folder opened, where it can rest on a folder again.
- **The path bar** (`header-bar/path-bar.tsx`): each segment (`Crumb`) takes drops into its folder, the section's into the root, by the same `canPaste` rules as a tree row, so a folder can't go into itself or below, and with Ctrl a copy into the entries' own folder duplicates them. Files from outside are uploaded there too. It's marked by `dragMarkers`, and a drag resting on a segment but the open folder's opens that folder, as GNOME's path bar does.
- **The sidebar during a drag**: while it's collapsed or hidden, a drag of entries or of files resting on the header's "Show sidebar" button (`useDragHold`, which takes no drop: it cancels the drag events saying "none", so the browser keeps sending them to it, as it wouldn't after a `dragenter` left alone, and shows its no-drop cursor; a touch drag reads that as nothing there. It marks the button as hovered through `data-drag-over`) shows it for that drag: the overlay while collapsed, or, docked but hidden, the sidebar over the content as the overlay is (`peek`, `data-peek`), so the hidden setting isn't changed. It goes again once the drag ends, dropped anywhere or called off (`endSidebarForDrag`), and for files from outside, as they leave the file manager, as the file manager never hears how such a drag ends. A sidebar already showing is left as it is. The backdrop lets drops through meanwhile.
- A drag goes on when the element it started from goes, as when resting on a folder opens it, which takes the view away. Its `dragend` then never reaches the root, so `useEntryDrag` also listens on the element itself, which some browsers still send it to, and ends the drag at the next move or press of the mouse once the element is gone, since browsers send none while dragging.
- **Touch and pen** (`useEntryDrag`'s `touch`): a press scrolls, so a touch drag starts from a long-press (`useLongPress`, 500 ms) and the finger moving on 8px without lifting. Lifting it without moving does what the long-press does by itself: in the content, selection mode with the entry selected; on a tree row or a search everywhere's result, the row's or result's menu at the press, a tree folder's offering `select()` (in the tree's selection mode, a long-press on a folder selects it instead, and lifting does nothing more), as a right-click would open it, so iOS, which never fires `contextmenu` for a long-press, has those menus too. The browser's own touch menu is swallowed on them (`onContextMenuCapture`).
  - What it drags is what a mouse drag from there would: in the content, the entry, or in selection mode the whole selection, which the long-press adds the entry to (keeping it if it's selected already); in the tree, the folder, or in selection mode the selection, which the long-press adds the folder to, or a new one with it alone under another parent; in the results, the result, or the selection, by folder. Section rows are never dragged, so after their long-press the finger scrolls.
  - It's the file manager's own drag, since browsers drag by touch differently or not at all: it sends the views the `dragenter`, `dragover`, `dragleave` and `drop` a mouse drag would (built `DragEvent`s with a `DataTransfer` of their own) at what's under the finger (`elementFromPoint`), inside the root only, so nothing outside the file manager is sent events it never asked for. So every drop target, mark and hold works as with a mouse, opening folders, expanding the tree and showing the sidebar included. They're sent again every 150 ms while the finger rests, as browsers send dragover, so what a hold opened under the finger is found.
  - It does what the target says a drop with the keys held would, as with a mouse: moves the entries, as the phones' and tablets' file apps do, or copies them where only that can be done (they can't be moved out, `copyOnly`, or a move is refused there), into a folder another adapter serves, or while Ctrl or Option (Alt) is held on a tablet's keyboard, the events saying so with Ctrl held; Shift or ⌘ held moves them into another adapter's folder, the events saying so with Shift held. `send` reads what the target set as the event's `dropEffect`. Without a keyboard, copying by touch within an adapter goes through Copy and Paste, as those apps have it, and so does moving into another's, through Cut and Paste. Letting go where nothing takes them does nothing.
  - The drag image (`drag-preview.tsx`, `touch`) follows the finger, above it and on its end side, so the finger doesn't hide it, placed through its `transform` each frame, and shows a "+" where letting go would copy, fading where it would do nothing (`effect`). Near a scrolling area's edges, 40px deep, the area under the finger scrolls, either way it scrolls (the path bar sideways), faster nearer the edge.
  - The page mustn't scroll under the finger meanwhile, which would also take the press away (`pointercancel`), and only a touchmove listener that isn't passive and is there when the touch begins can refuse that, so one sits on the root for good, refusing only while a drag is held or under way. While a touch or pen presses, the root's `data-touch-press` sets `-webkit-user-drag: none` on what's draggable, so no browser starts a drag of its own on a long-press.
  - `pointercancel`, or Escape on a tablet's keyboard, calls it off. The marquee stays mouse only.
- Dragged entries fade wherever they're listed (`hooks/use-dragged-ids.ts`, by adapter as cut entries are, `DragContext.dragged` holding their ids by adapter), and the folder they'd go into is highlighted through `dragMarkers`, or for the open folder by the panel's outline (see `component-styling.md`). A folder that can't take them (one of them, below one, or while another paste is being checked) isn't highlighted and the browser shows its no-drop cursor.
- While entries are dragged, or the overlay sidebar shows for a drag, its backdrop lets drops through to the content under it.
- The drag image is `drag-preview.tsx`, rendered by `file-manager.tsx`: the grabbed entry's icon and name on a card, stacked on a card per other entry (5 cards at most, each 4px further down and towards the end, and fainter), with a count of them all when more go along. It's rendered into `<body>` at the top corner for a single frame (`flushSync`), handed to `setDragImage`, and removed in the next animation frame, before it's painted. Safari cancels a drag whose image is wholly off screen, so it isn't placed off screen.
- The drag ends on `drop` as well as `dragend`, both caught on the file manager's root once they've bubbled up, since a move can remove the source row before `dragend` arrives. Every target's highlight clears once no drag is under way. Files dragged in from the desktop go to the same targets and are uploaded (see `uploads.md`); files dropped anywhere else in the file manager are refused, so the browser doesn't open them in place of the page. Other drags from outside, such as text, are left to the browser.

## Sorting

Sorting is client-side, in `utils/sort.ts`. `file-manager.tsx` owns the `SortOrder` (a key of name, size, type, modified, relevance or location, plus a direction), which persists across folders and the consumer can control (`sort`, `defaultSort`, `onSortChange`; see `props.md`), and `folder-view.tsx` sorts the listing with `entryComparator`. So can the view, list or grid (`view`, `defaultView`, `onViewChange`). Names and type labels compare in the `locale` prop's collation (`Locale.compareNames`), and the keys' and directions' labels come from the text (`SORT_LABELS`; see `locale.md`).

- Folders always come first. Ties fall back to the name, A to Z.
- **Relevance** is the default key (`defaultSort`) and ranks a search everywhere's results (see "Searching everywhere"). It means nothing in a folder, which goes by name, A to Z instead (`folderSort`, which `entryComparator` applies too), so the menu and the list's headers show that order there. The view menu offers Relevance, first among the keys and with no directions, only while the results show (`resultsShown`); picking another key there orders the results by it, and it stays when the search ends.
- **Location** orders a search everywhere's results by where they are, the section and then the folders, and the trash's root by where its entries were moved there from (`entryComparator`'s `locationOf`), A to Z, folders first still. It means nothing in any other folder, which goes by name, A to Z (`folderSort`'s `located`, true for the trash's root), and the view menu offers it after Name only where the list shows a Location column (`LOCATED_SORT_KEYS`), whose header sorts by it too, named "Original location" in the trash (see `trash.md`).
- Picking a key starts it in its own direction: names, types and locations A to Z, sizes and dates largest and newest first.
- Two controls share the order:
  - The header's chevron menu (`header-bar/view-menu.tsx`), with radios for the key and the direction.
  - The list view's column headers, where a click on the active column reverses it.

  The menu is the only control in the grid view, and in a list too narrow for its header row.
- The sidebar tree ignores it and stays by name (`nameOrder`), as does the transfer picker. Section order is the consumer's.
- The same menu has a "Show hidden files" checkbox (see "Hidden files"), and, while the sidebar docks, "Show sidebar" (see "Hiding the docked sidebar"), "Show properties", and zooming (see "Zoom").

## Hidden files

"Show hidden files" in the header's view menu, off to start with, is `showHidden` in `file-manager.tsx`, which the consumer can control or start on (`showHidden`, `defaultShowHidden`, `onShowHiddenChange`; see `props.md`), e.g. to keep it across reloads. Ctrl+H turns it on and off from anywhere in the file manager, as in GNOME Files, and the menu shows the key beside it (`showHiddenFilesShortcut`, as the language's keyboards name it). It's Ctrl only, not ⌘, since ⌘H hides the browser on macOS before the page sees it (see `keyboard.md`). It persists across folders, as the sort does. Whether an entry is hidden is `isHidden` (`utils/hidden.ts`): the entry's optional `hidden` when the adapter sets it, or else a name starting with a dot. So a backend with its own idea of hidden says so, and `hidden: false` keeps a dotfile always shown.

- Listings are filtered where they're shown, never in the store, so clash checks (the paste, upload and name dialogs) and `relist` still see every entry: a hidden name can clash too.
- The content view (`folder-view.tsx`) leaves hidden entries out before sorting, so selection, Select all, type-ahead, the marquee, the arrow keys, the selection bar's total, the screen reader's count and the preview's stepping (the `listing` of a `MenuRequest`) all go by what's shown. A folder holding only hidden entries reads "Folder is empty", as in GNOME Files.
- The sidebar tree (`use-tree-rows.ts`) leaves out hidden folders, and a folder whose listing holds none that show loses its chevron. `sortedFolders` keeps both the whole sorted list and the unhidden one per listing. Expanded state is kept by folder key, so a hidden folder comes back as it was.
- The "Move to…" and "Copy to…" picker leaves them out too, so a hidden destination is reached by turning the option on first.
- The open folder stays open when it is hidden and the option is turned off, or when it's reached with it off, and the path bar shows it; only what's listed in it is filtered.
- Selected entries that get hidden stay in the selection's id set, since the listing still has them, unlike removed ones, but don't count: `selected` only holds listed entries. Turning the option back on brings them back selected. `onSelectionChange` has them in its ids but not its entries.
- A created or renamed entry to be revealed (`revealId`), or a folder left through that is hidden, is given up on while hidden entries are off, rather than waiting for a listing that will never show it.
- `childCount` and `hasSubfolders` are the adapter's own and count hidden entries as the backend does.
- An entry or tree row that has the focus when it gets hidden hands it on as a removed one does: to the entry now in its place, or the row shown before it.

## Zoom

The list and the grid each zoom, as in GNOME Files, by steps from the size they start at: the list's icons or thumbnails beside the names (75%, 100%, 150% and 200% of 1.75rem) and the grid's (75% to 300% of 3.5rem), with the list's rows and the grid's columns growing with them (`LIST_ICON_SIZES`, `GRID_SIZES` in `styles/layout.ts`). Text stays as it is, which is the browser's zoom's job. Each view keeps its own step, so switching views keeps both, and it persists across folders, as the sort does. The consumer can control it (`zoom`, `defaultZoom`, `onZoomChange`, a `ViewZoom`; see `props.md`).

- `utils/zoom.ts` turns a step into sizes (`listIconSize`, `gridSize`), a step beyond a view's sizes counting as the nearest end, and steps it (`zoomedBy`, `canZoom`), from where it shows, and gives its size as a share of its start (`zoomScale`). `zoomContent` in `file-manager.tsx` zooms the view shown and announces the size it's at (`zoomChanged`, "Zoom 150%", through `formatPercent`), as nothing else says it; from the view menu that waits until the menu closes, as a menu hides the rest from screen readers, but the percentage there says it meanwhile.
- **Keys**: Ctrl+plus (or Ctrl+=, beside it on a US layout), Ctrl+minus and Ctrl+0, ⌘ too, as browsers zoom a page (`zoomStep` in `utils/shortcut.ts`, + and - as typed wherever the layout has them, 0 the key printed with it), handled by the root but **only with the focus in the content panel** (the folder view or a search's results), so the browser's own page zoom still works from the sidebar, the header, the panels and outside, for those who rely on it. A consumer's shortcut on the same keys runs first in the content, as any does.
- **Ctrl+wheel and pinching** over the content panel (`hooks/use-wheel-zoom.ts`, non-passive listeners on `panelRef`): a mouse's notch is a step, and a touchpad's pinch, which Chrome and Firefox send as Ctrl+wheel, steps every 50px it travels, counted afresh after a 250 ms pause or a turn the other way. Safari sends a touchpad's pinch as gesture events, which step every 1.4× the fingers spread or close; on a touch screen, where it sends them alongside the touches, they're left to the browser. Ctrl+wheel over the content never zooms the page, even at a view's end.
- **The view menu** ends, after a rule, with a "Zoom" subheader (`zoom`), styled as "Sort by", over a row across the menu as browsers' menus have one: a round Zoom out button, the size as a percentage between, which puts it back (named `zoomResetFrom`, "150%, reset zoom", its tooltip `zoomReset`), and a round Zoom in (`zoomIn` and `zoomOut` shared with the preview), each with a tooltip, its `aria-keyshortcuts`, and disabled where it can't go, the menu staying open. They're `MenuItem`s shaped as buttons, in a `group` `li` named by the subheader, since MUI 9's menu only moves the focus between the items registered with it (its roving tab index, in page order), so Up and Down reach them as any item.
- The list sets `--icon-size` on itself, which its rows' heights (`max(52px, icon + 16px)` narrow, where the size and date fold under the name, `icon + 16px` from `viewMedium`) and the Name header's inset follow, and the grid sets `--column` and `--wide-column`, its narrowest columns, below and from `viewMedium`. Every row and tile is still as tall as the others, as the virtualization needs.
- As the lines change size, the entry at the panel's top stays there (see "Lines" in `virtualization.md`), and with the focus in the view, the focused entry is scrolled into view too (`zoomedFrom` in the folder view and the results).
- Larger thumbnails are asked for as a view zooms in, the smaller ones showing meanwhile, and a larger one kept serves a smaller size (see `thumbnails.md`).
- The sidebar tree, the picker and the drag image don't zoom.
- Not yet: a pinch on a touch screen zooms the page, not the view, as the content takes the touch to scroll.

## The parts

- The sidebar tree is flat: `hooks/use-tree-rows.ts` turns the sections and the listings of the expanded folders into the rows the tree shows, each placed where it goes, and lists a folder once the tree comes to show its folders. `sidebar/location-item.tsx` renders one row each: a section, a folder, a folder that couldn't be listed or a single section's status (`TreeItem` is the shared `treeitem`), and the guide lines along expanded folders. Only the rows in or near view are rendered (see `virtualization.md`). A section with `showFolders: false` is a plain GNOME-style place: no chevron, no tree, and it never starts expanded. The default is `true`.

## Single section

`FileManager` takes either `sections` (groups) or a single `section`, never both; `FileManagerProps` is a union that enforces it. A location (`defaultLocation`, `location`) names the single section by its id too. Inside, a single section becomes one group of one, so navigation, the store and the path bar don't tell the modes apart. Only the sidebar does:

- `useTreeRows`, given the `single` section, lists the root's folders as the sidebar's top level, with no section row and nothing to collapse. The root loads straight away and shows loading, empty ("No folders") and error rows in place of the tree.
- The root itself is reached through the path bar's first crumb, since there is no row for it. There is no sidebar menu for the root either; the content background's menu covers it.
- With `showFolders: false`, the single section falls back to its plain row, so the sidebar isn't empty.

The playground shows this mode with `?single` in the URL.
- `header-bar/` holds back/forward, the path bar, the search field and the path field that take its place while searching (see "Search") and typing a path (see "Going to a path"), and the view buttons. Below `rootMedium` the path bar gets a full-width row under the buttons; from `rootMedium` up, it sits centred between them.
- `content/folder-view.tsx` loads the open folder and shows the loading, empty and error states around the list view (`file-list.tsx`, a `--columns` grid template) or the grid view (`file-grid.tsx`), which render only the entries in or near view (see `virtualization.md`). It highlights for a moment what uploads just put in the folder (`arrivals`, `data-arrived`), and scrolls to what "Show in folder" asks for, never selecting it (see "Showing what arrived" in `uploads.md`).
- Under the header bar, a row holds the content with the transfer, download and upload panels under it, and the properties pane (`properties-pane.tsx`), docked on its end side from `rootExtraWide` or an overlay below it (see `properties.md`).
- `content/trash-bar.tsx` sits above the trash's root in the content panel, with its button emptying it (see `trash.md`).
- `content/no-sections.tsx` takes the content's place while there's no section, as while an app is still getting its sections: "No sections to show" (`noSections`) with the folder icon. Meanwhile the header's folder search and Select buttons are disabled (`hasFolder`), and the empty tree leaves the tab order. Once sections come, the one opened in starts expanded, as it would have on mounting, when the file manager keeps the expanded folders and wasn't given `defaultExpandedFolders` (`expandsFirst`). The playground's `?lateSections` hands the sections over 3 s after the page opens.
- `dialogs/` holds the modals, which portal to `<body>` like the context menu: `name-dialog.tsx`, `transfer-dialog.tsx`, `paste-dialog.tsx`, `delete-dialog.tsx`, `restore-dialog.tsx`, `upload-dialog.tsx`, `preview-dialog.tsx` and `shortcuts-dialog.tsx`, with `conflict-step.tsx` shared by the transfer, paste, restore and upload dialogs, and `image-viewer.tsx`, the preview's image, which zooms, pans and turns.
- The transfer, download and upload panels under the content are `components/transfers/transfer-panel.tsx`, `components/downloads/download-panel.tsx` and `components/uploads/upload-panel.tsx`, outside `file-manager/` since they're meant to be shared (see `transfers.md`, `download.md` and `uploads.md`). Their look is `styles/panel.ts`.
- `components/icons/icon-slot.tsx` (`IconSlot`) fits consumer-supplied icons to the same 1.25rem box as the built-in ones, for the menus, the tree, the path bar, the picker and the headers' actions (`components/buttons/toolbar-actions.tsx`).
- `utils/format.ts` builds the `Locale`: the text, and the formats for sizes, dates and type labels in the `locale` prop's language (see `locale.md`).
